## (2) Red does not return fire / run
Hypothesis: red cannot target L1 (reach up 0) and the code only flinches an idle unit, so a marching red just walks on.
Evidence (PROVEN):
- The 13 hill shots hit red 46 (10x), 67 (2x), 32 (1x) in main; 46 (10x), 32, 69 (2x) in control. Shooters 2,3,4,5,6,8, all layer 1. At every one of these hits the victim has target 0 and still has a destination (attack-move to the pocket), checked from the per-tick trace (analysis: 13/13 victim target 0, destination set). Red 46 walks x=1850, y 2738 -> 2486 at constant pace across ticks 781-829.
- Red is not firing back at the arc for the same reason it is not at the hill: against the arc (same layer) red does return fire (1001 red shots; victims show `target` = their shooter).
- Reach: lab sets every type to reach 0 up, 1 down (run.py:REACH_UP, REACH_DOWN, `engine.set_reach`); `om_tac_in_reach` (csrc/unit.c:573) is false for a red looking up at layer 1. R-005-09: low ground never sees up. The control (sight off) does not change this: reach still blocks, so red cannot target in either fight. Answer to Westley's question: yes, blue is a band up, red cannot see or reach it.
- What the code does when hit by a thing it cannot target: csrc/unit.c:2156-2172 (`last_attacker` branch). Entry needs `order == NONE || (pursue && order == ATTACK_MOVE)` and `target_id == 0`; for `!om_tac_in_reach || stealth || noncombat` it calls `om_tac_start_flinch` ONLY `if (u->order == OM_ORDER_NONE)` (line ~2169). An attack-moving red (every red here) falls through: nothing happens. Also unit.c:2142-2145: a flinch is cancelled at once if the unit has any order. Flinch (unit.c:2026) = 200 wu directly away (OM_RETURN_FIRE_FLEE_DIST, om_constants.h). PURSUE_BY_STEERING default is 1 (checked with get_param).
Bible: NOT a pure gap. R-087-01 (docs/bible/epics/E-11-units-and-combat.md:~142) already says "a unit taking damage from an attacker it cannot see or cannot reach moves 200 wu directly away and stops", unqualified; ALG-62 (algorithms.md:266) says the same for a unit that cannot return fire; E-11 note line ~156 says the visible-but-unreachable branch is not built. But R-087-02 (order wins over auto-engagement) and R-087-06 (attack-mover returns fire; "an already-engaged unit ignores incoming damage") never say what an attack-mover does when it cannot return fire, and the code reads R-087-01 as idle-only. So: R-087-01 exists, its scope over attack-moving units is unwritten. Westley's SC2 rule is that gap.
Candidate rule text (not decided): "R-087-10 Given an idle or attack-moving unit with no target, When it takes damage from an attacker it cannot target (outside its reach, unseen by its side, or stealthed), Then it leaves the line of fire: it moves up to 200 wu away from the attacker, then resumes its attack-move toward its original point (R-096-02); a plain-moving unit and a guard (R-096-08, never walks off) ignore it; repeat hits re-trigger it."
Hook: unit.c:2169 (drop the `order == NONE` condition for ATTACK_MOVE, keep the original order point) and the flinch-cancel at unit.c:2142 (must not cancel a flinch that was started for an attack-mover). Note `om_tac_step_toward` moves the unit by position write, not by routing; check it against terrain/blocked cells before using it for a 200 wu walk. Resume = reuse the anchor/return path (anchor_set 2, `om_tac_return`).
Scale: 13 hits, 71-74 hp in total; the visible effect is the lines in frame 1.

## (4) Blue units at the left vantage fire / do not fire in the same situation
Hypothesis: not random; a deterministic result of unit type range, the 4-tick targeting stagger, and a position that jitters across a collider cell boundary.
Proof it is deterministic (PROVEN): main and control fight files byte-identical on rerun; per-tick state of all 72 units over 12000 ticks identical across 4 runs, seeds 10, 10, 11 and 3028; all 20 committed seed files identical after zeroing the seed field. No rng draw is reachable from the tactical step in this fight (the only `om_rng_draw` outside strategic code, tactical_support.c:785, is a drift fixture); units iterate by id, grid ties broken by (d2, id) (unit.c comment above `om_tac_nearest_enemy_within_range`). Reading state every tick (can_see/can_shoot) changes nothing: 1080 unit-frames of the committed file match the per-tick traced run exactly. CHECK_EVERY (run.py:41) only samples first_seen, blocked and silence; it does not touch the sim.
What differs between the eight left units (exact, from fire.py + probe.py, ticks 770-850), the only hill shots of the fight:
1. Range, not luck: Vanguards 1,3,5,7 have range 300; Wardens 2,4,6,8 have 350 (run.py ranges; the fight file `ranges`). Red 46 passes at 311-390 wu from units 1 and 7: both Vanguards never come in range and never fire (0 ticks with a target in the whole window).
2. Cohort stagger: a unit can pick a new target only on tick % 4 == (id-1) % 4 (unit.c:1727, :2242; R-087-08, ALG-62). The first shot of every shooter lands exactly on its slot tick: 2@781, 6@789, 5@796, 8@799, 3@810, 4@815 (slots 1,1,0,3,2,3). Unit 4 was 351 wu away on its tick 811 (range 350) and in range on 815.
3. Cell-boundary jitter: the walkers push into the padded collider and are pushed out, so their y oscillates around 2500 (e.g. unit 4: 2497.3-2504.5 over a few ticks). A unit whose cell is the blocked row y<2500 (x 1400-1700) has no line: of 620 unit-ticks in the window, all 73 with origin inside the collider have can_shoot false (100%), and can_shoot flips 43/33/33/17/15 times for units 1,3,4,2,7 but 0 times for units 5,6,8, which stand at y 2530-2535 (outside the blocked row). can_see also flips (fog uses the same grid), e.g. at tick 829 red 46 is unseen by units 1,2,3,4,7 and seen by 5,6,8.
Net: at the sampled frame (tick 800) units 2,5,6,8 hold target 46 and 1,3,4,7 do not: 1,7 out of range, 3,4 waiting for their cohort turn / standing in the blocked row. Not random: a function of unit id, type range, red position and sub-wu-to-6 wu position.
Control frame 15 (tick 12000): units 3,4,5,6,8 hold stale targets (32 and 69) 500-700 wu away and do not fire; 1,2,7 hold none. Cause: with a pursuing attack-move a target that left range is kept until a cohort turn finds another (unit.c:2216 "P1"); cross-layer acquisition only happens within attack range (`om_tac_pick_across`, unit.c ~1750), so only units that were in range when red passed (those 13 shots) hold a target; 1 and 7 never were. The holders try to walk to the target (destination = target) into the collider and stand still at y~2500: that is the `blocked 5` on the frame. No sight, no random.
UNPROVEN: why unit 2 in the control ends with no destination at (1711,2488) while 3-8 keep one (order dropped, probably the move give-up pass, tactical_move.c `om_move_giveup_pass`; not traced).
