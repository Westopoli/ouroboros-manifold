# H-066: qa-port-unique

"Two gates running at the same time never play on each other's game."

Flag harness; tool Workflow; no scene. Ready 2026-11-02; Channel: lab. Finding by the lab Dispatcher 2026-11-02 (while diagnosing the replay flake on push/b-h063); made urgent by DEC-two-gate-channels-2026-11-02 (two gates and so two pytest runs at once are now normal).

## Why

Evidence 2026-11-02 (the lab Dispatcher's probe): the cause of the second sweep red (swept sha cc34c657, `tests/qa/desktop/plays/C/s140_land.py` in setup) is a TCP self-connect in `wait_for_port` (`tests/qa/desktop/daemon_client.py`, lines 197 to 210). The QA port range 47500 to 47599 lies inside the Linux ephemeral range (32768 to 60999). Occasionally `connect()` to a closed 127.0.0.1:P is given source port P and the socket connects to ITSELF (TCP simultaneous open) with nothing listening; `wait_for_port` sees a successful connect and returns at once (the 0.07 s). The self-connected socket then closes, the port stays in use (TIME_WAIT), Godot's listen fails (the leaked game's stderr says `ERROR: qa_daemon: cannot listen on 127.0.0.1:47506 (err 22)`, ERR_ALREADY_IN_USE) and the first real call is refused (connection refused in `client.state()`). The test fixture raised without `stop()`, so the game leaked (orphan Godot, parent systemd). Reproduced: 7 self-connects in 400,000 connects to closed 127.0.0.1:47506 (about 1 in 57,000), and every time a bind to 47506 right afterwards failed with EADDRINUSE; on Linux it is deterministic: a socket bound to (127.0.0.1, P) and connected to (127.0.0.1, P) connects, and `getsockname()` equals `getpeername()`. No foreign listener was found (each play had its own godot.real as the listener when the wait returned). Also found: `stop()` SIGKILLs the process group and waits only on the xvfb-run shell, not on Godot, so about 100 TIME_WAIT sockets sit on 475xx between plays.

The first red (swept sha 4dbb0f68, present-on-boot) has the same symptom and probably the same cause (unproven; to confirm, the sweep log's refused port should match a `cannot listen ... err 22` line in the game's stderr).

A second hazard, real but unobserved: `pick_free_port()` picks a random port in 47500-47599 by binding and closing a socket; Godot opens that port later. Two concurrent pytest runs can pick the same port in the gap, and `wait_for_port` would then connect to the other run's Godot (wrong state, or a timeout). Not reproduced in six concurrent runs; scratch dirs and the xvfb display are already per-run, so the port is the one shared name left.

## Change (test infrastructure only; a clerk, under `docs/method/rulebook.md` with a Test-defect trailer, since the files are under tests/)

Six parts, all in the harness; no game-side change. Part 6 is the direct fix of the proven cause (the self-connect); parts 1 to 5 are defence in depth and cover the second hazard.

1. `pick_free_port()` tries the ports 47500 to 47599 in random order; for each it takes a non-blocking `flock` on `<push root>/tmp/qa_ports/<port>.lock` (the push root is the one the sibling scripts use, `$HOME/Projects/om-push` unless overridden), keeps the file descriptor open for the life of the process, then checks that the port binds; a lock it cannot take means the next port; when none is left it RAISES an exception whose message holds `QA PORT REFUSED no free port`. Add a one-line `# See also:` comment at the pick site pointing at this story.
2. Identity check after `wait_for_port`, with no game-side change: find the pid that owns the listening port by reading `/proc/net/tcp` for the listening inode and scanning `/proc/<pid>/fd`, and require that pid's process group to equal the Popen's pgid (`GodotGame` uses `start_new_session=True`, so the game and `xvfb-run` share the group); otherwise PRINT `QA PORT FOREIGN <port>` (stdout or stderr; the message is not raised, the retry loop continues): stop the game, pick another port and relaunch, up to 3 tries, then raise. The check also catches a self-connect (no listening inode at all) and a foreign listener, whatever let `wait_for_port` return early.
3. The `game` fixtures stop the game when setup raises (`try/finally` around `start`, `wait_for_port` and the first state call), so nothing leaks.
4. Teardown waits for process exit (and the port to be free) before the lock is released. The reason: `stop()` SIGKILLs the process group and waits only on the xvfb-run shell, not on Godot, so the teardown must wait on the Godot process itself.
5. If Godot exits early or its stderr contains `cannot listen`, the same retry path as part 2: stop, new port, retry (up to 3 tries, then raise).
6. The direct fix: `wait_for_port` treats a connected socket whose `getsockname()` equals its `getpeername()` as NOT ready; it closes that socket and keeps polling. A self-connect looks like a listener to a plain `connect()`, and this is the only place that gives it a chance to pass.

The port range 47500 to 47599 is unchanged (other scripts use 47590 to 47593).

Not in this story: any change to `autoload/qa_daemon.gd` (the harness now sees and stops the failure; a game-side exit-on-listen-failure stays a finding row unless the harness cannot see it).

## Tests

`tests/qa/desktop/test_qa_port_unique.py` (new; a different Sonnet writes it, red on main). The helper `tests/qa/desktop/qa_port_fakes.py` (fake godot and xvfb-run on PATH, a decoy listener in its own session, HOME in a scratch dir) is part of the fenced tests; the run is hermetic and takes about 11 seconds; the retry tests use real ports 47500 to 47599, so a busy machine could skew them; scope 4's 'port free before the lock is released' is checked as an ordering at the first instant the lock becomes takeable, because a fake that dies instantly cannot tell it from kill speed.

1. Eight processes started together, each calling `pick_free_port` with the same random seed, return eight distinct ports.
2. Positive control: the old picker (bind, close) called by the same eight processes with the same seed returns the same port in at least two of them.
3. When all 100 ports are locked, `pick_free_port` raises with `QA PORT REFUSED no free port`.
4. A lock file left behind by a dead process does not block a port (flock is released on process exit).
5. A foreign listener (a plain socket listening on the picked port, in another process group) is detected: the helper prints `QA PORT FOREIGN <port>` and ends up on a different port; positive control: a listener inside the game's own process group is accepted.
6. A fixture whose first state call raises leaves no process behind (stubbed game: the process is gone after the fixture error).
7. A game whose stderr says `cannot listen` or that exits early is retried on another port, up to 3 times, then raises.
8. Teardown does not release the port lock until the process has exited (stubbed slow-exit process).
9. Self-connect: a socket bound to (127.0.0.1, P) and connected to (127.0.0.1, P) (getsockname equals getpeername) makes `wait_for_port` keep waiting, not return; control: a normal listener on P is accepted at once.
