# H-084: play-leaves-no-game-behind

"A play never leaves a game running after it ends, however it ends, and a scene that needs a file to show anything is never passed without one."

## Finding (read from `origin/main`, 2026-11-04)

1. **The game outlives the play.** `scripts/play.sh` starts Godot with `setsid nohup ... &` (own process group) and keeps its pid in `gpid`. It ends the game with `kill "$gpid"` on two paths only: the scene mismatch (`PLAY REJECT scene`, exit 3) and the end of the proof (after the capture). Both window checks that time out (`PLAY REJECT wayland window`, `PLAY REJECT window unmapped` / `no window`, exit 2) `exit` with the game still running. There is no `trap`; the only trap is the `--tree` scratch removal. A `play.sh` ended by a signal (the reaper at its TTL, a Ctrl-C) leaves the game too.
2. **The register cannot see it.** The clerk starts `play.sh` through `proc.py start`, so the record holds `play.sh` only. When it exits, `proc.py reap` logs `PROC GONE` and archives the record; the game, reparented to systemd, was never recorded and is never reaped. Observed 2026-11-04: two such Godots at 800% and 470% CPU, load average 22 to 37.
3. **It feeds itself.** Under that load llvmpipe drops to 11 to 20 fps, the window check needs 30 fps for 3 s, so later plays reject with `PLAY REJECT wayland window` and leak again (runner-lab, 2026-11-04).
4. **A grey proof passes.** `fight_replay.tscn` draws a fight read from `OM_FIGHT`. The story `Scene:` line can carry launch arguments but no environment, so the H-053 and H-063 plays launched the scene with no fight file; `qa_state` still reports the scene, so `--check` passed and the portal proof showed an empty replay.
5. Separate, not in this story: `fight_replay.gd` formats `%r`, which GDScript does not support (`push_error("... %r ..." % path)`, `origin/main` line 40), so the message for a bad `OM_FIGHT` itself errors. A client finding for the next `fight_replay` story.

## Change

Files: `scripts/play.sh`, `docs/method/story_loop.md` (the Machine lines paragraph), `tests/method/test_play_cleanup.py` (new, the writer's). No change to the gate, to `proc.py`, or to the game.

1. `play.sh` ends the game it started on every exit path: a single `trap` on `EXIT`, `INT` and `TERM` signals the game's process group (`kill -TERM -- -$gpid`, then `KILL` after DRAFT-play-term-s 5 s if it is still there) and is cleared once the game is already gone. The existing `kill "$gpid"` lines go; the scratch removal trap is kept inside the same handler. A `SIGKILL` of `play.sh` itself cannot be trapped and is out of scope (named in the test file as such).
2. A new Machine line `Scene-env: KEY=VALUE [KEY=VALUE ...]`, read by `play.sh --story` with the `Scene:` line. A value that is a path in the tree is resolved against the tree before launch. The game starts with those variables set. When a value names a repo path that does not exist `play.sh` prints `PLAY REJECT scene input missing <KEY> <path>` and exits 5 before the build. No line, no change (every story that exists today).
3. `story_loop.md` step 2 names the line. The H-053 and H-063 story files gain a `Scene-env:` line in their own landing; this story does not edit them.

## Tests (`tests/method/test_play_cleanup.py`, written first by a Sonnet who does not build, red on main)

Same fakes as `tests/method/test_play_proof.py` (stub Godot in a fake HOME, stub `xdotool` / `xwininfo`, no real display, no portal, nothing captured). The stub Godot writes its pid to a file and sleeps.

- RED on main, the bug: with the stub never reaching 30 fps, `play.sh --check` prints `PLAY REJECT wayland window ...` and exits 2, and the stub's pid is still alive afterwards. Same for the X11 variant (`PLAY REJECT no window`). After the fix: gone within DRAFT-play-term-s.
- RED on main: `play.sh` sent `TERM` while waiting for the window leaves the stub alive; after the fix the stub is gone.
- Controls (already green, stay green): the scene-mismatch path and the success path leave no stub alive. The positive control for the detector is a stub that ignores `TERM` and a stub that handles it, checked with no `play.sh` involved; through `play.sh` the TERM-ignoring stub is RED on main (no `KILL` step) and green after the fix.
- RED on main: a story file with `Scene-env: OM_FIGHT=docs/none.fight.json` (file absent) makes `play.sh --story X --check` exit 5 with `PLAY REJECT scene input missing OM_FIGHT`; with the file present the stub Godot's environment holds `OM_FIGHT=<absolute path in the tree>` (control).
- A story with no `Scene-env:` line launches exactly as today (the dry-run `launch:` line is byte-identical to main's).

## Rulings (2026-11-04, on the test writer's report; DEC-h084-rulings-2026-11-04, Westley may veto)

1. **A run for a human.** Plain `play.sh` without `--check` hands the game to the person after the window check; that success stays running by design. The cleanup trap ends the game on every other exit: any `PLAY REJECT`, any signal during the wait, and every `--check` exit. It is cleared at the moment of a successful non-`--check` handoff. Test: a non-`--check` run that passes the window check leaves the stub alive (control); the same run rejected at the window check leaves none.
2. **Path or plain value.** A `Scene-env` value containing `/` is a path in the tree; a value without `/` is plain text and passes unchanged. A path is resolved against the tree the game is launched from (the scratch clone when `--tree` is used) to an absolute path before launch, and must not leave the tree (`..` or an absolute value: `PLAY REJECT scene input outside tree <KEY>`, exit 5). The missing-file line prints the value as written.
3. **Dry run.** The `launch:` line shows the resolved assignments (`OM_FIGHT=<absolute path> ...`) ahead of the Godot command, so a human sees what the scene gets.
4. **Patience.** `WINDOW_S` stays 60 and the writer's `PATIENCE_S` 30 is a test harness wait, not a product number.
