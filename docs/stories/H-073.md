# H-073: gate-gpu-preflight

"A gate that cannot get graphics memory says so, instead of reporting a failing test."

Flag harness; tool Workflow; no scene. Ready 2026-11-02 (the test writer's questions ruled by the Architect); Channel: lab; the builder starts 2026-11-02 and lands after the stack, H-068 first. DRAFT-gpu-need (3000 MiB) and DRAFT-gpu-wait (20 minutes) are Westley's drafts: he rules both numbers, and the code comment names them as his drafts. Finding by the Architect 2026-11-02, from the beta Dispatcher's H-069 gate reject (DEC-gate-gpu-memory-2026-11-02).

## Why

Evidence 2026-11-02: the machine's RTX 3060 has 12288 MiB. A local `ollama`/`llama-server` held 10232 MiB of it (`nvidia-smi` showed 11887 of 12288 MiB used). The gate plays launch `godot.real` under `xvfb` and use the real GPU; with three to four `godot.real` processes alive across the lab and beta gates the device ran out of memory. The beta gate for H-069 rejected the `lane_plays` stage on `tests/qa/desktop/plays/A/test_S_005_fog_of_sight.py::test_s_092_only_what_is_in_sight_is_drawn` with `index_array_create` (rendering_device.cpp:3421), `err != VK_SUCCESS`, `ERR_CANT_CREATE`, rc=134 on the second Godot launch, deterministic when run alone. The stage reads that as `red outside known-red list`, a code red, although no code is at fault. An environment fault reported as a failing test sends the story back to its builder for nothing (CLAUDE.md: a real finding is never reclassified as a skip; the converse holds, a missing resource is never a code finding).

Where the renderer is chosen (read 2026-11-02): `GodotGame.__init__` in `tests/qa/desktop/daemon_client.py` (line 195) sets `self.renderer = os.environ.get("OM_QA_RENDERER") or renderer or "opengl3"` and passes it as `--display-driver x11 --rendering-driver <renderer>` (line 226). Only `lane_plays_check` in `scripts/specfactory/merge_gate_support.py` (line 1339) sets `OM_QA_RENDERER=vulkan` in the pytest environment. `playthrough_check` sets nothing, so the playthrough stage runs the harness default (opengl3) unless the caller's environment carries the variable. The Vulkan device-memory failure above therefore belongs to `lane_plays`; whether the playthrough stage can run out of memory on opengl3 is for the builder to measure.

## Change (a builder reads the code and confirms or amends each part that the rulings below do not settle)

1. A new small file `scripts/specfactory/gpu_preflight.py`, a function and a CLI. It reads `nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader,nounits` and prints `GPU OK <free_mib>` or `GPU LOW <free_mib> need <need_mib>`. The need is DRAFT-gpu-need 3000 MiB (Westley's draft; the code comment names it as such). The boundary: LOW when free < need; free equal to the need is OK. The CLI exits 0 for OK and 3 for LOW. Exit 3 is the gate's existing harness-error status (the `merge_gate.sh` header: never counted as a regression); `GPU LOW` is its retryable case, which the clerk card names and tells from the other exit-3 cases (a compile error, a make timeout) by the GATE line. When `nvidia-smi` is absent it prints `GPU UNKNOWN` and exits 0: it never blocks a machine without an NVIDIA card.
2. The `playthrough` and `lane_plays` stages of `scripts/specfactory/merge_gate.sh` call it first. On `GPU LOW` they wait up to DRAFT-gpu-wait 20 minutes (Westley's draft, named as such in the code comment), polling every 30 s for memory to free (inside the script, not a chat), then stop with `GATE <stage> GPU-LOW` and exit 3. The wait and the poll are set by the environment overrides `MERGE_GATE_GPU_WAIT_S` (default 1200) and `MERGE_GATE_GPU_POLL_S` (default 30), so a hermetic test can set them to 1 and 0. This is a distinct verdict and NOT a reject of the story: the gate exits with the retryable status instead of running plays that cannot get memory.
3. A red whose log carries `ERR_CANT_CREATE`, `index_array_create` or `VK_ERROR_OUT_OF_DEVICE_MEMORY` is classified `GPU-MEMORY` and reported as retryable, never as `red outside known-red list`. The classification lives in `merge_gate_support.py`, in `playthrough_check` and `lane_plays_check`, and keeps their return shape: `(False, "GPU-MEMORY ...")`. The detail starts `GPU-MEMORY: <ids>`, the failing test ids as `red outside known-red list: <ids>` lists them today. GPU-MEMORY applies only when every red in the log is a GPU signature: a log that mixes a GPU signature with a real code red is NOT GPU-MEMORY, the stage still rejects with the code red listed. A stage that gets GPU-MEMORY exits 3, the same retryable status as `GPU-LOW`.
4. `docs/method/clerk.md` and `docs/method/gate.md` get one sentence each: a `GPU-LOW` or `GPU-MEMORY` result (gate exit 3) is retried after the graphics memory is freed and is never a known-red entry. The clerk.md sentence must contain neither `HEAD:main` nor the bare retired lock name (`tests/specfactory/test_gate_channels.py::test_t4e` bans any clerk.md line with `HEAD:main` that lacks `land_push.sh`, and any bare retired lock name once the channel locks are removed from the text).
5. Open question, not decided here: the two channels' xvfb plays are not serialised by this story. Allowing only one channel in `lane_plays` at a time would need a lock (a separate decision and story). The builder measures how many `godot.real` processes run at once across both gates and how much device memory each holds, and reports the numbers in the landing record.

Not in this story: stopping or limiting the local model server, any change to what the plays assert, and any change to the known-red lists.

## Tests

`tests/specfactory/test_gpu_preflight.py` (written by a different Sonnet; red on main; branch `origin/push/h073-tests`).

1. A stub `nvidia-smi` on PATH printing `11887,12288` (and `11887, 12288`, the real csv spacing) gives `GPU LOW 401 need 3000` and exit 3.
2. A stub printing `2000,12288` gives `GPU OK 10288` and exit 0.
3. With no `nvidia-smi` on PATH the CLI prints `GPU UNKNOWN` and exits 0.
4. A stubbed `lane_plays` log, and separately a stubbed `playthrough` log, carrying each of the three signatures is classified `GPU-MEMORY`, not `red outside known-red list`. Positive control: an ordinary assertion failure in the same stubbed log still is a `red outside known-red list` in both stages.

Ruled 2026-11-02 but not pinned by the writer's file (the builder honours each and names it in the landing record): the wait and poll loop with its two environment overrides, the `GATE <stage> GPU-LOW` line and exit 3 of the stage, the boundary free equal to need, the `GPU-MEMORY: <ids>` prefix (the file checks only that `GPU-MEMORY` is in the detail), the mixed log that keeps its code red, the exit 3 of a GPU-MEMORY stage, the two docs sentences.
