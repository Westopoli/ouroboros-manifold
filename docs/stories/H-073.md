# H-073: gate-gpu-preflight

"A gate that cannot get graphics memory says so, instead of reporting a failing test."

Flag harness; tool Workflow; no scene. Spec'd 2026-11-02 (NOT Ready); Channel: lab; becomes Ready after the stack landing. DRAFT-gpu-need and DRAFT-gpu-wait are drafts: Westley rules both numbers. Finding by the Architect 2026-11-02, from the beta Dispatcher's H-069 gate reject (DEC-gate-gpu-memory-2026-11-02).

## Why

Evidence 2026-11-02: the machine's RTX 3060 has 12288 MiB. A local `ollama`/`llama-server` held 10232 MiB of it (`nvidia-smi` showed 11887 of 12288 MiB used). The gate plays launch `godot.real` under `xvfb` and use the real GPU; with three to four `godot.real` processes alive across the lab and beta gates the device ran out of memory. The beta gate for H-069 rejected the `lane_plays` stage on `tests/qa/desktop/plays/A/test_S_005_fog_of_sight.py::test_s_092_only_what_is_in_sight_is_drawn` with `index_array_create` (rendering_device.cpp:3421), `err != VK_SUCCESS`, `ERR_CANT_CREATE`, rc=134 on the second Godot launch, deterministic when run alone. The stage reads that as `red outside known-red list`, a code red, although no code is at fault. An environment fault reported as a failing test sends the story back to its builder for nothing (CLAUDE.md: a real finding is never reclassified as a skip; the converse holds, a missing resource is never a code finding).

Where the renderer is chosen (read 2026-11-02): `GodotGame.__init__` in `tests/qa/desktop/daemon_client.py` (line 195) sets `self.renderer = os.environ.get("OM_QA_RENDERER") or renderer or "opengl3"` and passes it as `--display-driver x11 --rendering-driver <renderer>` (line 226). Only `lane_plays_check` in `scripts/specfactory/merge_gate_support.py` (line 1339) sets `OM_QA_RENDERER=vulkan` in the pytest environment. `playthrough_check` sets nothing, so the playthrough stage runs the harness default (opengl3) unless the caller's environment carries the variable. The Vulkan device-memory failure above therefore belongs to `lane_plays`; whether the playthrough stage can run out of memory on opengl3 is for the builder to measure.

## Change (the Architect's draft; a builder reads the code and confirms or amends each part)

1. A new small file `scripts/specfactory/gpu_preflight.py`, a function and a CLI. It reads `nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader,nounits` and prints `GPU OK <free_mib>` or `GPU LOW <free_mib> need <need_mib>`. The need is DRAFT-gpu-need 3000 MiB (Westley's number to rule). The CLI exits 0 for OK and 3 for LOW. When `nvidia-smi` is absent it prints `GPU UNKNOWN` and exits 0: it never blocks a machine without an NVIDIA card.
2. The `playthrough` and `lane_plays` stages of `scripts/specfactory/merge_gate.sh` call it first. On `GPU LOW` they wait up to DRAFT-gpu-wait 20 minutes, polling every 30 s for memory to free (inside the script, not a chat), then stop with `GATE <stage> GPU-LOW`. This is a distinct verdict and NOT a reject of the story: the gate exits with a retryable status that the clerk card names, instead of running plays that cannot get memory.
3. A red whose log carries `ERR_CANT_CREATE`, `index_array_create` or `VK_ERROR_OUT_OF_DEVICE_MEMORY` is classified `GPU-MEMORY` and reported as retryable, never as `red outside known-red list`. The builder says whether the classification lives in `merge_gate_support.py` (`playthrough_check` and `lane_plays_check` both build that message) or in the shell stage.
4. `docs/method/clerk.md` and `docs/method/gate.md` get one sentence each: a `GPU-LOW` or `GPU-MEMORY` result is retried after the graphics memory is freed and is never a known-red entry. The clerk.md sentence must contain neither `HEAD:main` nor the bare retired lock name (`tests/specfactory/test_gate_channels.py::test_t4e` bans any clerk.md line with `HEAD:main` that lacks `land_push.sh`, and any bare retired lock name once the channel locks are removed from the text).
5. Open question, not decided here: the two channels' xvfb plays are not serialised by this story. Allowing only one channel in `lane_plays` at a time would need a lock (a separate decision and story). The builder measures how many `godot.real` processes run at once across both gates and how much device memory each holds, and reports the numbers in the landing record.

Not in this story: stopping or limiting the local model server, any change to what the plays assert, and any change to the known-red lists.

## Tests

`tests/specfactory/test_gpu_preflight.py` (new; a different Sonnet writes it, red on main).

1. A stub `nvidia-smi` on PATH printing `11887,12288` gives `GPU LOW 401 need 3000` and exit 3.
2. A stub printing `2000,12288` gives `GPU OK 10288` and exit 0.
3. With no `nvidia-smi` on PATH the CLI prints `GPU UNKNOWN` and exits 0.
4. A stubbed `lane_plays` log carrying `ERR_CANT_CREATE` is classified `GPU-MEMORY`, not `red outside known-red list`. Positive control: an ordinary assertion failure in the same stubbed log still is a `red outside known-red list`.
