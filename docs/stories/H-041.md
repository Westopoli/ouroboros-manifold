## Contract change (lands first, documented here)

- `csrc/ouroboros_sim.h`: `int om_roster_set_collision_radius(om_world *w, int unit_type, double radius);` beside `om_roster_set_reach` (line 2008). Returns 0, or -1 for an unknown type or a radius outside DRAFT-radius-bounds 1 to 200. Recorded in `signatures.toml`.
- The collision site is the pair push in `csrc/tactical_move.c` (`om_move_collide_pair`), which reads `ms->radius`, the runtime value of the `OM_TP_UNIT_COLLISION_RADIUS` knob (`ouroboros_sim.h:1021`), not the compile-time `OM_UNIT_COLLISION_RADIUS` (the contract builder found this; the first read of the code named only the macro's sites). A pair pushes apart at r_a + r_b, a unit's radius being the knob times its type's radius over 15, so the knob keeps working as a multiplier and, with no radius set, the sum is 2 x the knob exactly as before. The collision pass's search reach, the grid cell and the grid margin use the roster's largest radius (the reach is the knob scaled by the largest over 15). The macro's other code use sites (`csrc/unit.c:2579`, `mission.c:2470,2743`, `enemy_macro.c:964,965`, `om_internal.h:537` OM_PRODSLOT_SPACING_WU) and the five comment lines that quote the spacing (`unit.c:2567`, `mission.c:2348,2436`, `enemy_macro.c:960`, `om_internal.h:535`) take the roster's largest radius, having no unit type in hand; `tactical_move.c:95,96` (grid cell and margin) the same, and `tactical_move.c:390` is the knob's own default, which stays 15. "Largest radius" counts the six built-in types (a type never set counts 15) plus any type whose radius is set; a custom registered type that was never set is not counted. That matters only when all six built-in types are set below 15 and a custom type was left at 15; for Westley's values (largest 30) it is exact.
- Determinism: the radius is read once at `om_roster_*` time, never from the file inside the tick.
- Save compatibility: `OM_SAVE_FORMAT_VERSION` is not bumped. The radius table is appended to a save only when a radius is set, so old saves load unchanged and a save made with none set is byte-identical to today's; a save made with radii set does not load on an older build. `docs/architecture.md`'s save paragraph says so in one sentence.
- When a type's radius is never set, its value stays `OM_UNIT_COLLISION_RADIUS` 15, so every existing trace, golden and lab fight is byte-identical (a test pins this).
- ABI: `OM_ABI_VERSION` goes 9 to 10 in the same landing. The header comment (`csrc/ouroboros_sim.h` line 28) says "Bump when signatures change", and E5 (7), E7 (8) and LAB-REV2-E0 (9) each bumped it when they added exported symbols; this contract adds one. ### Size rulings (Architect 2026-11-02, from the code read)

- (a) One source, one lookup. `scenes/tactical_c/unit_visuals.gd` line 12 `MAX_VISUAL_SCALE := 1.0` caps every unit at 1.0, so Westley's Bombard 1.44 and Bastion 2.00 could never draw at his size. `UnitVisuals` reads the era manifest's `visual_scale` (default 1.0) while `EraThemeResolver.get_unit_visual_scale` (default `EraConfig.UNIT_VISUAL_SCALE` 2.0) is called by nothing: two unrelated defaults. Ruling: the file wins and there is ONE lookup. The cap is removed (the file's own bounds apply), `UnitVisuals._vscale` goes through the single lookup, and neither the manifest `visual_scale` nor the era default decides unit size any more (the era default survives only as the lookup's missing-file fallback, see Tests).
- (b) Meaning. His `visual_scale` is the scale of the H-023 scene (`scenes/proto/unit_scale/`), where a unit's drawn radius is `visual_scale` x 15 wu, equal to the file's `radius`; so a unit's ground footprint radius in the game must equal the file's `radius` (4.05 Raider to 30.00 Bastion). The builder measures each model's native footprint radius, derives the factor per type, and REPORTS the table (type, native footprint, factor, resulting footprint) before editing. A model that cannot match (a mesh whose footprint is not roughly circular) is reported as a question for Westley, who owns looks. `drawn_scale` in the `qa_state` `unit_scale` key is the factor actually applied. It equals `visual_scale` only for a model whose native footprint radius is 15 wu, so the QA test does NOT assert `drawn_scale == visual_scale`: it asserts the drawn footprint radius in the 3D view (native footprint radius times `drawn_scale`) equals the file's `radius` within DRAFT-footprint-tol, 5 percent. The test writer proposed the 5 percent: the file has three decimals, and 5 percent of a footprint near 4 wu (the Raider's 4.05, about 0.2 wu) cannot be judged by eye while the sim collides at the exact radius. Westley owns it (thresholds batch row 10); the test runs with the draft meanwhile.
- (c) The 3D view (Architect 2026-11-02, the second code read). `scenes/ground3d/ground_units.gd` (the 3D ground view, the one the beta shows) draws every unit at a fixed `BODY_RADIUS_WU := 11.5` (the body polygon at line 36, the facing arrow at lines 17, 60 to 62 and 157, the slope-fit sample at line 116) and never reads `visual_scale`; `UnitVisuals._vscale` only scales the 2D bodies. Ruling: the 3D view is the consumer that matters. The body radius per role comes from the single lookup (the file's radius, so the drawn footprint equals the tuned radius; the shapes reach about 1.28 x their scale, per the comment at line 11, so the factor comes from the measured native footprint as in (b)); `BODY_RADIUS_WU` decides size no longer and may remain only as the missing-file fallback. `drawn_scale` in the `qa_state` `unit_scale` key reports what the scene that actually draws units applies (`ground_units` when the 3D view is up, `UnitVisuals` for the 2D view). The builder reports the per-model native footprint table before editing; looks are Westley's.
- (d) A further csrc use site. `csrc/om_internal.h:537` OM_PRODSLOT_SPACING_WU (2 x `OM_UNIT_COLLISION_RADIUS`, read by `om_mission_production_slot` at `csrc/mission.c:3140`) sets the production-slot spacing. It has no unit type in hand, so, like the other such sites, it uses the roster's largest radius. With it the nine code lines and five comment lines in the contract change are every use of `OM_UNIT_COLLISION_RADIUS` in `csrc` outside `om_constants.h`. The macro is a compile-time constant today: OM_PRODSLOT_RING_MAX (line 538) and a `_Static_assert` (line 539: half the capture radius, 150, must be a whole number of spacings) derive from it, and 150 is not a whole number of 2 x 30 spacings. The builder reports how the spacing and the ring bound follow the roster at the call; with no radius set they stay 30 and 5, so `tests/csim/test_VG_E_prodslot.py` and every existing trace are unchanged.

## Tests

- `tests/csim/test_collision_radius.py`: two roles with radii 15 and 30 push apart at the sum of their radii (ALG-68); unknown type and out-of-bounds radius return -1 (positive control); same seed and command stream give a byte-identical trace when every value is 15 or the function is never called; production-slot spacing equals two largest radii when radii are set, unchanged (30) when none is set. Save: a csim test (in this file, extended by the test writer; a builder never edits a test) that a save made with radii set restores the same radii on load even if `data/unit_scale.toml` has since changed, and that a save made with none set is byte-identical to today's.
- `tests/qa/test_unit_scale_readthrough.py` (headless). QA seam (Architect ruling 2026-11-02, the beta Dispatcher's question): there is NO radius getter in C; the contract adds only the setter, and a getter would widen the frozen header for a fact `tests/csim/test_collision_radius.py` already proves. `scenes/tactical_c/tactical_view.gd` `qa_state()` gains an additive key `unit_scale`: a dict keyed by role name (the test matches the names case-insensitively, the values file spells them Raider, Interceptor and so on), one entry per role `{radius, visual_scale, drawn_scale}`. `radius` is what `c_bridge` pushed to the roster at boot (15 on the missing-file fallback), `visual_scale` is `EraThemeResolver.get_unit_visual_scale(role)` after the file is applied, `drawn_scale` is the factor actually applied by the scene that draws the units (`ground_units` when the 3D view is up, `UnitVisuals._vscale[type]` for the 2D view), present only while the tactical view is up, null otherwise. The key exists for the QA harness only (qa_state keys are not a frozen contract, so no contract story). The file asserts: with Westley's file each role's `radius` and `visual_scale` equal the file's, and the drawn footprint radius in the 3D view (the model's native footprint radius times `drawn_scale`) equals the file's `radius` within DRAFT-footprint-tol, 5 percent (Westley's to rule, thresholds batch row 10). With the file missing: `radius` stays 15, `visual_scale` is 2.0 (`EraConfig.UNIT_VISUAL_SCALE`, the single lookup's fallback), exactly one warning line is printed on stderr, and the drawn footprint is not asserted (the 3D view keeps `BODY_RADIUS_WU` 11.5 in `scenes/ground3d/ground_units.gd` as the fallback).

## Known limits

The steering probe, the navmesh margin and the arrival tolerance stay on the global `OM_TP_UNIT_COLLISION_RADIUS`, so a Bastion pushes at 30 but steers and arrives as if it were 15.
