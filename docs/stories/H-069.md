# H-069: loading-screen-requests-once

"The beta's start does not shout at itself: asking for the same scene twice is not a replacement."

Flag client; tool Workflow; scene: the boot scene, the existing chain. Ready 2026-11-02; Channel: beta. Findings: beta Dispatcher B0 note (137 `SceneRouter: queued 'main_menu' replaced by 'main_menu'` warnings in 12 s) and the editor-debug log (`docs/northstar/plans/editor_debug/log.md`, still red). Rewritten 2026-11-02 around the beta Dispatcher's read of `autoload/scene_router.gd` (DEC-h069-router-rule-2026-11-02).

## Why

`scenes/loading_screen/loading_screen.gd:47` (`_process`) calls `SceneRouter.go_to(_target_scene)` every frame once `_skip_to_main` is set. In `autoload/scene_router.gd`, `go_to` with the router idle starts a transition and sets `_current_scene_name` (line 58). While a transition runs and nothing is queued, the request is stored in `_pending` (line 44) with no warning. While one request is already queued, a new request warns (line 43) and overwrites `_pending`: latest wins (`tests/test_scene_router_queue.gd`, lines 137 to 148). The code compares no names. `_finish_transition` (lines 67 to 72) pops `_pending` and calls `go_to` again, so a request for the scene being transitioned TO runs a second transition of that same scene (fade, free, rebuild) on every boot today. That double transition is the real bug; the warnings are its symptom (from the second frame on the loading screen replaces its own queued `main_menu` with itself).

The per-frame request is redundant since the pending queue (T12, 56a5d9c2, 2026-10-06): `go_to` never drops a request, so the privacy-flag race described in the comment at `scenes/loading_screen/loading_screen.gd:29` and in `tests/qa/desktop/daemon_client.py:233-245` ("dropped, no retry") is stale; the repeated calls only produce the warnings.

## Change (the Architect's ruling, 2026-11-02)

In the `_transitioning` branch of `SceneRouter.go_to`, a request that names the scene being transitioned TO and carries the same params is not queued and starts no second transition. The builder stores `_current_params` where `_current_scene_name` is set (line 58) and compares with Dictionary equality; a request for the same scene with DIFFERENT params is not swallowed (a `mission_briefing` for a different mission still gets its transition). The check holds for as long as the transition runs, fade-out included.

- If something is already in `_pending` (a different scene, or the same scene with other params), it is discarded: the running target is the latest request, so latest-wins holds, and the existing `queued '%s' replaced by '%s'` warning is printed for the discarded request.
- If nothing is queued, `go_to` returns silently.
- A request for a different scene (not the running target) keeps today's behaviour: it warns if something is queued and overwrites `_pending`. The idle path is unchanged.

The loading screen's per-frame call is NOT changed in this story (scope). Finding for a later hygiene pass: the comments at `loading_screen.gd:29` and `daemon_client.py:233-245` are stale (the latter is a fenced test file, so a clerk under `docs/method/rulebook.md`).

The builder runs the fenced race test S-C8-07 (privacy flag present at boot, `tests/qa/desktop/test_flow_spine.py`) as part of its gate and reports the result; if it shows the old race can reappear another way, the builder stops and reports.

## Tests (`tests/qa/test_scene_router_dup.py`, new; a different Sonnet writes it, red on main)

Model: `tests/test_scene_router_queue.gd` (a router subclass whose `_swap_scene` is overridden to log each swap and its params, stub scenes, real scene names as keys), run headless; the warnings are counted from the engine output. Swaps are counted, not `go_to` calls, and calls from the loading screen are not asserted.

1. Two or more same-scene, same-params requests while a transition runs produce exactly one transition of that scene (swap count == 1) and no warning.
2. Running A, queued B, then A requested again: the final scene is A, one warning for the discarded B, and no second swap of A.
3. The same scene with DIFFERENT params requested while it runs: a second transition with the new params still happens.
4. Control: a different scene requested while one is running and another is queued still warns and overwrites (latest wins).
5. Control: the idle path is unchanged (a `go_to` with nothing in flight transitions, and a later one transitions again).
