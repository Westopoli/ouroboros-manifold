# H-080: gate-queue

"A landing hands its candidate to the gate and comes back for the verdict; the gate works its own queue and a red main pauses it instead of failing everyone behind it."

Flag harness; tool Workflow; no scene; Channel: lab. Spec'd 2026-11-03 from the plan "the mail-and-station communication method" (Westley approved 2026-11-03; DEC-gate-queue-2026-11-03). After H-077 and H-079; the last of the five.

## Why

Clerks wait on `flock -w 14400` for the channel lock and run the gate themselves (519 lock commands and 1,690 gate commands in the week of 10-27). Of the real gate runs that week about 66 were rejected; 18 because main itself was red at the sweep (every candidate behind the red sweep was rejected one by one) and the rest largely because the candidate was behind a main that moved while it queued. This is the merge-queue problem; CI systems solve it with one queue owner that stacks candidates and pauses on a red main.

## Change

**`scripts/specfactory/gate_queue.py`** (daemon, `scripts/specfactory/systemd/om-gate-queue.service`, `Type=simple`, `Restart=on-failure`; one worker thread per channel in the registry of channels `lab`, `beta`; each worker holds `~/Projects/om-push/gate-<channel>.lock` with `flock` for as long as it runs, so a clerk mid-`flock` at the switch finishes first and the two never overlap).

- **Ticket**: the clerk writes `~/Projects/om-push/queue/<channel>/<id>.json` (`mktemp` then rename): `{"id": "<story id, or comma list for a stack>", "branch": "<origin ref>", "sha": "<candidate sha>", "worktree": "<path>", "requester": "<agent name for the info mail>", "tier": "<empty for the story's flag>", "ts": "<ISO>"}`. `gate_queue.py submit --channel <c> --id <id> --branch <ref> --sha <sha> --worktree <path> --requester <agent>` writes it and prints `QUEUE <channel> <id> position <n>`.
- **Order**: tickets by `ts`. The worker, per ticket: `git fetch`, merges `origin/main` into the candidate worktree (a conflict is a result `GATE merge REJECT conflict` and the ticket is done), runs `pre_gate.sh <worktree> origin/main <id>` then `merge_gate.sh <worktree> origin/main <id>` with `MERGE_GATE_QUEUE_S` set to the seconds the ticket waited, and writes `<id>.result` (`mktemp` then rename): the GATE lines verbatim plus `QUEUE verdict OK|REJECT <id> queue <s>s stage <s>s`.
- **Stacking**: while ticket j gates, ticket k (next in the same channel) is prepared on a worktree holding main plus j's candidate (`git merge` j's sha); if j passes, k's run counts; if j rejects, k is re-prepared without j before its gate. One prepared-ahead ticket per channel (DRAFT-queue-lookahead 1). Preparation worktrees come from `wt.py new q-<channel>-<n> --owner gate-queue` and end with `wt.py done`.
- **Pause**: before each run the worker reads the last `sweeps.md` row as `merge_gate.sh` does; a `REJECT` row with no `Fixes-sweep` exemption on the ticket's story writes `~/Projects/om-push/queue/<channel>/PAUSED` with `red-sweep <sha>` and waits (inotify on `sweeps.md`, else 30 s poll) until the row is green, then removes `PAUSED` and resumes; no ticket is rejected for the red row. A ticket whose story carries `Fixes-sweep: <that sha>` runs during the pause.
- **Wait**: `gate_queue.py wait --channel <c> --id <id> [--max <s>]` blocks on `<id>.result` (inotify, else 2 s poll), prints it, exits 0 on `QUEUE verdict OK`, 1 on REJECT, 3 on `--max`. The clerk runs it as a plain Bash (the clerk is a sub-agent, allowed to wait inside a script).
- **Mail**: on each result the worker runs `mail.py send --me gate-queue --to <requester> --class info --re <id> "gate <id> <OK|REJECT> <queue>s/<stage>s, result <path>"` (H-077; `gate-queue` is a registry table with `rules = false`, `senders = []`).
- **Status**: `gate_queue.py status` prints one line per channel `QUEUE <channel> <running id|idle> waiting <n> [PAUSED <why>]`; `status.sh` prints it.
- `gate_runs.csv` rows come from `merge_gate.sh` as today, with `queue_s` filled.

**Cards**: `clerk.md` step 4 becomes submit, then wait (no `flock`, no `merge_gate.sh` call by the clerk); `gate.md` "Per landing" paragraph describes the queue, the lookahead and the pause; README Locks row says the two channel locks are held by `om-gate-queue`; `method_check.py` `GATE_LOCKS` drops the retired `gate.lock`, and `~/Projects/om-push/lab-diag.lock` (orphan, nothing references it) is removed by the clerk that lands this story.

## Tests (`tests/specfactory/test_gate_queue.py` on the toy repo from `gate_toy_root.py`, `MERGE_GATE_TOY=1`; a different Sonnet writes them, red on main)

1. `submit` writes the ticket atomically and prints the position; `wait --max 1` on a missing result exits 3.
2. One worker loop (`gate_queue.py --once --channel lab`) runs a ticket through pre_gate and merge_gate on the toy repo and writes a result whose GATE lines equal the lines the same candidate produces through today's `flock` wrapper (positive control, byte-equal except timings).
3. Two tickets: the second's prepared tree contains the first's sha; when the first is rejected (a toy candidate that fails `base`), the second is re-prepared without it and passes.
4. A `REJECT` sweeps row writes `PAUSED red-sweep <sha>` and the ticket is not rejected; a green row written afterwards resumes it; a ticket whose story file has `Fixes-sweep: <sha>` runs during the pause.
5. `queue_s` in the `gate_runs.csv` row equals the ticket's wait within 2 s.
6. Each result sends one `info` mail to the requester (fixture registry, H-077's `mail.py`).
7. The worker holds `gate-lab.lock` while running: a `flock -n` from the test fails during a run and succeeds after.
8. `status` prints the running id, the waiting count and `PAUSED` when paused.
