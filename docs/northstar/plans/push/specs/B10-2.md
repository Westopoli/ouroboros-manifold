# spec: B10 increment 2 — traits, ability slot, Warden aura; migrate off the file-static registry

Piece B10, manager M2, increment 2 of 4 (`B10-1` landed S-081 + S-082, pushed as `push/B10-1`, not yet merged to `origin/main`). This increment: S-083 (stats/traits/ability contract, Warden passive aura) plus a **mandatory migration** M0 decided after reviewing B10-1's `leaf-01-Q1.md` finding.

## Migration (do this first — required, not optional)

M0's decision (F2c, already on `origin/main` and merged into this base): `struct om_world` (`csrc/om_internal.h`) now has `void *tactical_state`, `void (*tactical_state_free)(void *)`, and `uint64_t world_serial`. **From this increment on, no file-static state keyed by `om_world*` identity** — that was B10-1's workaround for an ABA hazard (freed test worlds reusing malloc addresses); this field eliminates it structurally.

Replace `csrc/unit.c`'s current `static struct { const om_world *owner; ...; int battle_ticked; } g_unit_registry` (and its `om_registry_bind`, `om_registry_start_new_battle_if_stale`, and every `battle_ticked` read/write) with a heap-allocated struct stored in `w->tactical_state`:

- Define the same fields (`units[OM_MAX_UNITS]`, `n_units`, `next_unit_id`, `custom_types[...]`, `n_custom_types`) in a struct with no `owner` or `battle_ticked` field — neither is needed anymore, since the state now lives and dies with the exact `om_world` instance that owns it.
- A helper (e.g. `static om_tac_state *om_tac(om_world *w)`) that: if `w->tactical_state == NULL`, `calloc`s the struct, sets `w->tactical_state` to it, sets `w->tactical_state_free` to a small `static void om_tac_state_free(void *p) { free(p); }`, sets `next_unit_id = 1`; else casts and returns the existing pointer. Every function that currently touches `g_unit_registry` calls this helper instead and uses the returned pointer.
- `om_tactical_reset(w)` still explicitly clears the struct's contents (memset the pointed-to struct, keep `next_unit_id = 1`) — that behavior is unchanged, it's just operating on `*om_tac(w)` instead of the static global.
- Delete the entire ABA-hazard comment block and the `battle_ticked` mechanism — it is fully superseded, not layered on top of.
- `const` note: `om_tac`'s signature needs a non-const `om_world *` (it writes `w->tactical_state`), so any currently-`const om_world *` parameter that calls it needs to drop `const` — check each declared signature in `csrc/ouroboros_sim.h` first; do not change a signature that's already non-const-`om_world*` without reason, and do not touch the header itself (it's already right — `om_unit_get_hp` takes `const om_world *w` and must stay read-only, so it should read via a read-only variant that returns NULL if `tactical_state` is unset rather than allocating).

Verify the migration didn't regress anything by re-running B10-1's two acceptance files (`test_E11_S081_...`, `test_E11_S082_...`) — they must stay green.

## Rules (verbatim from the bible, `docs/bible/epics/E-11-units-and-combat.md`, S-083 — Stats, traits, ability)

- R-083-01: a unit type's profile has the S-082 stats, zero to two traits, and exactly one ability.
- R-083-02: a trait modifies one stat or one multiplier by a fixed amount stated in the profile (Q-083-01 resolved: no trait exists in the launch roster's code today — every built-in unit type reports `trait_count == 0`; the mechanism (`om_unit_apply_trait_modifier`) must still work generically for any future trait/custom unit, exercised directly by the test below).
- R-083-03: a Warden's passive aura — any friendly unit within 300 wu takes 10% less damage and regains 0.075 HP/tick; **Q-084-01 resolved** (see the fenced test): multiple Wardens give *diminishing* damage reduction (first Warden 0.10, second 0.05 — i.e. each additional Warden in range adds half the previous one's reduction, or equivalently reduction = 1 − 0.9^n for n Wardens in range, both formulas agree at n=1,2; use whichever reads cleaner, the test only checks n=1 and n=2), while **healing stacks normally** (linearly, 0.075 × count of Wardens in range).

## Symbols this increment implements (in `csrc/unit.c`)

`om_unit_profile_trait_count`, `om_unit_profile_ability_count`, `om_unit_apply_trait_modifier`, `om_unit_set_hp`, `om_tactical_step`.

`om_tactical_step` already exists as a stub wired into `sim.c`'s tick loop (`OM_FEAT_TACTICAL`, per the freeze) — read its current body before changing it; it needs to run one tick of Warden-aura application (damage-reduction and regen bookkeeping) but must not duplicate or interfere with `om_tactical_run`/`om_tactical_run_until_eliminated`'s own per-tick combat loop from B10-1 (both are called in different test contexts — `om_tactical_step` is the single-tick orchestrator entry point sim.c's tick loop calls; the B10-1 combat loop functions call it once per tick internally, or replicate its aura pass — read the existing `om_tactical_run` body first and reuse, don't fork the logic).

`om_unit_apply_trait_modifier(w, unit_id, stat_field, delta)`: `stat_field == 0` must modify HP per the fenced test (`test_R_083_02`) — spawn a unit, apply modifier with `stat_field=0, delta=+20.0`, assert `om_unit_hp` increased by exactly 20.0. Small implementation choice: whether this also raises `max_hp` by the same delta (reads as a genuine stat buff) or only current HP — either satisfies the fenced test since the unit is freshly spawned at full HP; pick one, it's yours.

Warden-aura damage reduction must apply inside `om_unit_deal_damage` (already implemented in B10-1) wherever the target is within 300 wu of any friendly (same-faction) Warden — this means `om_unit_deal_damage` needs to query the registry for nearby same-faction Wardens when computing final damage. Regen (0.075 HP/tick per Warden in range, capped at `max_hp`) happens once per `om_tactical_step` call.
