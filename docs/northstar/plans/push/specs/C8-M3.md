## Reconnaissance already done (cite, don't re-derive)

- `autoload/scene_router.gd` (79 lines): `SCENES` dict has no `"galaxy"`,
  `"tactical_c"`, or chronicle entry. `go_to(scene_name, params)`: if
  `_transitioning` is true, **silently returns** (`if _transitioning:
  return`) — this is the S-C8-07 bug's second half. `_swap_scene` calls
  `new_scene.setup(params)` only `if new_scene.has_method("setup")` —
  most of the six destination scenes have no `setup()` on the route-in
  path this flow uses, so **no data reaches a scene through `go_to`'s
  params**; every destination scene must self-load its own data in its
  own `_ready()` instead (see "Self-loading pattern" below).
- `scenes/loading_screen/loading_screen.gd`: the actual root cause of
  S-C8-07. `_ready()` either sets `_skip_to_main = true` (if
  `SimBridge._ready_received` is already true) — handled by a
  self-healing `_process()` loop that calls `SceneRouter.go_to(_target_scene)`
  **every frame** until it succeeds, since `_skip_to_main` is never reset
  to false — OR connects `SimBridge.sim_ready` to `_on_sim_ready()`, which
  currently calls `SceneRouter.go_to(_target_scene)` **directly, once**.
  Since `sim_ready` is emitted by the sim exactly once ever (a real
  startup-complete event, not a Godot `CONNECT_ONE_SHOT` flag — the retry
  problem is the missing retry, not the signal itself), if that one call
  lands while `_transitioning` is still true (the privacy_modal →
  loading_screen fade tween hasn't finished yet), it's dropped forever
  and nothing calls `go_to` again. **The minimal, correct fix**: change
  `_on_sim_ready(_metadata) -> void: SceneRouter.go_to(_target_scene)` to
  `_on_sim_ready(_metadata) -> void: _skip_to_main = true` — this reuses
  the EXISTING self-healing retry loop the other branch already has,
  instead of adding new retry/queue machinery to `scene_router.gd`. One
  line. Verify against the actual fenced test (`test_s_c8_07...`), which
  is racy by nature — run it more than once if it passes on the first try
  before trusting the fix, and note in the report how many runs you
  checked.

## Self-loading pattern (the one real design decision this piece makes)

Since `SceneRouter._swap_scene` never passes data into a scene unless it
has a `setup()` method (and adding `setup()` calls everywhere would mean
also threading fixture data through every `go_to()` call site, a much
bigger change than this piece's scope), **every destination scene
self-loads its own placeholder/fixture data in `_ready()`, exactly once,
when reached with no other data already present** — mirroring the
pattern `mission_briefing.gd`'s `_ready()` already uses for its mock
backfill. Concretely:

- `galaxy_view.gd`'s `_ready()`: read `--seed` from
  `OS.get_cmdline_user_args()` (mirror `autoload/qa_daemon.gd`'s own
  `_arg_value(args, "--qa-port")` helper — same parsing shape, default
  `1` when absent), instantiate `res://autoload/c_bridge.gd` fresh,
  call `load_snapshot_live(seed, 60, [6])`; on success call
  `set_snapshot(bridge.snapshot())`; on failure (binary missing, pipe
  error) fall back to whatever `set_snapshot({})` /empty-state already
  degrades to (check `qa_state()`'s handling of empty `_regions` — should
  not crash regardless, this is existing behavior, don't change it).
- `mission_briefing.gd`'s `_ready()`: when reached with no real mission
  data (i.e. via this flow, not via a real mission-launch path elsewhere
  in the game — the existing mock-backfill branch already detects
  "nothing set yet" via `_data.is_empty()`; add the fixture load
  alongside/instead of the mock backfill on that same branch, or check
  `_frame_loaded` — whichever reads cleaner given the file's existing
  structure, your call, not a design decision with outside weight), read
  `tests/fixtures/mission_frame_seed11.json` and call own `load_frame()`
  with its content.
- `tactical_view.gd`: add `_ready()`, read
  `tests/fixtures/tactical_frame_seed11.json`, call own `load_frame()`.
- `debrief.gd`: add `_ready()` (none exists), call `_build_ui()` when
  reached fresh (mirror mission_briefing's `if _data.is_empty()` guard
  shape), and separately read `tests/fixtures/debrief_frame_seed11.json`
  and call own `load_frame()` so `_debrief()`'s frame-derived fallback
  (already built by piece C4) has real content to show.
- `chronicle_scroll_panel.gd`: add `_ready()` (or extend the existing
  one if `class extends PanelContainer` already has one — check), read
  `tests/transport/fixtures/snapshot_seed1_tick10.json` and call own
  `set_snapshot()`, then read `tests/fixtures/chronicle_frame_seed11.json`
  and call own `load_frame()`.

Reading a `tests/fixtures/*.json` file directly from production scene
code is an explicit, sanctioned exception for this piece only — the
piece spec's own "Fixture-vs-live notes" section says mission/tactical/
chronicle frames come from these exact files until B8/B9/B10 attach;
this is the same fixture-first convention already used throughout this
push, just reached from inside a scene's `_ready()` instead of from a
test file. Do not invent a separate non-test fixture directory — reuse
the same files the fenced unit tests for those scenes already use.

## Suggested leaf split (four legs, file-disjoint)

1. **Plumbing**: `autoload/scene_router.gd` (two/three new SCENES keys),
   `autoload/c_bridge.gd` (add `snapshot()`), `scenes/loading_screen/loading_screen.gd`
   (the one-line S-C8-07 fix).
2. **Galaxy leg**: `scenes/main_menu/main_menu.gd` (NewGame rename +
   retarget), `scenes/galaxy/galaxy_view.gd` + `.tscn` (self-load live
   snapshot in `_ready()`, add Mission button).
3. **Mission leg**: `scenes/mission_briefing/mission_briefing.gd` (Deploy
   rename + retarget + fixture self-load), `scenes/tactical_c/tactical_view.gd`
   + `.tscn` (add `_ready()` fixture self-load, add EndMission button).
4. **Debrief leg**: `scenes/debrief/debrief.gd` (Continue rename +
   retarget + add `_ready()` + fixture self-load),
   `scenes/world/chronicle_scroll_panel.gd` + `.tscn` (fixture self-load,
   add Return button).

Each leg is file-disjoint from the others. Leg 1 has no runtime
dependency on legs 2-4 to WRITE correctly (they just call
`SceneRouter.go_to("galaxy")`/`"tactical_c"`/`"chronicle"` as string
literals — those routes existing is a runtime concern, not a static one),
but the combined fenced test obviously needs leg 1's SCENES entries
present to pass, so merge/verify order matters even though write order
doesn't.
