## Framing (both directions, stdin/stdout)

4-byte big-endian length prefix, then a UTF-8 JSON object, no separators.
Read commands as length-prefixed frames from stdin; write every response
frame the same way to stdout. `stdout` must carry nothing but frames (no
stray `printf`s — the placeholder's single `printf("{...}\n")` line goes
away entirely; a bare newline-terminated line is not a valid frame and will
desync the reader).

## hello (first thing written, before reading any command)

```json
{"type":"hello","abi":2,"layout_ok":true,"seed":0,"n_regions":0,"features":[],"checksum_cadence":10}
```

`abi` = `om_abi_version()`. `layout_ok` = `om_abi_layout_check(sizeof(om_trace_row), sizeof(om_drift_row), sizeof(om_collision))` — three args, not one; the header (line ~106) is authoritative over the doc's shorthand "sizeof rows". `checksum_cadence` = `om_checksum_cadence()`. No world exists yet at this point (server hasn't seen `set_seed`) — `seed`/`n_regions`/`features` on this very first hello are reasonable placeholders (0 / 0 / empty array); nothing in the fenced test reads them, so pick the simplest correct-looking value and log it as an assumption, not a question — this is exactly the kind of internal choice the brief template's "small implementation choices are yours" carve-out covers, not a design decision with external weight.

## Documented deviation: `set_seed` does NOT auto-emit a snapshot

`docs/architecture.md`'s snapshot section says snapshot is sent "on request
and after `set_seed`/`load`". The fenced test's own script contradicts this
literally: it sends `set_seed` first, then `step n:10`, and asserts
`frames[1:11]` (the ten frames immediately after `hello`) are **all**
`"type":"delta"` — if `set_seed` emitted a snapshot frame, frame index 1
would be a snapshot, not a delta, and the assertion would fail. Per this
repo's rule that tests are the spec, build `set_seed` to emit **no frame at
all on success** (silent reconfiguration: create/replace the world with
`om_world_new(n_regions, seed)`, then `om_world_set_feature` for each id in
the `features` array, leaving every other feature off, then call
`om_world_generate(w)` — M0's set_seed contract, `docs/architecture.md`
"C transport v1"). The one exception: if `om_world_generated(w)` is 0 after
that call, answer `{"type":"error","name":"set_seed","reason":"generation
failed"}` instead of staying silent. `load` keeps the documented post-load
snapshot (nothing in the fenced test exercises `load`, so no contradiction
there — implement it per the doc).

## snapshot (on explicit `"cmd":"snapshot"`, and after `load`)

```json
{"type":"snapshot","tick":10,"checksum":1234567890,
 "regions":[{"i":0,"owner":-1,"tier":1,"military":12.5,"economy":30.0,"tension":8.0,"population":20.0,"stability":61.2,"capacity":44.0}],
 "factions":[{"id":0,"archetype":2,"budget":100.0,"tech":1.5,"stance":[3,1,2]}],
 "edges":[{"a":0,"b":1,"t":2}],
 "telegraphs":[{"attacker":0,"target":7,"commit":40.0,"declared_tick":8}]}
```

Build region rows from `om_region_field` (`OM_F_MILITARY/ECONOMY/TENSION/POPULATION`),
`om_region_composite` (`OM_C_STABILITY/CAPACITY`), `om_region_tier`,
`om_region_owner`, over `0..om_region_count(w)`. `checksum` =
`om_world_get_state_checksum(w)`; `tick` = the world's current tick (`om_world_step`'s
return value is the authoritative tick counter — track it, or add a getter
call if the header exposes one; check for an `om_world_tick`-shaped accessor
before assuming you must track it yourself).

Factions: `0..om_faction_count(w)`, `om_faction_archetype`, `om_faction_budget`,
`om_faction_tech`; `stance[k]` = `om_faction_stance(id, k)` for every other
active faction k (skip k == id) in ascending id order.

Edges: no direct "edge at index N" iterator exists. Build the full
undirected list by walking `om_region_neighbors(w, i, buf, max)` for each
region `i`, keeping only neighbor `j > i` (undirected, `a < b` per doc), and
reading the type with `om_region_edge(w, i, j, &type)`.

Telegraphs: `om_pending_telegraphs(w, out, max)` — `om_telegraph.attacker`,
`.target_idx`→`target`, `.commit`, `.declared_tick`.

## delta (one frame per tick advanced, i.e. every `om_world_step()` call)

```json
{"type":"delta","tick":11,"checksum":0,
 "regions":[{"i":3,"owner":0,"military":11.0,"economy":30.4,"tension":7.5,"population":20.1,"stability":62.0,"capacity":44.2}],
 "events":[...],"attacks":[...],"collisions":[...],"revolts":[...],"factions":[...]}
```

Only regions whose six numbers or owner changed since the previous tick
appear — track a per-region snapshot of the six fields + owner after every
step and diff. `checksum` = `om_world_get_state_checksum(w)` when
`tick % om_checksum_cadence() == 0`, else `0`.

Read the tick-log readers for the step just taken (each returns count-only
records for the LAST `om_world_step()` call, so call them once per step,
immediately after it, before the next step overwrites them):
`om_tick_events` → `events` (fields: `tick, region_idx→region, template_id→template,
chain_tag→chain, source, delta[OM_F_COUNT]→delta, creates_faction`; `draw`
and `n_spawned` are not in the doc's shape — leave them out, or include if
trivial, your call, log which you picked).
`om_tick_attacks` → `attacks` (`attacker, target_idx→target, d_military,
d_economy, d_tension, collision`). Doc names a `"band"` field that has no
matching member in `om_attack_result` — the header has `mode` (telegraph/surprise)
and `outcome` (breakthrough/contested/repelled) instead; pick the one that
reads as "band" (outcome is the closer semantic match — a breakthrough/
contested/repelled band) and log it as an assumption citing both candidates.
`conquest` = the struct's own `conquest` field.
`om_tick_collisions` → `collisions` (`target_idx→target`, `faction[0..n_colliders)→factions`,
`winner`, `margin`, `refund`).
`om_tick_admin_rolls` → `revolts` (`region_idx→region, faction_id→faction, draw→roll`) —
filter to `triggered == 1` only (the doc's example is a fired revolt, not
every chance roll); log this filter choice as an assumption.
`factions` in a delta: doc shows only `{id, budget, tech}` (a thinner row
than the snapshot's) — include only factions whose budget or tech changed
this tick, same diff-tracking approach as regions.

## command (read from stdin, one JSON object per frame)

```
{"type":"cmd","name":"step","n":1}
{"type":"cmd","name":"run_to","tick":500}
{"type":"cmd","name":"snapshot"}
{"type":"cmd","name":"set_seed","seed":7,"n_regions":60,"features":[1,2,3,6]}
{"type":"cmd","name":"set_feature","feature":4,"on":true}
{"type":"cmd","name":"inject","bug":6}
{"type":"cmd","name":"save","path":"saves/slot1.omsave"}
{"type":"cmd","name":"load","path":"saves/slot1.omsave"}
{"type":"cmd","name":"quit"}
```

`step`/`run_to` both stream one delta frame per tick advanced (see the
fenced test: `step` with `n:10` must produce exactly 10 delta frames, so
implement `step` the same way as `run_to` — call `om_world_step` in a loop,
emit a delta after each call). Answer every command except `step`/`run_to`/`set_seed`
with `{"type":"ack","name":"...","tick":N}` on success or `{"type":"error","name":"...","reason":"..."}`
on failure; `step`/`run_to` end their delta stream with one trailing `ack`
(consistent with the doc's "run_to streams deltas then one ack" — extend the
same rule to `step`, and note `set_seed` sends nothing at all per the
deviation above, not even an ack — the fenced test's frame-count math
requires it). `inject` only exists in the debug build (`#ifdef
OM_DEBUG_INJECT`, `om_debug_inject`); if this build isn't the debug variant,
`inject` always answers `error`. `save`/`load` use `om_save_state_size`/`_write`
(write path) and whatever the matching read-back symbols are (grep the
header for `om_save_state_read` or equivalent near line 1419-1420) — `load`
replies with the post-load `snapshot`, per doc. `quit` flushes stdout and
exits 0.
