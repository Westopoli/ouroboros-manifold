## Architecture decision (manager-decided, not the leaf's call)

`om_world`/`om_internal.h` has no unit storage today, and both files are parent-owned — this leaf cannot add fields to either. All B10 unit/tactical state is **private to `csrc/unit.c`**: a single static, file-local registry (a fixed-capacity array of unit rows, capacity a local `#define` in `unit.c` such as `OM_MAX_UNITS 4096` — array-size defines are lint-exempt per decision 5), bound to one "current" `om_world*` at a time. `om_tactical_reset(om_world *w)` rebinds the registry's owner to `w` and clears every row; every spawn/query/command function must defensively check `registry.owner == w` and behave as if freshly reset (empty) if not — this is the safety net against `world_factory`'s per-test `om_world_free`/malloc address reuse across tests, since no parent file can be touched to hook a free-time callback. Do not propose a header change for this; it is not needed and the plan's `NEEDS-HEADER.md` escalation path is for cases that genuinely require one.

## Rules (verbatim from the bible, `docs/bible/epics/E-11-units-and-combat.md`, via the regenerated cards at `docs/northstar/proving_ground/evidence/card_regen/E-11/`)

**S-081 — Three categories, a soft triangle**
- R-081-01: attacker category A vs target category B, damage = base damage × M[A][B]. M already emitted as constants in `csrc/om_constants.h`: `OM_CATEGORY_MULTIPLIER_{STRIKE,LINE,SIEGE}_{STRIKE,LINE,SIEGE}` (9 defines, lines 369-377). Use them, do not re-literal the matrix. Note Siege→Strike is 0.20 (Q-081-01 resolved: code value, not the bible's stale 0.75 — the constant is already correct).
- R-081-02: equal-power Line vs Strike in a straight fight → Line wins with ≥30% HP remaining; same pattern for Siege vs Line and Strike vs Siege from the flank.
- R-081-03: a Bastion attacked by 4 Raiders from the flank survives ≥20s (the Siege exception to Strike-beats-Siege).
- R-081-04: at a 1.5× power advantage, time-to-kill is 30-40% shorter than at 1.0×.

**S-082 — The six**
- R-082-01: the launch roster is exactly the table in `tests/csim/test_E11_S082_the_six.py`'s `ROSTER_TABLE` dict (lines ~27-100 — read it directly, it is the fenced source of truth, do not transcribe from this spec) — category, role, hp, damage, interval, range, speed, sensor, layer_transition, aoe per unit type (`OMUnitType`: RAIDER=0, INTERCEPTOR=1, VANGUARD=2, WARDEN=3, BOMBARD=4, BASTION=5; `OMCategory`: STRIKE=0, LINE=1, SIEGE=2, both classes defined identically in every E-11 test file).
- R-082-02: every Strike unit faster than every Line unit, every Line unit faster than every Siege unit (already true by the roster table's own speed column — this rule is a contract check on the table, not separate logic).
- R-082-03: Bastion has the most HP by at least 2× the next; Raider has the least (also a contract check on the table).
- R-082-04: both Strike units (Raider, Interceptor) see farther (sensor_radius) than both Siege units (Bombard, Bastion).
- R-082-05: only Bombard has an area attack (aoe > 0).
- R-082-06: `om_roster_register_custom_unit` lets an expansion pack add a unit type declaring category/role/stats/one ability with no engine code change — implement it as a real registration path (assigns a free `unit_type` id, stores the same per-type profile fields the roster table uses), not a stub.

## Determinism (verbatim)

Same seed, same command stream, byte-identical trace. No fast-math, no platform transcendental calls without a deterministic implementation, no hash-order or wall-clock input to the sim. Combat resolution order across units in one tick must be deterministic (iterate the registry in a fixed, stable order — spawn order / unit_id order, never hash-map iteration order).
