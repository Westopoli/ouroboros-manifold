Piece id `C8` in `pieces.toml`.

## Purpose

Today nothing wires main menu -> galaxy -> mission -> tactical -> debrief ->
chronicle -> galaxy into one loop. `scene_router.gd`'s `SCENES` dict has no
`"galaxy"` key at all. Clicking NEW GAME goes `new_game.tscn` -> (BEGIN) ->
`onboarding`, never `galaxy_view.tscn`. `mission_briefing.gd` still routes
Deploy to `"tactical"` (old `scenes/tactical/tactical.tscn`), not
`scenes/tactical_c/tactical_view.tscn`. `debrief.gd` routes Continue to
`"time_jump"` -> `main_menu`, never a chronicle scene. C8 rewires all of it
into the six-step loop below. Fenced acceptance test already red for exactly
this reason: `tests/qa/desktop/test_flow_spine.py`.

## The seven steps (S-C8-01..07, piece-local ids)

1. Boot -> main menu. Real boot chain is
   `privacy_modal.tscn` -> `loading_screen.tscn` -> `main_menu.tscn`, not a
   rule under test, just plumbing the test drives through.
2. Click `NewGame` -> `res://scenes/galaxy/galaxy_view.tscn`.
3. Click `Mission` (new, on galaxy view) -> `res://scenes/mission_briefing/mission_briefing.tscn`.
4. Click `Deploy` -> `res://scenes/tactical_c/tactical_view.tscn`.
5. Click `EndMission` -> `res://scenes/debrief/debrief.tscn`, then click
   `Continue` -> chronicle. No `"world"` scene exists in `SCENES` today; test
   accepts either exact scene `res://scenes/world/chronicle_scroll_panel.tscn`
   OR any scene whose tree has a control path containing `ChronicleScrollPanel`
   (root node name of that tscn, confirmed).
6. Click `Return` -> back to `res://scenes/galaxy/galaxy_view.tscn`; daemon
   still answers `state` after; kill Godot.
7. Boot reaches the main menu whether or not the privacy flag exists.
   `SceneRouter` must not drop a `go_to` issued while transitioning — launch
   with `user://privacy_accepted` already present (own game instance,
   `reset_privacy_flag=False`) and `state.scene` must still reach
   `res://scenes/main_menu/main_menu.tscn` within 15s. This is a rule, not
   boot plumbing like step 1 — it is the real bug in Findings item 1 below,
   promoted to a fenced test because it's a real game defect, not a test
   quirk. Racy by nature of the bug (a timing race, not a hard hang): fails
   most runs as of this writing, passes when the sim happens to become
   ready outside the transition window.

## Findings from writing this test (not C8's job to fix, flagging for the record)

1. **Real, reproducible boot race — now a fenced rule (S-C8-07), C8 must
   fix it.** Once `user://privacy_accepted` exists (i.e. every launch after
   the very first ever on a machine — `config/use_custom_user_dir=true` +
   `custom_user_dir_name="data"` in `project.godot` makes this an OS-level
   persisted file, not scratch-cwd scoped), the game frequently never
   leaves `loading_screen.tscn` — first confirmed with a 90s wait (sim
   genuinely reaches `sim ready` in under a second per its own log line, so
   this is not a slow sim); a later 5-run sample of S-C8-07 alone hung past
   its 15s budget on 2/5 runs and reached the main menu in under 2s on the
   other 3/5, i.e. a real timing race, not a hard deterministic hang.
   Hypothesis: `SimBridge.sim_ready` fires while `SceneRouter._transitioning`
   is still true from the privacy_modal -> loading_screen fade
   (privacy_modal's flag-present path calls `_route_to_loading()` via
   `call_deferred`, reaching `SceneRouter.go_to()` sooner after boot than
   the manual Accept-click path does, so the sim has less lead time and the
   race lands more often); `go_to()` silently drops the request
   (`if _transitioning: return`, no retry), and the one-shot `sim_ready`
   signal is already consumed, so nothing ever calls `go_to("main_menu")`
   again. The fenced test's `game` fixture (`daemon_client.py`'s
   `GodotGame.start()`) deletes the flag before every launch so S-C8-01..06
   stay deterministic regardless of this bug; S-C8-07 does the opposite on
   purpose (`reset_privacy_flag=False`, writes the flag itself via
   `write_privacy_flag()`) specifically to catch it. Fix belongs in
   `scenes/loading_screen/loading_screen.gd` / `autoload/scene_router.gd` —
   either `go_to()` queues/retries a dropped request instead of silently
   swallowing it, or `sim_ready` is buffered until the transition clears.
2. **`--qa-port` mode's `tree` had no rect data.** `qa_daemon.gd`'s own
   `_collect_tree` only returned `path`/`class`/`text`; `qa_driver.gd`'s
   `_do_click_node` (the only click-by-name path) dereferences `_root`,
   which is only ever set in `--qa-script` mode — null in `--qa-port` mode,
   so `click_node` crashes there. Added `rect_px` to `qa_daemon.gd`'s
   `_collect_tree` (mirrors `qa_driver.gd`'s already-proven computation) so
   this test can click by rect centre instead; did not touch
   `_do_click_node`/`_root`. C7 is attached (`autoload/qa_daemon.gd` is its
   footprint) — this is a small, disclosed M0 addition on top, not part of
   any piece's diff.
3. **`pieces.py`'s `ROOTS` tuple** did not include `tests/qa/desktop` (only
   `tests/qa/t1`), so this acceptance id would only ever WARN
   ("not under a known pytest root"), never really collect-checked. Added
   `"tests/qa/desktop"` to `ROOTS` in `scripts/specfactory/pieces.py`.
