# spec: B10 increment 3 — one ability each (S-086)

Piece B10, manager M2, increment 3 of 4 (`B10-1` S-081/S-082 and `B10-2` S-083 + `tactical_state` migration both pushed, not yet merged to `origin/main`; `B10-2`'s one red assertion was a test defect, already fixed by M0 on `origin/main` — pulled into this base). This increment: S-086, the largest single S-0xx story in E-11 — six unique per-unit abilities, manual activation, enemy auto-activation, telegraphs, zones, and the ability-event feed for the renderer.

## Rules (verbatim from the bible, `docs/bible/epics/E-11-units-and-combat.md`, S-086 — One ability each, via the regenerated cards at `docs/northstar/proving_ground/evidence/card_regen/E-11/275a{1,2,3}-*.md`)

- R-086-01: Raider/Surge — activated: for 60 ticks (3s) speed ×2.5, damage ×2.0; then cooldown 1,500 ticks (75s).
- R-086-02: Interceptor/Intercept — **never manually activated** (the player never activates it — every `om_command_activate_ability` call targeting an Interceptor is rejected, unconditionally). Auto-triggers when an enemy Strike unit is within 350 wu on its layer: speed ×1.8, damage ×1.5 for the first engagement; then cooldown 600 ticks (30s).
- R-086-03: Vanguard/Brace — activated: immobile at once (speed 0), no bonus for 40 ticks (2s windup), then 50% less damage and 1.3× output while braced; activating again **cancels** the current brace with the same 40-tick windup (i.e. re-activating while braced ends the brace and restarts the windup-then-brace cycle, not a second stacked brace); cooldown 700 ticks (35s), starts at activation (not at brace-end).
- R-086-04: Warden/Rally — activated: every friendly unit within 400 wu regains 112 HP at once, capped at max HP; cooldown 1,500 ticks (75s).
- R-086-05: Bombard/Barrage — activated with a target position: after a 30-tick (1.5s) telegraph visible to both sides, every enemy within 100 wu of the position on the Bombard's layer takes base damage ×3.0 (subject to the category multiplier per S-081, then the AoE cap of 4×(base×3.0) applied to the **total** damage dealt across all targets in the blast, not per-target); cooldown 1,800 ticks (90s).
- R-086-06: Bastion/Fortify — activated: for 400 ticks (20s) every friendly unit within 350 wu of the Bastion takes 20% less damage; the zone moves with the Bastion (i.e. re-evaluated against the Bastion's current position every tick, not a fixed point) at the Bastion's speed ×0.4 while fortified; the zone is visible to the enemy; cooldown 1,400 ticks (70s).
- R-086-07: an ability on cooldown, when activation is attempted, is rejected and nothing changes.
- R-086-08: an "enemy" unit (any unit, regardless of faction — the rule and its fenced test exercise faction-1 units, but the mechanism is not faction-gated; see the Design note below) auto-activates its ability when ready and its threshold condition holds: an enemy in range for Surge/Brace/Barrage, a damaged friendly in radius for Rally, two or more friendlies in radius for Fortify. No other enemy timing logic exists — this auto-check is the only AI ability logic S-086 requires.
- R-086-09: every ability activation (manual or auto) emits an explicit `om_ability_event` (tick, unit, ability, target, duration, radius) for the renderer.

## Design note: auto-trigger vs. manual activation are two independent paths

`om_command_activate_ability` is the **manual** path: it checks only "is this ability off cooldown and not currently active" (plus Brace's cancel-and-restart case) — it does **not** check any threshold condition, and it always rejects an Interceptor (R-086-02). Read `tests/csim/test_E11_S086_one_ability_each.py::test_R_086_01` closely: a lone Raider with no enemy anywhere in the world is manually activated successfully — proof the manual path has no threshold gate.

The **auto-trigger** check runs every `om_tactical_step` (or wherever your combat tick already iterates every unit — reuse it, don't add a second full-registry scan if one already exists) over every unit whose ability is off cooldown and not active: Intercept always uses this path (never the manual one); the other five abilities are eligible here too whenever their threshold holds, regardless of which faction owns the unit — this is what makes `test_R_086_02` (an Interceptor with no faction specified beyond the default) and `test_R_086_08` (explicitly faction-1 units) both work through the same mechanism. The "enemy in range" threshold for Surge/Brace/Barrage is not pinned by any fenced test to an exact radius beyond being consistent with each unit's own `attack_range` (`test_R_086_08`'s Raider-vs-Vanguard case is 150 wu apart against a 200 wu Raider attack range) — using each ability-owner's own `om_unit_profile_attack_range` as that threshold is a reasonable, test-consistent choice; it's yours to confirm.

## Symbols this increment implements (in `csrc/unit.c`)

`om_command_activate_ability`, `om_unit_output_multiplier`, `om_unit_ability_cooldown`, `om_unit_ability_active`, `om_tactical_run_until_engagement_ends`, `om_unit_damage_reduction`, `om_tactical_telegraph_active`, `om_tactical_zone_visible_to_enemy`, `om_unit_set_ability_cooldown`, `om_tick_read_ability_events`, `om_tactical_tick`, `om_unit_effective_speed`.

`om_tactical_tick` and `om_unit_effective_speed` are declared in the header block but not yet meaningfully implemented by B10-1/B10-2 (check current stub bodies first) — `om_unit_effective_speed` needs to reflect Surge's ×2.5, Brace's 0-during-brace, and Fortify's ×0.4-on-the-Bastion-itself modifiers on top of the unit's base `om_unit_profile_speed`; `om_tactical_tick` is read by `test_R_086_09` (`evt.tick == lib.om_tactical_tick(w)`) so it must return the current tick counter the combat loop is already advancing internally — expose it, don't reimplement tick counting.

`om_ability_event` (already declared in `csrc/ouroboros_sim.h`) has fields `tick, unit_id, ability_id, target_x, target_y, duration, telegraph_ticks, cue_id, radius` — `om_tick_read_ability_events` returns the events emitted since the last read (per-tick buffer, drained on read — `test_R_086_09` reads immediately after one `om_tactical_step` and expects the Surge event with `duration == 60`). Ability-id-to-unit-type mapping is 1:1 by declared order: Raider→Surge(0), Interceptor→Intercept(1), Vanguard→Brace(2), Warden→Rally(3), Bombard→Barrage(4), Bastion→Fortify(5) (matches `OMAbility` in the test file exactly, same order as `OMUnitType`).

## Determinism / scale note

Same as prior increments: fixed iteration order, no wall-clock. The per-tick ability-event buffer must not grow unbounded across ticks it isn't read — clear or bound it per your own judgment (small implementation choice), it just needs to hold at least one tick's worth of events reliably for the fenced test.
