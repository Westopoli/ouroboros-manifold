only). `attach/T1` landed — `pipe/ouroboros_pipe` now builds and exists.
This increment rebinds `c_bridge.gd` from file-only to live-pipe-first,

## Source of truth

- `docs/architecture.md` "C transport v1" — wire protocol (4-byte BE length
  prefix + JSON, both directions; `hello` first; `set_seed` is **silent**,
  no ack, no snapshot — confirmed by T1's own fenced test and now landed
  behavior; `snapshot` on request; `step n` streams n delta frames then one
  ack; `quit` exits).
- `autoload/sim_bridge.gd` (read in full, mirror its shape, do not edit
  it) — the existing pattern for spawning a subprocess and reading
  length-framed JSON over a pipe (`_spawn_sim`, `_read_framed`,
  `OS.execute_with_pipe`). **Load-bearing warning already in that file's
  header comment**: `execute_with_pipe` returns a single bidirectional
  `stdio` `FileAccess`, and *writing to it permanently breaks reading*
  (`ERR_FILE_CANT_READ`) in Godot 4.6 — that is why `sim_bridge.gd` never
  writes to `stdio` at all and instead polls a separate temp file for
  outbound commands. **`om_pipe.c` has no temp-file channel — it reads
  commands framed on stdin only** (T1 retired the temp-file channel by
  design), so `c_bridge.gd` cannot reuse `sim_bridge.gd`'s read-only
  pattern verbatim; it must find a way to actually write to the process.
  This is a real, unresolved technical question — do not guess a fix
  without checking: build a small throwaway probe (not committed, deleted
  before finishing) that spawns `pipe/ouroboros_pipe`, writes ONE complete
  framed command script in a single write call, and then only reads —
  never writing again afterward — and confirms whether reads still work
  after that one write. If they do, this is your implementation shape. If
  writing breaks reading even for a single one-shot write, escalate to the
  parent with what you tried and what broke — do not silently fall back to
  fixture-only without reporting, since that would defeat this increment's
  purpose.
- `tests/test_c_bridge.gd`, `tests/test_galaxy_view.gd` — must both stay
  green exactly as they are (18/44 checks respectively) — this increment
  is invisible to both fenced tests, which only exercise the file-fixture
  path (they never delete/hide `pipe/ouroboros_pipe`, so if your rebind
  breaks the fixture fallback, both tests still stay green regardless —
  they are not a signal that the pipe path itself works; verify the pipe
  path separately, manually, per the acceptance section below).
- `Makefile`'s `pipe/ouroboros_pipe` target (do not edit) — the binary
  path from the repo root, already built as part of T1.

## What to build

`load_snapshot_file(path: String) -> bool` stays as the fixture-file path,
unchanged (still used as the fallback and by the fenced tests). Add a new
method, something like `load_snapshot_live(seed: int, n_regions: int,
features: Array) -> bool` (exact name your call, not tested), that:

1. Spawns `pipe/ouroboros_pipe` (path relative to repo root — resolve via
   `ProjectSettings.globalize_path("res://pipe/ouroboros_pipe")` or
   equivalent; cwd should not matter since the binary is self-contained
   and static-links nothing project-relative, but confirm), the same
   `OS.execute_with_pipe` call shape `sim_bridge.gd` uses.
2. Writes the framed command script: `set_seed` (seed, n_regions,
   features), `snapshot`, `quit` — three commands, one write.
3. Reads frames until the process exits or a `snapshot` frame arrives;
   stores the snapshot the same way `load_snapshot_file` does, so
   `regions()`/`owner_of()`/`checksum()`/`edges()` all work identically
   against either source.
4. On any failure (binary missing, spawn failure, malformed response),
   returns `false` and leaves whatever was previously loaded (via
   `load_snapshot_file`) untouched — never crashes.

Whoever wires this into `galaxy_view.gd`'s `set_snapshot` call path is a
later step, not this increment — this increment only makes `c_bridge.gd`
capable of the live path; report whether you also wired it in or left that
for a follow-up (your call, log it).
