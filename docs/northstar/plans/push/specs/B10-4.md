Piece B10, manager M2, increment 4 of 4 — the last one (`B10-1` S-081/S-082, `B10-2` S-083, `B10-3` S-086 all pushed, not yet merged to `origin/main`). This increment: S-088, the render-facing read surface. Small in scope compared to B10-3, but it also **extends** B10-3's ability-event emission code, not just adds new isolated functions.

## Rules (verbatim from the bible, `docs/bible/epics/E-11-units-and-combat.md`, S-088 — Reading units on screen, via the regenerated card at `docs/northstar/proving_ground/evidence/card_regen/E-11/277a-*.md`)

- R-088-01: a Raider or Interceptor, when drawn, appears as 3 to 5 small craft in formation sharing one HP bar and one position — the sim still tracks exactly one entity (one unit id, one HP, one position).
- R-088-02: an ability event, received by the renderer, plays a cue at that tick for the event's duration — Barrage shows its telegraph ring at the target for 1.5s before impact, Fortify shows its zone, Brace shows a planted state.
- R-088-03: in a T2 screenshot of a mixed force, category is distinguishable by silhouette size: Strike smallest, Siege largest.

## Symbols this increment implements (in `csrc/unit.c`)

`om_unit_position_y` (companion to the already-implemented `om_unit_position_x` — same registry lookup, just the y field), `om_unit_render_craft_count`, `om_cue_lookup`, `om_unit_render_silhouette_size`.

Per the fenced test (`tests/csim/test_E11_S088_reading_units_on_screen.py`, read it in full — it is short and exact): `om_unit_render_craft_count(w, unit_type)` returns 3-5 for Raider and Interceptor (Strike squad display); a sensible default for the other four types (not asserted by any fenced test — a single craft, i.e. 1, is the natural reading of "the sim tracks one entity" applied to non-squad types, but it's your call). `om_cue_lookup(const char *name)` is a small name→id registry — the fenced test looks up `b"cue_barrage_telegraph"` and compares it against whatever `cue_id` your Barrage ability event already carries, so the id returned by a name must be internally consistent with whatever id you stamp onto that event (see the extension below — same source of truth for both). `om_unit_render_silhouette_size(w, unit_type)` must produce values where every Strike unit's value is less than every Line unit's, which is less than every Siege unit's — keyed primarily on category is the simplest way to guarantee this (test takes the min within each category and compares across categories, so any category-based scale with a clear gap between tiers works).

## Required extension to B10-3's ability-event emission (read `test_R_088_02` closely — this is not a new isolated function, it's filling in fields on an existing mechanism)

B10-3 built the `om_ability_event` emission path (ring buffer, `om_tick_read_ability_events`) but the fenced S-086 tests it satisfied only checked `tick`, `unit_id`, `ability_id`, `duration`. `test_R_088_02` now checks two more fields on events already being emitted:

- The Barrage activation event needs `telegraph_ticks == 30` (the 1.5s telegraph from R-086-05, already a real countdown B10-3 implemented — just surface its length on the event) and `cue_id == om_cue_lookup("cue_barrage_telegraph")`.
- The Fortify activation event needs `duration == 400` (S-086 already requires this — confirm it's already correct) and `radius == 350.0` (Fortify's own aura radius from R-086-06 — surface it on the event if it isn't already).

Read `csrc/unit.c`'s current ability-activation/event-emission code (from B10-3) before writing anything — you're adding two field-population lines per relevant activation site, not rebuilding the mechanism.
