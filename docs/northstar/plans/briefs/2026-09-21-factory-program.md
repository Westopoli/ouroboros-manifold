# The Factory: research and design program for Agora's autonomous build-and-QA system

## Context

Westley's target: Claude writes plans, stories, measurable and visual expectations, and tests (or later only defines tests for agy to implement); Agora transcribes them into cards and requirements, builds against the tests, and QA-tests the result the way a player would, until the expectations are met. Claude and Westley do the last 20 percent. The build half now works on E-05. The QA half was promised in PLAN.md (Principle 7, Stage 5 T1/T2 scenarios, probes C, D, G) but never designed end to end, and today's Stage 1 look found it proven only on a one-button toy scene, with a false-positive history and no path to the real game.

This is a thinking program, not an implementation plan. Its deliverable is a serious addition to `docs/northstar/PLAN.md` that says, at a high level and traced through, how the system builds and verifies everything the bible describes: 21 epics and 160 stories today, 20-30 eras, many landscapes, multiplayer, years of work, features nobody has defined yet, and other projects after Ouroboros. Implementation (Stage 3) and verification on each epic (Stage 4) follow only after Westley approves the design.

Constraints from Westley (first-class requirements of the design):
- **Incremental, never more than one bite.** A prototype ladder: the sim runs → chronicle on top → landscape/biome generation → objectives → units → multi-layer, each rung with its own functional and visual expectation and its own QA pass, every rung re-verifying the rung before it. Not a jump to the MVP.
- **Open-ended.** The system must absorb features that do not exist yet, months from now, without harness code changes: project knowledge lives in data, not in Agora.
- **Multi-project.** Ouroboros is the first tenant; a second project plugs in with a profile and a bible, not a fork.
- **Well thought out now.** Trace the implications, research how similar systems succeeded and failed, close the ambiguities, write it down.

## What Stage 1 established (inputs to the design)

Built and working: cards, ladder, regression gate, sizing cap, gate cards, `card_lint.py`, `card_slice.py`; Agora's director/explorer QA loop (DeepSeek plans, local qwen executes, DeepSeek judges), desktop backend on Xvfb with xdotool and a JSON debug-port protocol, budgets, fingerprinted findings, triage to fix work; probe C detectors (toy C, passed); rules files per epic; a real Godot client on the old Python sim.

Gaps: expectations are prose only and the rules files drop the visual end-state; e2e files cover 4 of 21 epics; card generation is Claude-triggered scripts, not an Agora step; the QA detector set is a web-app shell set, not the RTS bug catalog; screenshots are write-only; no T1 QA against the C sim; no harness scene, no Ouroboros campaign, no chain trigger; zero client or integration-ladder cards; the actor cannot press a key (every keyboard directive misreports as a bug); campaign 004 converged on a harness false positive nobody detected; the display-isolation fix (`69cc682`) is unmerged; rules cap 6000 chars; doc drift (pipe claim, escalation path, Godot 4.6 vs 4.7).

Prior art already surveyed (18 sources across two passes): Dream-RSI, AlphaEvolve, AIDE², Darwin Gödel Machine, SICA, ChatDev, MetaGPT, Anthropic's long-running-agent and context-engineering posts, Ralph loop, Spec Kit, SWE-bench harness-variance; TITAN, GBQA, playtest-agent, VideoGameBench, BALROG, SmartPlay, Voyager, Claude/Gemini Plays Pokémon, OSWorld, WebArena, godot-agent, metamorphic testing, EA SEED, modl.ai. Recurring principles: strong model specifies, cheap model executes; verification behavioral and automated, never self-report; state in files; structured artifacts over chat; archive of attempts; reward hacking actively defended; bounded work units; context curated; harness matters as much as model; actor and verifier separate; state oracles before pixels; scripted personas before LLM; tiny action vocabulary; replay before filing; pause-while-thinking for real-time games. The Fireship video's own transcript was unreachable; its subject (Dream-RSI: replay past attempts offline to pick the next strategy) is captured.

## Amendments from the Round 5 audit (2026-09-19)

An external audit stress-tested the design against the executor's fifth round (R7a-R7l in `DECISIONS.md`). Adopted, and binding on Phase B, B.9 and C:

- **Tick-stage closure.** When an acceptance test's symbol closure contains an orchestrator (for Ouroboros `om_world_step`), every hook the orchestrator runs joins the closure. A stub hook outside `allowed_files` blocks the card; the chain is ordered by hook stage. Replaces the pure symbol-closure cut rule (R7b, R7c).
- **Diff-scoped mutation gate.** Before DONE, the candidate's changed lines are mutated (operator flips, constant replacement); if no acceptance test fails on a mutant, the card is under-tested: no DONE, escalate to test authoring. Shadow fixtures stay for literal hard-coding but do not replace this (R7g).
- **Control-coverage lint.** A card whose function has "ways this could be wrong" items with no matching control in its acceptance fails lint (WARN for one epic, then FAIL). A function must be tested for the rules it owns, not for one field (R7g, R7d).
- **Plateau early-stop.** In the ladder, several distinct candidates failing on an identical test set stops the run and escalates to fixture diagnosis instead of spending the 10-run cap (R7e, R7h, R7l applied this by hand).
- **Fixture defects are a named failure class** in B.7 with their own detectors: unsatisfiable-by-construction controls (R7h), vacuous controls whose numbers never reach the branch (R7l), confounded two-agent fixtures (R7e), same-tick re-declaration (R7i, R7k: a bible gap, flagged as a rule question).
- **Sanitizers.** UBSan in every C card's build; ASan via `LD_PRELOAD` where it loads; Valgrind memcheck on a sampled subset. MSan dropped: it cannot be loaded into a stock Python through ctypes (A7 memo error, corrected).
- **Vision judge is not optional for rendering defects.** Visual claims are judged by Gemini vision via agy by default (capped like intervene); a local model only if PX-12's VRAM number allows. State first, vision never alone, but never absent.
- **Spec cache, not a third source.** The expectation spec is generated from the epic and never hand-edited; a drift check fails when a test's rule id has no spec entry or a fenced test changes without its epic changing (R7f edited tests and left the epic stale).
- **Skeletons carry standard includes** (`math.h`, `stdlib.h`, `string.h`); hoisting only helps when the model writes the include (R7a).
- **Parent patches are fenced like cards.** A hand patch may touch only the function the diagnosis names and never another card's scope (R7j implemented 204b1's job inside 204a1's function; `c3aa447` hand-implemented 204b1). Hand-implementation is an escalation needing Westley's sign-off, recorded in the run ledger.
- **Regression tiers stated explicitly:** per candidate, the whole headless suite (seconds); per rung gate, the earlier rungs' QA missions (minutes); per epic gate, everything.
- **Round 5's run data is the first input to B.7** (the failure-mode table), mined before decisions are taken.

## Phase A: Research (sonnet doers, read-only, 5-7 briefs)

Each brief answers named questions with sources and returns a memo saved under `docs/northstar/research/factory/` in the ouroboros repo (this is northstar research, Claude reviews every memo). Questions are chosen to close a specific ambiguity in the design, not to survey.

- A1. **Spec-to-task transcription at scale.** How Spec Kit, MetaGPT SOPs, and BDD/Gherkin toolchains represent a feature so that tasks, tests and acceptance derive mechanically; how they version specs; how they handle a feature type the pipeline has never seen. Output: candidate artifact schema for "story → expectation spec → tests → cards" that is project-agnostic.
- A2. **Verification against reward hacking with a weak implementer.** AIDE², DGM patch validation, SWE-bench harness-variance; mutation/positive-control practice; how fences and regression gates are kept honest when the implementer is a 30B model that will exploit any loophole. Output: the gate set (fail-first, green-check-by-lint, regression, gate cards, controls, replay) with the known holes and the missing ones.
- A3. **Long-horizon coherence.** Anthropic's initializer/coding-agent split, Ralph loop's coherence decay, ChatDev/MetaGPT drift; how projects run for months keep architecture coherent when every unit is a bounded card. Output: the periodic architecture-review pass (who, cadence, inputs) and what "archive of attempts" Agora should keep.
- A4. **Autonomous game QA as a plug-in.** TITAN state abstraction, playtest-agent oracles and personas, GBQA hallucination rates, godot-agent daemon, VideoGameBench latency; how detectors and personas are kept game-agnostic with a thin per-game profile. Output: the oracle taxonomy (state, invariant, metamorphic, visual) and the per-project profile shape.
- A5. **Self-improvement of the harness.** Dream-RSI replay, SICA harness self-edit, continual-harness refiner; what Agora may safely let a model change about itself (prompts, mission library, strategy choice) and what must stay human-owned. Output: the refiner loop and its guardrails.
- A6. **Content at scale.** How data-driven games ship dozens of era/biome packs on one engine (config-driven content pipelines, validation of content packs, procedural generation QA); how a factory validates content rather than code. Output: what "an era pack" is as an artifact the factory can build and QA.
- A7. **Multiplayer determinism and its QA.** Lockstep/deterministic sim testing, cross-platform trace checks, desync detection as a detector class. Output: the determinism gates the factory runs from the first rung.

## Phase B: Design (Claude, with Westley in the loop at each checkpoint)

Write the design as a system model, then trace it through scenarios. Sections:

1. **Artifacts and the pipeline.** Story → expectation spec (Given/When/Then with state checks, invariant ids, visual claims) → tests (fenced) → cards (sized) → build → gate → QA mission → finding → revision. Each artifact has a schema, an owner (Claude, script, agy, local model, Westley), a fence, and a positive control. Nothing in the pipeline names Ouroboros.
2. **Roles and models.** Specifier (Claude, day-side), transcriber (scripts, later an Agora step), implementer (local 30B), escalator (Gemini via agy), verifier and refiner (separate model, never the actor), judge of last resort (Westley via flags). What each may and may not change.
3. **The project boundary.** What lives in `agora/` (generic harness, action vocabulary, oracles, dispatch, budgets) versus `projects/<slug>/` (profile, rules, mission specs, detectors, planted bugs, campaigns) versus the project repo (bible, tests, code). A second project's onboarding checklist as the test of the boundary.
4. **QA architecture.** Game-side hook (dev-only daemon: canonical state, UI tree, fixture/seed, pause and tick-step, screenshot, input fallback); actor (scripted personas and replays first, model as escalation, extended vocabulary); oracles (T1 trace detectors and invariants; state checks; metamorphic relations; vision judge only for visual claims); verifier (replay to reproduce, then file); refiner; harness positive controls (planted bugs, input-liveness, scenarios that can fail); scheduling by the chain.
5. **The prototype ladder.** Rungs P0..Pn with, for each: what is built, the functional expectation, the visual expectation, the QA target and detectors, the gate that re-runs every earlier rung. Decided 2026-09-19 (D3): P0 sim runs and traces deterministically (headless) → P1 galaxy view renders it → P2 landscape/biome generation, opened by a design phase Westley joins (biome/landscape generation and its sister system: economy, buildings, civilization cities) with a Godot mockup he approves before any tests are authored → P3 objectives → P4 units and one mission → P5 fog → P6 two layers → P7 chronicle and time jump (after E-04, E-06, E-07) → P8 eras as data → P9 multiplayer. The ladder replaces round-major ordering for what enters Stage 3 next; Track L's rounds attach to rungs.
6. **Scale and cost model.** Cards per epic, runs per card, Gemini calls per run, QA sessions per rung, tokens Claude spends per story; where each grows with 20-30 eras and what stays flat because content is data.
7. **Failure modes and controls.** One table: mode, how it shows up, detector, control, owner. Includes everything found this week (impassable tests, whole-file rewrites, false-positive convergence, missing verbs, cross-card spans, silent regressions).
8. DONE 2026-09-21 (`research/factory/B8-scenario-traces.md`; seven design changes applied to PLAN.md, three Round 8 questions). **Scenario traces (the design's own tests).** Walk the design through: (a) a feature nobody has defined, month 6, touching sim, client and content; (b) era pack number 12; (c) a multiplayer desync report; (d) a QA finding that is really a story defect; (e) a second project with no game at all (a web app); (f) Agora idle because Tested runs dry. Each trace ends green or produces a design change.

Checkpoints with Westley: after A (research memos), after B.1-B.3 (pipeline and boundary), after B.5 (ladder), after B.8 (traces). Every ambiguity becomes a `Q-` flag with candidate answers, never a guess.

## Verification of this program

The design is accepted when: every PF experiment in B.9 has a recorded pass or a recorded design change; every scenario trace in B.8 ends green or in a recorded design change; every ambiguity has a `Q-` row; a reader can onboard a second project from the boundary section alone; the ladder's first three rungs each have a written functional expectation, visual expectation and QA target; the failure-mode table covers every incident from `harness_defects_2026-09-17`; and PLAN.md contains no stale claim the program found (checked by grep for the known ones).

## Working method

Claude thinks and writes; sonnet doers research, extract and check. Research memos land in the repo as they finish; design text is drafted in the plan file, reviewed with Westley, then moved into PLAN.md. No implementation, no card authoring, no dispatcher changes during this program; the E-05 chain keeps running under the executor's hand-off.
