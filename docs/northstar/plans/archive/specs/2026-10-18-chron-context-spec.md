# CHRON-CONTEXT: the chronicle's context terms (spec, rev 1, 2026-10-18)

**Status: drafted by the Architect from the 2026-10-18 pre-flight scout (read-only; lines on `origin/main` at `03cd9502`); Sonnet audit next; Westley's W3; builds after SIM-LOGS lands (it supplies `last_mission_region`). Not launched. Not a contract piece: no header, ABI, save or pipe change.**

## Why

E-09 R-066-02 and R-066-04, ALG-50: an event's significance is its base (tier plus a capped delta term) times a context multiplier with four terms: in the last mission's region (+0.5), an attached character (+0.3), chain length (+0.1 × min(L, 5) when L > 1), a lineage member in the region (+0.8). The jump scores every event with the first three fixed at 0 (`chronicle.c:1665-1672`, `chron_context_multiplier(0, 0, 0, has_lineage)`; the comment admits it). Sim lane ledger row 11; split out of SIM-LOGS by the round-3 audit (the chain length needs a per-jump store the loop does not keep: `fired[]` is a 128-entry per-tick buffer, `generational.c:1929`, refilled every tick, and a chain's `n_events` is complete only at loop end).

The reference never set `chain_length` (dead there too) and set a character only on the commander-death event; the bible is the rule, so the terms are implemented as written and the reference's silence is noted, not copied.

## Ruling (taken by the Architect 2026-10-18: **W3 (b)**, the bible's rule implemented; Westley may veto)

- **W3 chain length.** (a) stays 0 (the reference's effective behaviour); (b) **the number of events in the jump sharing the event's `chain_tag`, from the per-jump chain table `chains[].n_events` (`generational.c:2008-2022`), read after the loop; untagged events (tag 0) and events whose chain fell past `GEN_JUMP_CHAIN_CAP` (32, silently skipped today) count as length 1**. Lean (b): R-066-02, R-066-04 and ALG-50 say it.

## The piece

**Files.** `csrc/generational.c` only (`gen_time_jump`, :1948-2100), plus new tests. Owner `CHRON-CONTEXT`; `depends_on` SIM-LOGS (for `om_simlog_state.last_mission_region`; until it lands the pass reads `om_mission_last_region(w)` with a `has_last_region` flag the test sets, the test writer names the accessor) and the attached rows that hold `generational.c` (B7, B7b, B5-chronicle, B6-lifecycle, B6-collapse-pick: landed history, hold nothing).

**The store.** A local array in `gen_time_jump`, transient, never saved or hashed: `struct { uint32_t region, tier; double dsum; int32_t chain_tag; } rec[CHRON_JUMP_REC_CAP]` with `CHRON_JUMP_REC_CAP` = `DRAFT-chron-rec-cap` 8,192 (measured: about 986 events per 50-tick jump, 2026-10-15 and 2026-10-18 runs; the worst case is `n_ticks × OM_EVT_LOG_CAP` = 12,800 at a 100-tick jump, so 8,192 holds every measured jump with 8x margin and the worst case loses the tail). Overflow rule: past the cap the event is not stored, `n_rec_dropped` counts it, and it is scored in the loop exactly as today (context terms 0), so no event is lost from `net[]`, `event_fired[]`, `active[]` or `peak[]`; the count is printed by the probe, not asserted. Heap (`calloc`, freed at the end of the function) so the stack stays small; about 192 KB.

**The loop** (per fired event with `region_idx < nr`, when `track_events`): unchanged except that, beside the existing `om_chronicle_score_event` call that updates `active[]`/`peak[]`, the event's `(region, tier, dsum, chain_tag)` is appended to `rec[]` when there is room. `net[]`, `event_fired[]` and `chains[]` are filled exactly as today.

**The second pass**, immediately after the tick loop and before `om_lineage_generate_descendants` and `om_process_natural_deaths` (`:2034-2039`), because `om_lineage_member_in_region` (`:2196-2204`) reads active characters that lineage generation adds and deaths remove, and the loop's scores saw the pre-jump characters; a pass placed later would score a different lineage term. For each record: `chain_length` per W3; `in_mission_region = (region == last_mission_region)`, with `last_mission_region` -1 when no mission has ended in the campaign (SIM-LOGS) so no region matches; `has_character` 0 (no simulated event carries a character: `evt_fire`, `events.c:606`, sets none; `om_event_get_attached_character` serves manual fires only, `events.c:1100-1113`; the term stays a follow-up until events carry one, and the pass takes it as a parameter so that follow-up is one line); `has_lineage` as the loop computed it (`chron_region_has_lineage_member`, same world state). The score is `om_chronicle_calculate_score(w, tier, dsum, in_mission_region, has_character, chain_length, has_lineage)` (`chronicle.c:2096`, exists, uncalled); `peak[]`/`active[]` are rewritten for the region under the same rule the loop uses (`if (!active[r] || score > peak[r])`), starting from a cleared `peak[]`/`active[]` for the regions the records touch (the loop's own values for those regions are superseded; regions with only dropped events keep the loop's values). Everything after the pass runs as today.

**What stays byte-identical** when the new terms are 0 for every event (no mission ended, no chain longer than 1): every output, including the S070 values (3.6 and 2.0) and `om_chronicle_score_event`'s signature. What changes on purpose: the peaks of regions equal to the last mission region and of events in chains longer than 1, hence which regional entries the scroll picks there; the chronicle hash pins under `TD-SIM-2` move with SIM-LOGS already.

**Finding recorded, not fixed here:** `GEN_JUMP_CHAIN_CAP` 32 silently skips every chain past the 32nd in a jump (`generational.c:2008-2022`); the 2026-10-15 sweep saw 1,749 multi-event chains in 25 jumps, about 70 per jump, so most chains never reach `om_chronicle_add_chain_event`. This is a cause of ledger row 8 beside the score-0 push. Its own row: `CHRON-CHAIN-CAP`, after the rows 7 to 9 probe reports.

**Tests** (test writer, a different agent than the builder; `tests/csim/test_CHRON_context.py`): a jump with one mission ended in region r and a lone event in r scores base × 1.5 (+0.5) against the same event elsewhere; a two-event chain scores its events with +0.2 under W3 (b) (or unchanged under (a)); an event in a region with a lineage member keeps +0.8 after the pass (the pass reads the same characters: assert the peak equals the loop-era value when the mission and chain terms are 0); a jump of more than `CHRON_JUMP_REC_CAP` events (built by `om_event_fire_manual` in a loop or a 100-tick jump at the region count that reaches it; the writer measures) drops the tail, counts it, and loses no region from `active[]`; `test_E09_S070_my_family_is_always_in_the_story.py` stays green unchanged (the control that the signature and the lineage term are untouched). Positive controls: a build with the pass placed after `om_process_natural_deaths` fails the lineage-term test when the test kills the member in the jump; a hand-built record set with a wrong chain count fails the chain test. Red on the built tree because the mission-region term is 0 today (assertion line pasted by the writer).

**Acceptance.** The chronicle sweep (`scripts/simviewer/probes/chronicle_twin.py`) shows the mission-region bonus on entries about the last mission's region and, under (b), chain entries once rows 7 to 9 and `CHRON-CHAIN-CAP` land.
