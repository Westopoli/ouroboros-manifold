# Simulation viewer: port the old 2D strategic viewer onto the C sim

> **Spec with pre-flight corrections: `2026-10-12-simviewer-spec.md` (wins where it differs: binary framing, dbg pipe, core retention hook, SV-0 queued behind E7/W2/E1R).**

## Context

ROADMAP "Three steps" step 1 (docs/northstar/ROADMAP.md:97) asks for exactly this: verify the C simulation still follows the bible's stochastic rules by watching it, because the legacy Python sim had a pygame viewer and the C sim has none. Westley's ask (2026-10-12): a 2D view of every civilization and its regions, one colour per civ, per-region graphs of the current variables, a line graph over time, the events that hit each region; two modes, tick mode at a rate he sets and mission mode that jumps to the sim's next chosen mission, shows the chosen location, and lets him press "continue" and set a mission success level to see the effect on that region and the galaxy. The viewer is tooling: it never enters the game loop, so the no-runtime-API and determinism contracts are untouched. Goal of the tool: find regressions in mission choice and in the source of the chronicle.

## Stage 1: investigation (done, read from origin/main)

**The old viewer exists and is the right base.** `simulation/strategic_viewer.py` (894 lines, pygame) replays a JSONL dump: regions as nodes with faction colour, territory hulls, friction edges, a 4-arm "radar" per region (one arm per field), 60-tick sparklines in a sidebar, a faction sidebar, a bottom event log with click-to-jump, scrubber, play/pause, speed, pan/zoom, click-to-pick. Its producer `simulation/run_strategic_viewer.py` runs the legacy Python sim and writes the dump; `docs/random/strategic_viewer_plan.md` is its design note. `simulation/sim_viewer.py` is the tactical (unit) viewer, not this. Dump shape: header (regions with name/tier/colour, factions, layout) then one line per tick with `regions[i].fields` (military, economy, tension, population), `composites` (stability, capacity), `faction_id`, `events` (tick, region_id, type, chain_tag), `friction`, `factions` (budget, tech_level, stances, totals).

**The C sim already speaks everything the viewer needs, over the pipe** (`pipe/ouroboros_pipe`, JSON lines, docs/architecture.md:213-371):
- `set_seed` (seed, n_regions, features) builds the world and starts the campaign; `snapshot` gives every region's owner, tier, military, economy, tension, population, stability, capacity, the factions (archetype, budget, tech, stances), the edges, telegraphs, chapter, commander.
- `step` n / `run_to` tick stream a `delta` per tick: changed regions, `events` (region, template, chain, source, delta per field), `attacks`, `collisions`, `revolts`, faction budgets. Tick mode is `step 1` on a timer.
- `mission_start` (faction, era_kind) runs the sim's mission generator and answers a `mission` frame with the chosen `region`, `archetype`, objectives, force, briefing: that is "where the sim sent the player".
- `objective_complete` (objective, completion 0..1) then `mission_end` answers a `debrief` frame (band, achieved, brought_home, `region_delta` for the four fields, commander fate) and a fresh `snapshot`: that is the "success level" button. `mission_refuse` is the refusal path (band 5, tension rises).
- `jump` ticks answers a `chronicle` frame (entries, ownership timeline per stride, keyframes) then a `snapshot`: the time jump the game performs between missions. The sim picks the real length inside `om_time_jump_run` from the requested value (Q-056-01 notes the client sends raw ticks; the viewer sends what the client sends, read from `autoload/c_bridge.gd` at build time).
- `save` / `load` exist for bookmarking a state.
- Python already drives the pipe in tests (`tests/transport/test_pipe_tactical_world.py`: `subprocess.run([PIPE], input=frames)`), one-shot; the viewer needs a persistent process (`Popen`, line-by-line), which the pipe supports (architecture.md:318).

**The five outcomes (Westley's question, answered from the bible and the code).** S-077 "Five ways it can go" (docs/bible/epics/E-10-missions.md:122-130): final score = 0.75 x objective score + 0.25 x retention (R-077-01); the archetype's four thresholds classify it into total_failure, partial_failure, partial_success, strong_success, total_success (R-077-02; refusal is a sixth, R-078-05). S-078 applies the archetype's consequence table row for the band to the region (R-078-01 to R-078-04). The C sim does all of this today in `om_mission_end` (csrc/mission.c:1514-1541): scores objectives, measures retention from the force's HP, classifies with `om_mission_classify_band` (:1275, the R-077-02 table), applies `om_mission_apply_consequences` and the economy's mission end; the pipe's `mission_end` calls it and answers the `debrief` (band, objective_score, retention, commander fate). So the MVP does port outcomes into the simulation; no gap there.

**One gap for "pick one of the five":** nothing lets a client name a band. The only inputs are objective completion (`objective_complete`, 0..1) and the force's HP. Retention is 1.0 when every unit is unhurt (mission.c:1499-1511), so without a fight the final score is at least 0.25, and total_failure (thresholds 0.15 to 0.25) can never be reached from the viewer. The fix is a one-field contract addition: `mission_end` takes an optional `"retention"` (0..1) that replaces the measured value, documented in architecture.md as a tooling override (the game client never sends it). With it the viewer maps a band pick to (objective completion, retention): for a band whose threshold midpoint m is at least 0.25, retention 1 and completion (m - 0.25) / 0.75; below, retention 0 and completion m / 0.75. The viewer pins the R-077-02 threshold table with its citation, and its test asserts the debrief's band equals the pick for every archetype and band: a drift between the table and the code is then a finding, which is this tool's purpose. Per CLAUDE.md the pipe-frame change lands first as its own contract piece (SV-0, `csrc/pipe/om_pipe.c` `handle_mission_end`, `docs/architecture.md` session commands, one test in `tests/transport/`), audited by a second Fable chat before the viewer pieces build on it.

**What the pipe does not give:** 2D positions for regions (the Godot galaxy computes them from the graph in `scenes/galaxy/galaxy_gen.gd`) and region or faction names (no `om_region_name` in the header; the chronicle has name fragments but that is not needed here). The old viewer solved positions with a seeded spring layout from the edge list; the port does the same with a small deterministic force layout in pure Python (no networkx dependency; the old plan's networkx fallback is replaced). Names: `R<i>` and `F<id>`; colours by faction id from a fixed palette.

**Environment:** `.venv` is Python 3.12 with numpy, no pygame, no networkx. `pipe/ouroboros_pipe` builds with `make pipe/ouroboros_pipe`. Tests for Python tooling live under `tests/` beside `tests/skilllab`, run with the repo `.venv` pytest.

## Stage 2: design

**Shape: one new package, no edit to the sim, the pipe, or the client.** `scripts/simviewer/` (tooling beside `scripts/skilllab/`), three files, plus tests under `tests/simviewer/`:

1. `scripts/simviewer/pipe_session.py` (about 120 lines). `PipeSession` wraps a persistent `pipe/ouroboros_pipe` process: `send(cmd) -> list[frames]` reads frames until the verb's terminal frame (per architecture.md: `step` ends with the last `delta`, `snapshot` with `snapshot`, `mission_start` with `mission`, `mission_end` with `debrief` then `snapshot`, `jump` with `chronicle` then `snapshot`, `error` anywhere). Pure JSON in and out, no pygame. Positive control in its test: a fake pipe script answering canned frames; integration test on the real binary (skipped when not built, same pattern as tests/transport).

2. `scripts/simviewer/history.py` (about 150 lines). `History` turns the frame stream into what the viewer draws: the latest snapshot merged with every delta (regions by index, owner, the six values), a per-region ring of the last N ticks for sparklines, the per-region event list (tick, template id, chain, delta), the mission log (tick, chosen region, archetype, band, region_delta per mission), and the layout: a seeded force layout from the snapshot's edges (deterministic: fixed iteration count, fixed seed, positions rounded), cached per (seed, n_regions). Pure, testable without a display: feed it recorded frames from `tests/transport/fixtures/snapshot_seed1_tick10.json` plus a short recorded delta stream.

3. `scripts/simviewer/viewer.py` (port of `strategic_viewer.py`, about 600 lines). Keeps the old drawing functions (territory hulls, edges, node, radar arms, sparklines, event log, sidebar, controls strip, pan/zoom/pick) with their inputs changed from the dump's tick list to `History`. Two modes, switched with `M`:
   - **Tick mode:** `Space` play/pause, `[`/`]` change the rate (ticks per second from a fixed ladder 1, 2, 5, 10, 20, 50), `→` one tick; each timer tick sends `step 1` and folds the delta.
   - **Mission mode:** `Enter` sends `mission_start` and the map centres and flashes the chosen region with the archetype name in the sidebar; keys `1` to `5` pick the outcome (total failure, partial failure, partial success, strong success, total success; `0` refuses) and `Enter` again sends `objective_complete` for every objective at the computed completion then `mission_end` with the computed retention (see the five-outcomes note above); the debrief's band is shown beside the pick (a mismatch is drawn red: that is a finding), its `region_delta` on the region, and the before-and-after snapshot diff on the whole galaxy (regions whose owner or any field changed get an outline pulse for 2 seconds, the sidebar lists the top changes); `Enter` a third time sends `jump` with the client's default length and shows the chronicle entries in the event log and the ownership timeline as a scrubber over the jump's keyframes; then the loop repeats. Every mission is appended to the mission log panel (tick, region, archetype, picked band, sim band) so a bad run of choices is visible at a glance.
   - Both modes keep the old click-to-pick region sidebar (fields and composites as number plus bar, 60-tick sparklines, the region's events) and the faction sidebar (`F`).
   - Launch: `.venv/bin/python -m scripts.simviewer --seed 1 --n-regions 60 [--rate 5] [--mode mission]`; `--features` defaults to the client's launch set read from `autoload/c_bridge.gd` `DEFAULT_FEATURES` at build time and pinned as a constant with that citation.

**Dependencies:** `pygame` added to the `.venv` (tooling only; recorded in the simviewer README with the install line). No networkx.

**Not in scope:** names from the chronicle, the Godot galaxy's exact positions, save-slot browsing beyond `save`/`load` to a path, anything in `csrc/`, the pipe, or the client. The old `simulation/` files stay as they are (legacy reference, ROADMAP step 1 names them).
