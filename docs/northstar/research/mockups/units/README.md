# P4 units mockup — design as built

Rung P4 of the prototype ladder: six units, movement and combat on one layer, toy tactical sim in GDScript at a fixed 20 Hz tick, seeded and replayable from a command list. Built against E-11, E-13, E-18's 60-second paragraphs and Round 1 rules (R-082 through R-100, R-132/R-136).

## Running it

```
~/.local/bin/godot --scene scenes/mockups/units/units_mockup.tscn
```

Hotkeys: `Space` play/pause, `T` step one tick, `R` reset the current scenario, `Tab` toggle kit, `F12` screenshot, left-click select, left-drag box-select, right-click move, `Shift`+right-click attack-move, right-click on an enemy attack-target. Scenario dropdown and kit button are also clickable in the HUD.

This could not be run on Westley's seat from this session; confirmed instead that the QA driver is inert without `--qa-script`: booting the scene through `qa_boot.gd` with `--qa-scene res://scenes/mockups/units/units_mockup.tscn` and no `--qa-script` produces an empty output directory (no `_run.json`, no side effects) — the driver's own `_ready()` returns immediately when that arg is absent.

## Design as built

**Roster and kits.** `roster.gd` loads a kit JSON (`kits/greek.json`, `kits/settled_reach.json`); both carry the identical R-082-01 stats table, differing only in display name, palette, and (deliberately) nothing else in silhouette geometry — the era-agnostic rule (R-145-01) says a Raider reads as a Raider in any era, so shape and size are shared, only colour and name vary. Six roles: `flanker` (Raider/Peltast), `screen` (Interceptor/Skirmisher), `frontliner` (Vanguard/Hoplite), `support` (Warden/Priest), `artillery` (Bombard/Ballista), `anchor` (Bastion/Phalanx). Silhouette shapes: `swept_dart`, `flat_wing`, `wedge_slab`, `spire_radial`, `long_barrel`, `wide_block`, one fixed vocabulary word per role, sizes doubled once during the first pass for legibility (see checklist).

**Sim (`toy_sim.gd`, `UnitsToySim`).** Fixed 1/20s tick, in order: commands, targeting, movement, collision, attacks, facing, deaths. Movement is BFS route + line-of-sight string-pulling on a 100wu grid for point-to-point orders, with a per-tick ally-block probe (40wu ahead) and a fixed left/right sweep (seed-biased per unit) for local deflection; a deflected heading holds for 60wu before re-evaluating. A multi-unit move/attack-move order translates a shared destination by each unit's offset from the group's centroid (not a literal shared point — units can't all physically stand on the same coordinate) and paces the whole group to its slowest member's speed, which is how `formation_move`'s "arrive together" requirement (FORM-9, ≤40 tick spread) is actually achieved; this pacing mechanism isn't named by any R-### rule and is flagged below as a design choice, not a guess. Collision is a 3-iteration push-apart pass, 30wu minimum separation, stationary units take zero displacement. Attacks are flat-damage, backswing-gated (10 ticks); every unit's attack timer starts pre-charged so the *first* shot after acquiring a target fires immediately rather than waiting a full interval — a deliberate pacing choice for a 60-second demo, not an R-### requirement, and flagged below. `flank_4v4`'s Raiders are now issued as four independent single-unit `attack_move` commands converging on one point rather than one shared group command, so they path independently instead of preserving their start-spread all the way to the destination (fix pass, see checklist item 4).

**View (`unit_view.gd`).** One `MultiMeshInstance3D` per (role, faction), mesh built once per silhouette shape via `SurfaceTool` (a flat-topped extruded polygon for five shapes, a base prism plus a central-apex cone for `spire_radial` since the fix pass — a flat cap read as a plain disc), material per (role, faction) with `vertex_color_use_as_albedo` on and the per-instance colour carrying the fully-resolved colour directly (faction colour at rest, lerped to the flash/death boost colours on hit/death — fixed this pass; a multiplicative tint against an already-saturated albedo can never brighten past the base colour, so the original design could never actually flash or flare regardless of camera work). The render transform (`get_unit_render_transform`) scales each shape's own measured local bounding box to the kit's declared `size` exactly, so a recipe's rendered footprint always matches its declared length/width/height regardless of the shape's internal point proportions (fixed this pass — see checklist item 1 for the two stacked bugs this replaced). Strike roles (`flanker`, `screen`) draw 3-5 small copies in a fixed V-offset pattern to read as a squad. Hit flash and the death sequence (bloom → drift → darken → remove) are driven purely by `current_tick - event_tick`, never wall-clock — deterministic regardless of frame pacing. Death removal is fixed at 80 ticks (4.0s) post-death, chosen to sit inside both the brief's "3 to 5s darkening" and DEATH-8's "60 to 100 tick wreck window" language, which otherwise conflict with a separate "removed at 15s" line — flagged below.

**Camera, HUD, input.** `camera_rig.gd` is fixed top-down (pitch locked at 90°, never tilts, unlike the landscape mockup's dynamic pitch) with pan/edge-scroll/wheel zoom, height range 500-12000wu, canvas 8000x8000wu, ground plane 14000x14000 (enlarged from 9000 this pass — the old size showed void/sky at the edges above camera height ≈5428). `hud.gd` owns the sim instance, kit/scenario loading, the play/pause/step loop, and all input: left-click select, drag-box select, right-click move/attack-move (shift)/attack-target-on-enemy, scenario dropdown, kit toggle (Tab), tick/survivors/selected/command-log readout; the four readout labels carry a black outline since this pass (they were pale-grey-on-pale-ground, nearly invisible). `qa_tick_until_flash(max_ticks)` (new, on the root and `hud.gd`) steps one tick at a time until a hit-flash is active, for QA scripts that need to land mid-fight reliably instead of on a fixed tick count.

**Scenarios.** Six JSON files at the brief's 60-second numbers: `lineup` (all six roles in a row, spacing tightened this pass for the height-900 camera), `mirror_10v10` (frontliner mirror, 250wu, both attack-move), `bombards_1000` (10 artillery vs. a close point-man frontliner plus two trailing at 1000wu, so all ten bombards concentrate fire on one target the way the E-11 paragraph implies), `flank_4v4` (4 flankers vs. 4 artillery around a routing obstacle — Raider start positions and the obstacle repositioned this pass so the approach spreads into two prongs instead of single file), `formation_move` (4 flankers + 4 anchors, 3000wu move), `plain_move_under_fire` (3 frontliners crossing under 2 artillery, testing R-096-01).

## What the report answers (see also the finishing report, delivered as chat output)

1. **Silhouettes.** All six now read individually or as a distinct squad cluster at the height-900 lineup camera: `frontliner` (wedge), `anchor` (wide block), `support` (octagon + raised spire, was a plain disc), `artillery` (long thin barrel, now correctly the longest single-model silhouette on screen — was the smallest blob, root cause traced and fixed this pass), `flanker`/`screen` (two visually distinct squad clusters, small diamonds vs. larger wings).
2. **Fight pace.** `mirror_10v10` (pure frontliner mirror): no death within 1200 ticks (60s) at these R-082-01 numbers — first death measured at tick 1576 (~79s), well past the "obviously working in 60 seconds" bar, though still comfortably inside R-085-01's ≥45s floor. `bombards_1000` (concentrated-fire design): first death at tick 124 (6.2s, confirmed via `qa_state`), matching the "before they close" framing well. 45s does *not* feel visually readable for the pure mirror at these numbers — see the open question below (unchanged this pass; toy_sim.gd's stats/timings weren't touched).
3. **Flanking.** Fixed pass: repositioning the Raiders into two spread pairs and issuing four independent attack-move commands (rather than one shared group command whose offset-from-centroid math preserved the tight start-cluster all the way to the destination) produced a visible two-pronged approach instead of single file (see `pass1/flank_result.png`) and meaningfully improved the outcome (1 Bombard now dies, was 0). But over the full run to ~1500 ticks, **Bombards still win** (3 alive, 0 Raiders) — the opposite of the E-11 paragraph's "Raiders kill the Bombards." Per the brief's instruction, stats were not tuned to force a different outcome; recorded below with two candidates.
4. **Frame/tick time.** `fps_ms` (llvmpipe, 720p, per rendered frame): 156.5ms. `timing_ms.tick_avg` (20 units): 0.30ms, well under the 2ms budget.
5. **Under-defined points** — see below.

## Questions for Westley

Built the simplest thing that shows each question; no candidate was picked silently.

- **Formation-pace mechanism.** `formation_move`'s "arrive together" requirement isn't specified by any R-### rule in the toy_sim section. Implemented: a multi-unit move order paces the whole group to its slowest member's speed (simplest thing that satisfies FORM-9). Candidates: (a) keep this as the toy's answer; (b) a real formation system with per-unit slots/offsets held relative to a leader (E-13 S-095, explicitly out of Round 1 scope); (c) no cohesion at all — accept "arrive together" only holds for same-speed groups.
- **Pre-charged attack timer.** Every unit's first shot after acquiring a target fires immediately rather than waiting a full interval. Candidates: (a) keep pre-charged (used throughout this build, makes `bombards_1000`'s pacing work); (b) require a full interval before the first shot too (more "realistic," but pushes `bombards_1000`'s first death well past 60s using the same concentration design); (c) split the difference with a shorter fixed first-shot delay.
- **Death-visual removal timing.** Brief text conflicts: "3 to 5s darkening" / DEATH-8's "60 to 100 tick wreck window" vs. a separate "removed at 15s" line. Built at 80 ticks (4.0s), inside both the darkening range and DEATH-8's window; the "15s" line is either a different (longer, colder-linger) phase this toy doesn't implement, or a stale number. Candidates: (a) keep 80-tick removal as the whole lifecycle (this toy); (b) darken over 80 ticks then hold a "cold" wreck until 300 ticks (15s) before removal, matching the 15s line literally; (c) treat 15s as superseded by DEATH-8's window.
- **Flank outcome: Bombards still win even with a spread, two-pronged Raider approach.** With R-082-01's numbers (Bombard sensor 300wu, range 1200wu, area 150wu, no minimum range) and the fix pass's spread-approach `flank_4v4` (no longer single-file — see checklist item 4), four Raiders still lose to four Bombards over a full run (Bombards 3 alive / Raiders 0 by tick ~1500), the opposite of the E-11 paragraph. The spread approach did measurably help (1 Bombard now dies before the Raiders are wiped, was 0) but didn't flip the outcome. Candidates: (a) give artillery a minimum range, so Raiders that close inside it stop taking fire — turns "get close" into a real tactic; (b) the E-11 paragraph may assume the flank arrives unseen (no sensor/fog model exists in this toy to test that — Bombard sensor 300wu is *smaller* than its own 1200wu range, meaning in a real fog-of-war build the Bombards might not even see Raiders approaching until they're already close, which this toy can't represent); (c) accept the toy's numbers are correct and the E-11 paragraph needs revising once a real build can test sensor/fog interaction.
- **Projectile look.** Round 1 of this mockup has no projectile/attack-visual layer at all (E-18 S-134 is a separate story, not in this ladder rung's scope per the brief's "abilities off in Round 1" framing extended informally to attack visuals); combat reads only via hit-flash and death. Candidates: (a) add a placeholder projectile line/dot for a future pass; (b) leave attack visuals to the eventual real renderer, this toy only needs to prove movement/combat/death.
- **Flinch (R-087-01) and the `stop` command (R-096-06).** Both explicitly skipped/deviated per the brief's own instruction ("Flinch may be skipped, list it"; `stop` implemented as "clear order" rather than literally rejected). Listed here as instructed, not re-litigated.
- **Damage scale for the toy.** R-084-01's full damage model (Brace/Fortify/Warden-aura reduction, R-084-03's AoE cap) is not implemented — flat base × matchup(1.0) only, no falloff, no AoE. Reasonable for Round 1 (abilities off), but Bombard's `AoE wu: 150` stat is present in the roster and silently unused. Candidates: (a) leave AoE for a later combat-visuals pass; (b) implement the AoE cap now since it's cheap and would change `bombards_1000`'s pacing materially.

## Fresh-eyes review (2026-09-22, Sonnet reviewer, screenshots only)

Verdict: fix first. The toy sim's checks are green, but the render and the camera framing fail three of the epic's "obviously working" claims on direct inspection. Blockers: the artillery silhouette renders as the smallest blob on screen although its kit size is the longest (a mesh-scale defect the size-only check SIL-3 cannot catch); mid-fight and end-of-fight shots are identical with no hit visible; the flank shot clips the Bombards at the frame edge before contact; the death pair is indistinguishable at that camera height. Should-fix: the support silhouette reads as a plain disc; the two Strike squads are indistinguishable at the lineup camera; black void bars at the map-zoom edges; low-contrast HUD on the first frame; the facing shots were never committed. Held for Westley: with the table's numbers (Bombard sensor 300 wu, range 1,200 wu, area 150 wu) four Raiders funnelled single-file by the obstacle lose to four Bombards, the opposite of the E-11 paragraph; the fix pass spreads the approach first and escalates the sensor-versus-range interaction as a rule question if the Bombards still win.

## Fix pass response (2026-09-22)

All nine items from the fresh-eyes review addressed; full before/after evidence per item in `scenes/mockups/units/qa/checklist.md`. Two blockers turned out to have a deeper root cause than the review anticipated, traced and fixed (not just reframed with better camera work):

- **Artillery silhouette (blocker).** Not a single bug: `Basis.scaled()` doesn't scale local axes the way the original code assumed (verified empirically with isolated probes), compounded by shape recipes whose local bounding box doesn't span the full unit square on every axis. Fixed at the transform level (`unit_view.get_unit_render_transform`) so every recipe's rendered footprint now matches its kit `size` exactly. New render-level regression check (FOOT-12 in `verify.gd`) added specifically because SIL-3 is data-only and cannot see a mesh-scale bug like this.
- **No hit/death visible (blocker).** Root cause was two stacked bugs in the material/colour pipeline, not camera framing: `vertex_color_use_as_albedo` was never set (the whole flash/death colour mechanism was silently ignored by the renderer), and even fixed, the design multiplied a near-white tint against an already-saturated base colour — mathematically incapable of ever brightening past the base, so no camera position could have made it visible. Fixed by making the per-instance colour carry the fully-resolved colour directly. This single fix unblocks both the death pair and the fight-mid hit-flash requirement.
- **Flank clipped at frame edge (blocker).** Camera now follows the two forces' actual midpoint at capture time; raiders repositioned into a two-pronged spread approach (see below).
- **Support disc, Strike squads indistinguishable, void bars, HUD contrast, uncommitted facing shots (should-fix, all five).** All fixed; see checklist items 2, 3, 7, 8, 9.
- **Held: flank outcome.** The spread, two-pronged approach (four independent attack-move commands instead of one shared group command that preserved the tight start-cluster to the destination) measurably changed the fight — 1 Bombard now dies before the Raiders are wiped, was 0 — but Bombards still win the full engagement. Per the brief's instruction, stats were not tuned; recorded in Questions for Westley above with three candidates (artillery minimum range; the E-11 paragraph may assume an unseen approach that this toy has no sensor/fog model to test; or the toy's numbers stand and the paragraph needs revising).
