# P5 fog and sensors mockup

## Design as built

`scenes/mockups/fog/fog_mockup.tscn` is the entry point: `~/.local/bin/godot --scene scenes/mockups/fog/fog_mockup.tscn`. Hotkeys: **B** Begin Mission, **M** toggle fog memory, **R** Reset (reseed from the spinbox), **T** step 20 ticks, **Space** play/pause continuous ticking. Left-click a friendly to select it (bolds its sensor ring); right-click issues a straight-line move to the selected friendly.

The scene is split exactly as the brief's file tree: `truth.gd` (`class_name FogTruth`, `RefCounted`) is the toy sim — it owns two friendlies (a 700wu and a 500wu sensor unit) patrolling scripted rectangular waypoint loops, eight enemies (three of them near the friendlies' starting positions and always deterministic — `radius 0.0` loops, so their position is their fixed `center` regardless of seed; five more sit far out of range, three of those with small nonzero loops purely for visual flavor and seed-jitter), three obstacle boxes (two `tall: true`, blocking line of sight; one decorative), three zones (one `interference` at intensity 0.5, one `hazard`, one `cover` — only `interference` affects anything numerically), five node markers, and two enemy structures. `compute_visibility()` recomputes from scratch every call — no memory, matching R-089-04 — using each friendly's own interference-shrunk effective radius and a 2D segment-vs-AABB line-of-sight test against the tall obstacles only. `fog_grid.gd` (`class_name FogCellGrid`) is a flat 64x64 cell array (100wu cells on the 6400wu canvas) with three states; `update()` marks cells under any circle `visible`, and cells that drop out of vision go to `explored` if the memory flag is on or straight to `never_seen` if it's off — never back to `never_seen` while memory holds. `fog_view.gd` (`class_name FogView`) builds the static terrain once and every `_sync_view()` rebuilds only the dynamic layers (friendlies, the filtered enemy list, sensor rings, the fog quad); it never receives `truth.enemies` itself, only whatever list `fog_mockup.gd` hands it after filtering by `visible_enemy_uids` — that filtered-list-only pattern is exactly what the real Godot client should copy for R-089-03.

The client-truth split the brief asked for (R-089-03: "the mockup's toy sim keeps the truth in a separate object and hands the view only the visible set, and a check proves the view has nothing else") is VIEW-4 and STRUCT-7: `fog_mockup.gd`'s `_sync_view()` builds `enemy_list` by filtering `_truth.enemies` against `visible_enemy_uids` *before* calling `_fog_view.update_enemies(enemy_list)` — `FogView` never sees the unfiltered array, and `FogView.get_enemy_uids()` (reading `MeshInstance3D` node metadata back out of the actual scene tree, not cached data) is what verify.gd asserts against.

The fog quad itself is a single `Image`/`ImageTexture` on one `PlaneMesh`, rewritten cell-by-cell every mission tick (the brief's "either is fine, `Image` is simpler" option). Recon phase bypasses the grid entirely and just fills the image fully transparent, matching R-092-01/04. Sensor rings are `ArrayMesh` `PRIMITIVE_LINE_STRIP` circles, cheap and Compatibility-safe.

Pass-2 fixes (fresh-eyes review of the pass-1 screenshots): `hud.gd`'s readout was reading `qa_state().visible_enemy_uids` (truth's raw, phase-blind visibility) instead of `view_enemy_uids` (what `FogView` actually holds), so recon showed "visible enemies 3 of 8" with zero enemies drawn; it now reads `view_enemy_uids`, and `RECON-5` asserts the HUD text itself is 0 in recon and matches `view_enemy_uids.size()` after Begin. Node `Label3D`s existed but `font_size 48 * pixel_size 0.01` (the default) rendered 0.48 world-unit-tall text against a 6400wu map — invisible at any camera height; `pixel_size` raised to 2.2 makes every node's type text legible at the standard camera height in a 720p shot (`fixed_size` was tried first and instead blew the label into a screen-filling quad at these distances — reverted). The standard camera (`qa_camera` in `qa/smoke.json`) moved from `(4000, 3200, 3200)` to `(5500, 3200, 3450)`: the old framing put friendly 2's patrol loop past the bottom edge in 6 of the 8 review shots (derived and solved via the rig's fixed 72° pitch, where the screen-center ground point equals the pan target exactly).

## Resolved: the pass-1 "environmental" hang was a harness bug, not contention

Pass-1's report blamed the full `qa/smoke.json` script hanging after 4-5 screenshots on machine contention (~30 concurrent Godot QA processes, load 18-23 on 16 cores) and worked around it by splitting the script across short-lived launches. That diagnosis was wrong. The real cause, found and fixed on `main` in `b65afa8`: `qa_boot.gd`'s `SceneTree` wrapper runs the mockup without autoloads, but did not free them first — the `SimBridge` autoload's Python sim died immediately under the wrapper, `SceneRouter` routed to the error screen, and freeing the mockup mid-script produced the fade-then-stall pass-1 saw and misattributed to load. `qa_boot.gd` now frees every autoload before instantiating the mockup scene. This pass's fixes were verified by merging that commit and running the unmodified `qa/smoke.json` as one script (clean 1280x720, the 1920x1080 review batch, several oracle-plant runs) — all finished inside the 600s timeout with `errors.txt` count 0, no splitting needed.

## Bug found and fixed during QA: enemies_px was off by 1.5x

`get_viewport().get_visible_rect().size`, read from inside this scene, reports `(1920, 1080)` — the project's base resolution — regardless of the actual `--resolution 1280x720` (or any other) the QA run captures at (confirmed with a debug print). `Camera3D.unproject_position()` computes in that same inflated space, so `qa_state()`'s `enemies_px` (the field the brief's HIDDEN-X/RECON-X pixel-probe oracles sample screenshots at) was reporting coordinates 1.5x too large in both axes — probing the wrong pixel entirely. `_project_to_ground()`/`_pick_friendly()` (mouse click → world ray) had the same bug in the opposite direction. Fixed by scaling `unproject_position()`'s output down and the mouse position up by `DisplayServer.window_get_size() / get_viewport().get_visible_rect().size` (`fog_mockup.gd:_viewport_scale`/`_unproject_to_window_px`). Verified: before the fix, a 50x50-pixel search around `enemies_px["102"]` in the `recon-shows-enemy`-planted `recon.png` found 0 enemy-red pixels; after the fix, the same search at the corrected coordinate found ~400.

## Questions for Westley

1. **Obstacles/zones/nodes drawn always, even under `never_seen` fog.** The epic's R-092-03 says terrain stays visible after Begin Mission; the `references/E-12/notes.md` derived rule says never-seen space is pure black with no terrain. This mockup followed the brief's explicit instruction, so `memory_off.png` and the new `memory_off_full.png` (map-height, memory off) both show fully-lit obstacle boxes and node labels sitting in otherwise pure-black fog — visually looks like a bug but is doing exactly what was specified, and `memory_off_full.png` is the clearest single proving shot for this tension since it isolates "everything but current vision" at full map scale. Left unchanged this pass — this is a design question, not a bug. Candidates: (a) keep terrain features always-visible (current — simplest, matches "recon shows everything" framing extended past recon), (b) gate obstacles/zones/nodes behind the same three-state fog as the ground (matches the reference screenshots literally, costs a per-object visibility toggle keyed to the same grid lookup already used for structures).
2. **Q-089-01 (ghost markers).** This mockup draws nothing at an enemy's last-known position once it drops out of vision — R-089-04 taken literally. Candidates: (a) no memory of enemy positions at all (current), (b) a faded/greyed last-seen marker that persists until vision returns, matching some RTS conventions, (c) a last-seen marker only for *structures* (already partially true here — buildings darken instead of disappearing) and never for units.
3. **Q-094-01 (sensor circles for unselected units).** Current: every friendly's ring is always drawn, at low alpha; the selected unit's ring is bold. Candidates: (a) current (every ring always visible, selection just changes weight), (b) only the selected unit shows a ring at all, (c) rings show on hover but not otherwise.
4. **Interference zone look.** Current: a flat translucent purple `CylinderMesh` patch, distinct from the fog's black/dim greys. Candidates: (a) current flat tint, (b) a hatched/striped pattern for a busier "something's wrong with sensors here" read, (c) an animated pulse (ruled out for the mockup — brief disallows shader-driven effects, but a `CPUParticles3D` drift would be cheap and allowed).
5. **Fog cell size / dim level / edge softness.** Built: 100wu cells (64x64 over the 6400wu canvas), 60% black alpha for `explored`, hard-edged cells (no blur/feather). Candidates for dim level: 50% (a bit lighter, closer to some RTS conventions) vs the current 60%. Candidates for edge softness: hard cells (current, cheapest, and the brief's own suggested approach) vs. a blurred/anti-aliased fog edge (would need a shader or a much finer grid — likely not worth it for a mockup).

## Mockup review 1 fixes

**Edge scroll.** Root cause: `camera_rig.gd`'s edge check compared the tracked mouse position against `DisplayServer.window_get_size()` (real window pixels), but the mouse position itself was tracked in canvas space (`get_viewport().get_visible_rect().size`, the project's fixed 1920x1080 base resolution under `canvas_items` stretch — see the shared README's own note on this). On Westley's window (4480x1440, real pixels) the right/bottom thresholds compared against numbers far larger than the canvas ever reaches, so those two edges were unreachable; left/top happened to work because 0 is 0 in both spaces. Separately, `get_viewport().get_mouse_position()` tracks the real `DisplayServer` pointer, which never moves under Xvfb's synthetic `move` verb, so the bug was invisible to any oracle built on that call. Fix: track the mouse from `_unhandled_input`'s `InputEventMouseMotion.position` (fires for both real hardware and the QA driver's synthetic events) and compare it against the same canvas-space `get_viewport().get_visible_rect().size` the zone thresholds are already defined in, one coordinate space throughout. Also skip edge scroll while `gui_get_hovered_control() != null`, since the HUD panel sits inside the top-left edge zone. Evidence: `qa/edges.json` run at `--res 2560x1440` (`scripts/mockup_qa.sh run fog scenes/mockups/fog/qa/edges.json <out> --res 2560x1440`, 0 errors) — `camera_pan` moved from `[3200, 3200]` (center) to `[4439, 3200]` on a right-edge mouse (+x), to `[4439, 4440]` on a bottom-edge mouse (+z), to `[3199, 4440]` on a left-edge mouse (-x), and to `[3199, 3200]` on a top-edge mouse (-z) — all four directions now pan, including the two Westley reported dead.

**Seed.** Root cause: `truth.generate(seed)` seeded an RNG that only drew enemy patrol phase offsets; every obstacle, zone, node, structure, and friendly waypoint order came straight from the loaded fixture/scenario files regardless of seed, so two different seeds produced numerically distinct but visually indistinguishable maps. Fix, all inside `generate()`: every obstacle, zone, and structure position is jittered by up to 400wu (`_jitter()`), the interference zone is additionally rotated around the canvas center by a seed-derived angle (`_rotate_interference_zone()`), each enemy that patrols a loop (`radius > 0`) gets a seed-picked loop radius from a fixed candidate set and a seed-picked direction, and each friendly's waypoint list is reordered and optionally reversed from a seed-derived offset (`_reorder_waypoints()`). `fog_mockup.gd:_regenerate()` calls `_fog_view.rebuild_terrain()` after `generate()` so the rebuilt obstacle/zone/structure meshes reflect the new positions, and `_grid.setup()` gives the fog grid a clean slate to re-derive against the new layout. `hud.gd`'s seed spinbox now connects `value_changed` (in addition to the existing R-key reseed) so dragging or typing a new seed regenerates immediately. Evidence: headless `SEED-11` (`verify.gd`) asserts seeds 11 and 12 place at least half the fixture's obstacles more than 200wu apart — passes clean, fails under the `seed-ignored` plant (confirmed `PLANT seed-ignored LIVE`, 3 failures: `DET-1`, `SEED-11`, `SPIN-12`). Headless `SPIN-12` sets the HUD spinbox's `value` directly (not via a UI click) and asserts `qa_state().seed` and `regen_count` both updated. The Xvfb pixel oracle (`qa/seed_diff.json`, `--res 1920x1080`): clean, `diff recon_seed11.png recon_seed12.png` = **0.114447** (>= 0.10, the two seeds now render visibly different maps); under the `seed-ignored` plant, both screenshots come out **0.000000** apart (both seeds forced to 11 internally, `qa_state().seed` reports 11 for the seed-12 shot too) — the plant is a clean, provable positive control on both sides. `recon_seed11.png` was pixel-identical (diff 0.000000) to the batch's own `recon.png`, so only `recon_seed12.png` was added to `pass1/`.

Side effect, expected and correct: seed 11's own layout is no longer byte-identical to the pre-fix screenshots, because the RNG stream is now consumed by jitter and enemy-loop draws even when the seed is 11 — the fixture is still the deterministic base, but every seed (11 included) now perturbs it. The full `pass1/` batch was re-shot at 1920x1080 against the fixed camera framing and hardcoded `qa_move` target used by `qa/smoke.json` (already re-aimed at the new seed-11 interference zone position in this branch's earlier commit); every existing headless check (`VIS-2`, `LOS-3`, `VIEW-4`, `RECON-5`, `MEM-6`, `STRUCT-7`, `SYM-8`, `JSON-9`, `TIME-10`) stayed green, and all 6 plants (`fog-leak`, `no-memory`, `recon-shows-enemy`, `radius-ignored`, `los-ignored`, `seed-ignored`) came back `LIVE`. Three of `qa/checklist.md`'s recorded pixel numbers moved because the new seed-11 layout is visually different from the old one and their screenshots were regenerated: `DET-1`'s recorded hash (`4183577953` → `2378956369`, both reproducible across two independent clean runs), `TRAIL-X` (`0.034728` → `0.031647`), `MEM-X` (`0.060932` → `0.059319`), and `RING-X`'s planted diff (`0.416238` → `0.371383`, `circles["1"]` still correctly stuck at 700wu under `radius-ignored`). The `enemies_px["102"]` pixel coordinate `RECON-X`/`HIDDEN-X` probe against (enemy 102 has `radius 0.0`, so its position is seed-invariant by design) is unchanged at `(786, 87)` at 1280x720 — reconfirmed this pass, not stale.
