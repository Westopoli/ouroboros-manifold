# Objectives mockup (P3)

This mockup shows P3 of the prototype ladder (`docs/northstar/PLAN.md:164`): given an archetype, the primary objective is placed at the right kind of place on a generated map, marked and named on the ground and in the HUD, its progress is legible, and the placement is satisfiable.

## Run it

```
~/.local/bin/godot --scene scenes/mockups/objectives/objectives_mockup.tscn
```

Hotkeys: archetype dropdown and seed spinbox in the top-left panel; **R** regenerates with the current dropdown/spinbox values; **T** advances 50 toy ticks; **P** toggles autoplay at 20 ticks/second until the mission completes. Mouse wheel zooms (height 800-20,000wu), WASD pans, edge-scroll pans. The 200x200 minimap bottom-right shows every fixture node as a dot, the player spawn as a blue square, and the current objective as a kind-specific glyph.

A wrapper run without `--qa-script` leaves the `QADriver` inert — confirmed: `qa_driver.gd`'s `_ready()` returns immediately when `--qa-script` is absent from `OS.get_cmdline_user_args()`, so no `_run.json` or any other QA output file is ever written on Westley's own interactive launch.

## Design as built

**places.gd** loads one of the three seeded fixture dumps (`fixtures/nodes_seed{11,12,13}.json`, produced once by `tools/dump_nodes.gd` from the landscape mockup's `FieldMap.generate()`, never at runtime) and exposes `nodes_of`/`candidates`/`player_spawn`/`enemy_spawn`/`route_length`/`route_path`. Routing is a real `AStarGrid2D` over a 100wu grid; cells within 150wu of any `hazard_anchor` are always blocked, cells within 1200wu have a 5% seeded chance of being blocked (deterministic per-cell, not draw-order-dependent), giving the "not always a straight line" behaviour the brief asked for without making the map impassable.

**mission_gen.gd** carries the ten-archetype table from R-073-01 (the "or" row, Reconquest, takes its first-listed kind per the brief's instruction). For each kind it picks a candidate node (seeded, cycling through alternates on failure and recording what it skipped), checks satisfiability (inside canvas, >=2000wu from the player spawn, route time within the R-076-01 time budget), and builds the toy-tick state (target/enemy scatter, escort route with a small seeded cosmetic jitter). `tick()` advances progress per R-075-02 to R-075-06, including the hold_zone pause window (200-300) and completion at 1.0 (R-075-07).

**markers.gd** draws the beam/label/ring/glyph/scatter/route per kind, sharing a small static mesh+material cache across regenerates. The marker label uses `pixel_size` 2.2 (billboard, no_depth_test). **objectives_mockup.gd** additionally draws every fixture node as a small flat box and type label (`pixel_size` 1.6), and a faction-blue block at the player spawn.

**camera_rig.gd** is a fixed top-down rig (pitch 90 degrees, R-103-03) copied down from the landscape mockup's pan/edge-scroll/zoom, with the ground-follow and band-pitch logic stripped since this mockup has no terrain. The root auto-pans the camera to a pan target on every regenerate, keeping whatever height was last set: for every kind except escort_to_extraction the target is the objective's own position; for escort_to_extraction it is the point 75% along the rendered route toward the objective end, so both the marker and a long stretch of the route trail land in frame at tactical zoom (a route can run several thousand wu longer than the frame at height 3000, so no single point shows all of it — see "Design points" below). `qa_camera_at_objective(height)` lets a QA script jump the camera onto the current objective at an arbitrary height without hardcoding a world position.

**hud.gd** is the archetype dropdown, seed spinbox, Regenerate/Tick+50/Play controls, the objective line with an ASCII progress bar (`#`/`-`, JetBrainsMono), a satisfiable readout (route length, time limit, skipped-candidate list), and the minimap. `qa_set("kind", ...)` (QA-only, no dropdown entry) forces the objective's kind independent of the selected archetype, used by `qa/smoke.json` to get a fifth, genuinely-distinct kind exemplar since R-073-01's Round 1 table never selects `survive_duration` on its own.

## Bugs found and fixed along the way

Two real bugs surfaced only under the Xvfb/llvmpipe QA path during the original build, not headless:

1. **Camera never marked `current`.** The lone `Camera3D` node never had `current = true` set; nothing in the 3D view rendered at all until this was added.
2. **`places.gd`'s node-drawing spec was never implemented.** `map_zoom.png` was a bare plane with only the mission marker until commit `24384ec` added the missing box+label per node.

Two harness-level bugs (not this mockup's code) were chased and fixed upstream mid-session during the original build, both merged from `main`: Xvfb's screensaver blanking the window after 600s of a slow run (`a98c47f`), and `SimBridge`'s dead-pid error route fading the screen and freeing the mockup mid-script even under `qa_boot.gd`'s script-mode boot (`b65afa8`).

## Fix pass (2026-09-22, second session)

Six items from the fresh-eyes review, each reproduced with a screenshot or pixel sample before the fix and re-shot after:

1. **Label3D text invisible.** Root cause exactly as the review predicted: `markers.gd` and `objectives_mockup.gd` set `font_size` but left `pixel_size` at the Label3D default of 0.01, so 64px (marker) and 40px (place) text rendered under 1wu tall on a 24,000wu canvas — not an Xvfb/headless limitation, a real bug. Fixed: `pixel_size` 2.2 on the marker label, 1.6 on place labels, tuned by screenshot at the tactical camera height (3000). First attempt at 6.0/1.6 (a naive canvas-ratio scale from the galaxy/fog mockups' own values) badly overshot — text dominated and overlapped the whole frame — so both were retuned down against an actual capture. Added `LABEL-12`: every `Label3D` in the scene must have `pixel_size >= 0.5` and non-empty text.
2. **`map_zoom.png` showed only the HUD.** The smoke script's `qa_camera 12000 12000 12000` was a fixed survey point independent of which archetype/fixture was loaded. Added `qa_camera_at_objective(height)`, which pans/zooms onto the current mission's own position; `map_zoom` now uses it and the ring, glyph, and label are centred in frame.
3. **Destroy-targets colour and escort route framing.** Checked the destroy-targets scatter/glyph material directly: already `StandardMaterial3D` unshaded with the kit orange (`KIND_COLORS.destroy_targets`), and a clean re-run pixel-samples bright orange (`rgba(255,140,50,1)`) at both the glyph and the scatter boxes — no code defect found; the "near black" read in the fresh-eyes review was almost certainly the same stale/contention capture as the background gradient (see item 4). The escort route framing was real: the camera panned to the extraction node, one end of a route that can run several thousand wu longer than the visible frame at height 3000, so most of the trail sat off-screen. Fixed by panning to a point 75% along the route instead (see "Design as built").
4. **Grey background gradient.** Tested the review's sky-bleed hypothesis directly: switched `background_mode` from 2 (Sky) to 1 (Color, `#0A0D12`) and diffed a matched screenshot against the Sky-mode version — 0.000069, noise floor, no visible difference. The camera never leaves pitch -90 in this mockup, so the sky is never actually in frame under either mode. The gradient itself did not reproduce on any clean re-run this session, at any camera height, under either background mode — most likely a stale or contention-era capture (the original build session ran under up to 8 concurrent `godot` processes and 7+/8GB swap). Kept flat Color since it's simpler and the procedural sky buys nothing here; noted which mode was kept and why.
5. **Fifth kind exemplar was a duplicate.** `defensive_stand` and `multi_front_defense` both resolve to `hold_zone` at the same `objective` node, so those two shots were pixel-identical (`diff` 0.000683, below the 0.01 candidate), and R-073-01's Round 1 table never selects `survive_duration` on its own. Added `qa_set("kind", ...)` (see "Design as built") and swapped the smoke script's fifth exemplar to a hand-forced `survive_duration`; all five `KIND-X` pairwise diffs now clear 0.01 (0.019-0.031).
6. **HUD progress bar glyphs.** `▮`/`▯` rendered half-tofu'd: JetBrainsMono has the filled block glyph but not the light one, so "done" cells were fine and "remaining" cells were missing-glyph boxes even after applying the font. Switched to plain ASCII (`#`/`-`), which every font renders, and kept the JetBrainsMono override for a consistent monospace look.
7. **Node-box claim re-verified.** The fresh-eyes review said `kind_defensive_stand.png`'s node boxes were "not borne out by the file" — true of that specific (stale) capture. A fresh re-run at both 720p and 1080p shows 3 named gray boxes ("objective", "chokepoint" x2, "extraction") clearly near the ring; `pass1/kind_defensive_stand.png` is the current proof.

See the fix-pass items above for what changed to get there.

None of the five Round-1 kinds needed `transit`, so this didn't block anything here, but it means the "one generator, nine node types" claim is currently aspirational for that one type.

The skip path only fires under the synthetic ROUTE-6 test fixture and the fault-injected plants.
4. **Frame time under llvmpipe at 720p; generation time.** `timing_ms.gen` 22.5-29.3ms (budget 200ms). `fps_ms` 100.4-170.4ms/frame this session (a quieter machine than the original build session, which saw 198-310ms/frame under heavy concurrent load).

## Questions for Westley

Both bugs that needed your Forward+ seat in the first pass turned out to be reproducible and fixable from the Xvfb captures alone — see "Fix pass" above. Nothing outstanding needs your eyes before this mockup can be judged from `pass1/`.

Design points I did not decide, each with two or three candidates:

1. **Time-limit scaling for a walkable mockup** (the brief itself flagged this as under-defined). Built: base `B = 350` ticks flat for every archetype (not varied by canvas tier), scaled x20 for the mockup. Candidates: (a) keep it flat as built — simplest reading of the brief's own text; (b) scale `B` by the archetype's `canvas` field via the Q-076-01 band (small=250, medium=350, large=450); (c) ask you for the real per-archetype base minutes once Q-076-01 itself is answered.
2. **Escort route rule and camera framing.** Built: the real A* path (over the same blocked-cell grid used for satisfiability) drives the actual satisfiability check and the rendered route's *shape*; a small seeded lateral jitter (+-80wu on interior points) is layered on top purely for visual variety and to give `mission_hash` seed-sensitivity, without touching the satisfiability math; the camera now pans to 75% along the route toward the objective. Candidates: (a) keep as built; (b) drop the cosmetic jitter, accept the escort archetype is visually seed-invariant like hold_zone (would drop SEED-2 below its 6/10 floor unless something else changes); (c) if the landscape generator ever produces more than one `extraction` node, let seed choose among them instead of jittering; (d) for the camera, a route this long at tactical zoom fundamentally cannot show both endpoints at once — a real build might want a "zoom to fit route" camera move instead of a fixed height, which this mockup's fixed-height smoke script doesn't attempt.
3. **How secondaries would show.** Round 1 has none (`docs/legacy/mvp/feature_mvps.md`'s E-10 block); nothing was built for this. Candidate for whenever it's needed: reuse `mission_marker.gd`'s own precedent — `SECONDARY_COLOR` (dimmer gray-blue), smaller glyph, no beam.
4. **Marker's look at the far band.** At the map zoom band (height 12000), the ring/glyph/label are now confirmed legible in frame (`pass1/map_zoom.png`); the place-node boxes and labels shrink similarly but stay readable. Whether it stays legible all the way to this mockup's true max zoom (20,000wu) wasn't separately shot for `pass1/` and is worth a look.
5. **Kind coverage for Round 1's ten archetypes.** R-073-01's table only ever produces 4 distinct primary kinds across the 10 archetypes (hold_zone x4, destroy_targets x3, eliminate_force x2, escort_to_extraction x1); `survive_duration` never appears from the table alone. `mission_gen.gd` fully implements survive_duration's placement and tick logic (it's one of the five kinds R-075 defines); this pass added a QA-only `qa_set("kind", ...)` override so the mockup could still show it, which is a test-harness workaround, not a real fix to the archetype table. Candidates: (a) accept 4-kind coverage from the real archetype flow for Round 1, survive_duration demonstrated only via the QA override; (b) treat this as a sign `multi_front_defense` (currently "hold_zone x2", simplified to a single hold_zone for Round 1) was meant to be the survive_duration representative — this would contradict R-073-01's literal table, so not chosen; (c) ask whether Round 1 wants an eleventh, synthetic archetype purely to exercise survive_duration through the real flow.

## Mockup review 1 fixes (2026-09-22, third session)

**1. Edge scroll dead on the right and bottom.** Confirmed with prints at `--res 2560x1440` before touching anything: `get_viewport().get_visible_rect().size` reports the fixed 1920x1080 base canvas regardless of window size (`canvas_items`/`expand` keeps canvas units constant; the window just changes pixel density), while `camera_rig.gd`'s old bounds came from `DisplayServer.window_get_size()` = `(2560, 1440)`, real pixels. Right threshold needed `mouse.x > 2500`; mouse never exceeds ~1920 in canvas units, so it never fired. Bottom needed `mouse.y > 1380` against a ~1080 max — same story. Left/top compare against a small constant (60) near zero, which reads the same in either space, so they worked, exactly matching Westley's report.

A second, harness-only defect surfaced while proving the fix: `get_viewport().get_mouse_position()` (the polling call the old code used every frame) never updated across four distinct `qa_driver.gd` `move` verb calls in the same run — it stayed pinned at the value from the driver's own boot-time "kill edge scroll" motion the whole time (127 frames, verified via a temporary debug print, removed before the real fix landed). It tracks the real OS/Xvfb cursor, which `Input.parse_input_event()` (what `move` uses) never actually moves. The event delivered to `_input(event)` carries the correct, already-canvas-transformed position on every synthetic move (confirmed: raw `(2540, 720)` at window 2560x1440 arrived at `_input` as `(1905.0, 539.9999)`, exactly the `0.75 = 1920/2560` scale). Fix tracks `_mouse_pos` from `_input()`'s `InputEventMouseMotion` instead of polling, which is both correct in real play (Godot always delivers `_input` mouse events pre-transformed into viewport-local units) and provable by the QA driver. `_edge_scroll_dir(mouse, bounds)` is now a pure, directly testable function; bounds is `get_viewport().get_visible_rect().size`, the same space `_mouse_pos` lives in.

Proof at `--res 2560x1440` (`qa/edges.json`, camera parked at `(12000, 12000)`): move to `(2540, 720)` -> `camera.x` `12000 -> 13550`; move to `(1280, 1420)` -> `camera.z` `12000 -> 13550`; move to `(20, 720)` -> `camera.x` `13550 -> 12000`; move to `(1280, 20)` -> `camera.z` `13550 -> 12000`. All four edges pan; `errors.txt` count 0. Headless companion `verify.gd` `EDGE-13`: a centred mouse (same space as bounds) does not pan, and a mouse at `bounds.x - 10` / `bounds.y - 10` does, in that same space — passes under `--headless`, where `DisplayServer.window_get_size()` is degenerate `(0, 0)` and can't stand in for a real window.

**2. Regenerate did nothing.** `hud.gd`'s `_on_regenerate_pressed()` called `qa_seed()` with the seed spinbox's own unchanged value, so R and the button rebuilt the identical mission every time. Reproduced first: seed 11, `defensive_stand`, state before `key R` and two states after -> `hash` `2014373198` all three times, `regen_count` climbing (2, 3, 4) proving the handler *did* fire, just with the same seed. Fixed by bumping the spinbox by one before calling `qa_seed(n)`; `qa_seed(n)` itself is untouched (still exact, still what the `seed` verb and `qa/smoke.json` use). Re-ran the same repro: seed now reads 11, 12, 13 across the three states, and hash changes for a seed-sensitive archetype (`siege_breaking`: `3289694821` at seed 11 -> `2334985817` at seed 12). Note `qa/smoke.json`'s own `after_r` checkpoint uses `defensive_stand` (`hold_zone`), one of the four archetypes documented above as deliberately seed-invariant (same single "objective" node regardless of seed) — so `after_r`'s `hash` staying at `3757886768` while `seed` advances `12 -> 13` and `regen_count` advances `10 -> 11` is the correct, expected post-fix reading, not a residual bug; `qa/checklist.md` records both numbers.

**3. Edge-scroll coordinate-space survey of the other five mockups (read-only, not edited this pass).** All six mockups' `camera_rig.gd` files (`fog`, `hud`, `landscape`, `layers`, `objectives`, `units`) poll `get_viewport().get_mouse_position()` for edge scroll. Which bounds they compare it against:

| mockup | bounds source | shares the defect |
|---|---|---|
| `scenes/mockups/fog/camera_rig.gd:41` | `DisplayServer.window_get_size()` | yes |
| `scenes/mockups/hud/camera_rig.gd:30` | `DisplayServer.window_get_size()` (also used, unrelated to edge scroll, for aspect ratio at line 58) | yes |
| `scenes/mockups/landscape/camera_rig.gd:89` | `get_viewport().get_visible_rect().size` | no |
| `scenes/mockups/layers/camera_rig.gd:41` | `get_viewport().get_visible_rect().size` | no |
| `scenes/mockups/units/camera_rig.gd:39` | `get_viewport().get_visible_rect().size` | no |

`fog` and `hud` need the same bounds-source fix as `objectives` did; `landscape`, `layers`, and `units` already compare in the same coordinate space the mouse position is in, so a window bigger than the 1920x1080 base canvas should not dead-zone their right/bottom edges. None of the five were touched this pass — each gets its own pass if Westley reports the same symptom there. All five still poll `get_viewport().get_mouse_position()` rather than tracking it from `_input()`, so the same harness-testability gap (provable only with a real OS-level mouse move, e.g. `xdotool`, not the QA driver's synthetic `move` verb) applies to them too; not a play-time bug, since real hardware motion does move the real cursor those calls read.
