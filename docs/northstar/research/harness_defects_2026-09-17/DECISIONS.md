## R10 (2026-09-20): three dead controls, one mechanical check that catches all of them

R7h, R7l and R9 are the same failure with three different causes: a positive control that cannot tell the correct implementation from the planted bug. R7h could not observe in time (the reading step runs before the mutating step). R7l's own numbers never reached the branch it tested (the clamp never engaged, so both orders gave 31.3). R9's reorder changed nothing observable, because the write it reorders is synchronous (verified by the executor with two independent scenarios, not argued). Each cost a card its full attempt budget and a human diagnosis; each was found by hand, after the fact.

PX-13 built detectors for the first two, and they work, but they read docstring and naming conventions, and they would not have caught R9 at all.

**The check that catches all three, mechanically and without conventions: a control must be able to fail.** Run each control against the clean build and against the debug build with its own `OM_BUG_*` injected. If the outcome is identical either way, the control is dead, whatever the cause. This is Principle 3 ("every detector ships with a positive control") applied to the controls themselves, and it is cheap: both libraries are already built, and a control run is a fraction of a second.

Decisions:
1. **Control liveness becomes a gate**, not a lint: a control that does not flip between the clean and injected builds fails the story's Definition of Done and blocks its card from queueing. It runs in the CPU slot with the rest of the pre-queue checks.
2. PX-13's tick-order and vacuous-numbers detectors are **kept as diagnostics**: they say *why* a control is dead, which is what a human or the escalator needs in order to fix it. Liveness says *that* it is dead.
3. A dead control is a `test-defect` under C6, split per PX-18's own result: a filter fix, a guard fix, or a single number the fixture needs (PX-13 already computes the distinguishing value for the vacuous class, e.g. military 15.0 for R7l) goes to the escalator under the test-fix gate; a scenario that must be re-derived from the rule text goes to Claude's test-authoring ledger instead. Westley is involved only when the test-fix gate itself flags the change (a widened tolerance or threshold).
4. `OM_BUG_*` ids whose control is dead are not evidence of anything; the epic's "ways this could be wrong" item they came from is still unproven and stays open.

## R12 (2026-09-20): a repaired test silently kills the control that copies its detector

After R11 landed, the liveness gate was re-run on `test_control_osc_as_level` and reported `DEAD` again, with a different symptom: before the fix both runs failed, now **both runs pass**. Cause, verified: the control's docstring says it "reuses the exact detector" from `test_E02_S018_oscillation.py::test_R_018_04`, and it does, by copying the loop. That test was repaired earlier the same night (`93b9525`) to start its window at `k=1`, because window `k=0` is off by `A*sin(econ_phase)` for every implementation, correct or buggy, from how ALG-01 seeds the previous-tick value. The control still loops from `k=0`, so it trips on the clean build as well and can no longer distinguish anything.

The failure mode is general and new to the table: **a control that copies a test's detector goes vacuous the moment that test is repaired**, silently, with no failing test anywhere to announce it. The drift check already designed covers epic to spec to test; it does not cover test to control.

Decisions:
1. A control that mirrors a test's detector declares that link **machine-readably**: a module-level constant (`MIRRORS = "tests/csim/test_E02_S018_oscillation.py::test_R_018_04"`) or a pytest marker, never only a sentence in the docstring. Importing a shared detector is better where the shared surface is worth the indirection, but that is a judgement per control: when the executor fixed this one (`1f81182`) it kept the copy, reasonably, because the shared part was a single loop line. Copies are allowed; undeclared copies are not, because the drift check in decision 2 can only find what is declared. Grepping docstrings is the convention-dependence PX-13 already named as its own weakness.
2. The drift check extends to test-to-control pairs: changing a test file requires re-running liveness for the controls that mirror it, in the same commit.
3. This is the first defect the liveness gate found on its own, hours after an unrelated repair created it, with nobody looking. That is the argument for running it as a gate rather than a diagnostic.
4. The fix itself is a `test-defect` under C6: the executor session repairs the control to match the repaired detector; Westley is not involved. Done in `1f81182`; liveness now reports `LIVE` for it ("as-written=passed, neutralized=failed").
5. `test_control_composite_pre_clamp` remains the one dead control in E-02 (both runs fail on its own guard assertion before reaching the injected check). It is a `test-defect` awaiting the same treatment, tracked here so it is not mistaken for a passing control.
