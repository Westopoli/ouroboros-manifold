## CAN_ENGAGE

The engine has no single per-tick order. Acquisition tests range first then sight (`om_tac_nearest_actable` `unit.c:2006-2010`; cross-layer `om_tac_pick_across` 1751-1752: `om_tac_in_range` then `om_tac_may_act_on`); the held-target check tests sight first (`unit.c:2139`) then reach, stealth, range (2143); the fire pass tests alive, `om_tac_in_range` (which folds reach in, 1716-1719), cooldown-or-first-shot, `om_combat_can_shoot` (2259-2262) and never rechecks sight. All are conjunctions, so parity needs only the boolean; the order is a diagnostic choice and the spec must say so. Recommended order (what the unit cannot change by moving first): **1 out of reach, 2 not seen by the side, 3 out of range at this offset, 4 outside the arc, 5 line blocked.** The spec's order (range before seen) is acceptable if it states it is diagnostic, not the engine's.

Lines to add:
- "Not seen by the side" is the engine's `om_tac_faction_sees` (`unit.c:1165-1169`: stealth, own sight, then `om_fog_faction_sees`), and `om_fog_faction_sees` includes live ping discs (`fog.c:486-501`, `om_fog_ping_reveals` at 500). It is applied only when `OM_TP_TARGET_BY_SIGHT` is 1 (`om_tac_may_act_on` 1178), but a stealthed target is refused at either switch value (`unit.c:2143`), so reason 2 = `t->stealth || (by_sight && !faction_sees)`. Note the lab's composed count uses `om_player_can_see` (spec line +37/2), which differs from the engine when player fog is explicitly off (`fog.c:614`, omniscient) and ignores the stealth flag; the parity check must run with fog on.
- Return -1 (never a reason code) for: unknown id, dead attacker, dead target, same faction or neutral (`om_tac_hostile` `unit.c:1695`: either faction < 0 or equal), attacker == target, non-combat attacker (`om_tac_noncombat` 1699: Supply, Evacuation).

- Parity statement: for every `OM_TAC_EV_FIRE` event on tick t, `om_combat_can_engage(attacker, target)` queried after tick t returns 0 or -1-with-target-dead (the fire pass uses post-movement positions, `unit.c:2250` `om_tac_refresh_positions`, which are the end-of-tick positions). ## ARC

- **Gate: fire only, never acquisition or hold.** The face pass turns a unit toward its *engaged target* when within 1.5 x range (`tactical_move.c:2320-2326`, "a stationary unit that is firing turns too", 2312); with no target it faces its heading. If acquisition were gated, a flanked unit would never acquire, never turn, and ruling 8 (a) could not happen. Gate on fire gives exactly the ruling: acquire, hold (`om_tac_hold` 1921, engaged so stationary, `om_move_is_stationary` `tactical_move.c:1096`), turn at the category rate, fire once inside; `om_combat_can_engage` reason 4 reads "outside the arc" meanwhile. Line to add: the hold decision (`unit.c:2235-2242`, `!in_range || !om_combat_can_shoot`) does not consult the arc; a unit stops for a target it must turn to.
- **Return fire (R-087-06, `unit.c:2095-2117`)** is acquisition, so untouched; the shot waits for the turn. Add the line.
- **Guard (R-096-08)** acquires through the same scans (its only special case is no pursuit, `unit.c:2143`), so a guard turns and fires inside its post; add the line. - **Moving unit:** the face pass prefers the engaged target within 1.5 x range over the heading (2320-2331), so R-100-01's "faces heading when moving" applies only without a target in that band; an attack-mover with a target in range is held anyway. Add the line. Also: a kiting unit (attack-target in range) snaps its facing at the target with no rate cap (`tactical_move.c:2213`), so the arc never bites under attack-target; state that the arc is felt by attack-move, guard, idle and return-fire units only.
