# A3 — Long-Horizon Coherence for a Card-Based Factory

The Factory already has real evidence of the failure mode this memo is about: on 2026-09-18 the executor chat cut cards 204-207 "by rule pair" and six of them failed a mechanical lint (`SPANS_ANOTHER_CARD`) because their tests reached stub functions owned by other, later cards (`docs/northstar/research/harness_defects_2026-09-17/DECISIONS.md`, "Third round" section). Card 203b2 was marked satisfied while the function it actually owned, `om_pending_telegraphs`, stayed a stub. This is architecture-drift-by-construction, and it happened inside one afternoon, not months. The questions below are about keeping a 21-epic, years-long build from producing that at scale.

## 1. What Anthropic's own harness and context papers prescribe

Anthropic's "Effective harnesses for long-running agents" (https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) splits the agent into an **initializer** (runs once, generates a JSON feature list of 200+ items each marked pass/fail with steps, writes `init.sh`) and a **coding agent** (every subsequent session, works exactly one feature, updates only that feature's status, writes `claude-progress.txt` for the next session). The coherence mechanism is structural: JSON instead of markdown specifically because free-text is where an agent "improves" scope unasked; git commits plus the progress file are the cross-session memory bridge. Reported failures: agents declared victory before all features passed, left half-implemented features with no note for the next session, marked features done without end-to-end testing (bugs invisible to code review), and — absent the explicit feature list — tried to build the whole app in one shot and burned context before finishing anything.

"Effective context engineering for AI agents" (https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) prescribes compaction (summarize near the context ceiling, reinitialize from the summary — with the explicit risk of "the loss of subtle but critical context whose importance only becomes apparent later"), structured external note-taking (a NOTES.md-style file outside the context window), and sub-agent fan-out where a lead gets a condensed 1,000-2,000 token report, not the sub-agent's transcript. It is explicit this is task-dependent tuning, not a solved problem, and claims no month-scale answer.

Our closest analogue to the feature list is `RELEASE_CHAIN` in `next.py` (169 build cards, E-03..E-17) plus `campaigns/todo/*.jsonl`; our closest analogue to the progress file is `report.md` + `candidates.jsonl` per card and the `.swarm/*/REPORT.md` cascade logs. We already have the JSON-not-markdown instinct in `cascade_types.py`'s frozen dataclasses (`CheckResult`, `GateResult`, `Outcome`).

## 2. Documented coherence decay in other long-run agent systems

The Ralph Wiggum loop (Geoffrey Huntley, May 2025) is the closest published analogue to a bounded-card, fresh-context, model-writes-a-slice loop: "each iteration may 'fix' the immediate error while introducing architectural drift, and over time, the codebase becomes internally inconsistent with different modules making different assumptions," because "generated code reflects the agent's path to a working state, not an intentional structure" (https://tessl.io/blog/unpacking-the-unpossible-logic-of-ralph-wiggumstyle-ai-coding). No numeric measurement is given; the claim is qualitative, from practitioner logs.

ChatDev and MetaGPT are the multi-role precedent (specialist roles, staged artifacts), but the sources found report quality/executability scores, not coherence-decay curves — MetaGPT's generated tests were only ~80% accurate on HumanEval, and executability scored 3.75/4 for MetaGPT vs 2.25/4 for ChatDev on SoftwareDev (https://arxiv.org/html/2307.07924v5). Neither isolates architecture drift as its own metric.

Two 2026 benchmarks fill the measurement gap directly. SlopCodeBench: "structural erosion increases in 77% of trajectories while verbosity increases in 75.5%," agent output is "2.0x more structurally eroded and 2.3x more verbose" than a baseline of 473 real Python repos; better initial prompts cut starting erosion up to 62.3% but "do not stop iterative degradation" (https://arxiv.org/pdf/2603.24755). SWE-EVO benchmarks long-horizon evolution (avg. 21 files touched, 874 tests/instance) and finds OpenHands scoring 25% versus 72.8% on ordinary SWE-bench — sustained multi-file coherence, not single-patch correctness, is the bottleneck (https://arxiv.org/html/2512.18470v5). Voyager's skill library (https://arxiv.org/abs/2305.16291) sidesteps duplication via semantic-similarity retrieval from a vector store rather than preventing duplicate authorship outright; no explicit dedup mechanism surfaced in the sources, so this is a partial answer, flagged rather than asserted.

## 3. Practices that hold a weak-model, bounded-task codebase together — what we already run

We already run several of the textbook practices, traceable in-repo:

- **Contract files, parent-locked / leaf-owned.** `csrc/om_internal.h` (private struct layout) and `scripts/cascade_types.py` (frozen dataclasses `Outcome`, `GateResult`, `CostRow`) are read by every card but only Claude/cascade-foundation changes their shapes; `build.py:809` notes the model "invents member" layouts without this file. `cascade-foundation`'s DECOMPOSITION.md names this as a pattern the manager-mode template has no slot for ("contract parent-locked for signatures, leaf-owned for bodies") and recommends the skill absorb it.
- **A pinned cross-leaf interface table**, written once per decomposition, naming exact signatures two shards must agree on before either is built (`.swarm/cascade-foundation/DECOMPOSITION.md`). Cost: one pass per cascade wave. Evidence it's imperfect: `REPORT.md` still logged three cross-shard schema mismatches (controls row schema, TRUST row schema, tz-awareness) that slipped past the table, caught only by a live post-admission smoke run, not the 110 passing unit tests — the report recommends a mandatory "pinned seams" table with exact field names/types/example rows plus a fixture per seam.
- **Mechanical dependency-map linting before queueing** — `card_lint.py` statically walks a card's acceptance-test AST, collects every `om_*` symbol reached (through `conftest.py` helpers too), resolves each to the `.c` file defining it, and fails the card `SPANS_ANOTHER_CARD` if that symbol is a stub outside `allowed_files` (`card_lint.py:305-368`). Runs per card, zero cost, before any model call — "no new helper without a name check," structurally enforced. Documented blind spot: "it sees STUB markers, not functional incompleteness" (`DECISIONS.md`, R4) — card 207 read clean while three E-05 controls actually failed.
- **Periodic architecture-review by the strong model.** The three DECISIONS.md rounds (2026-09-17/18) are this in practice: Claude re-cut E-05's remaining cards by file-and-algorithm-family after the rule-pair cut failed, and R2 moved struct-field additions into a parent-owned `om_internal.h` patch because "a one-file card cannot add struct fields." Cadence so far is reactive (six lint failures forced it), not scheduled.
- **Invariant suites run whole, not per-card.** Q7 (DECISIONS.md, second round) adds `kind: gate` cards running a story's whole test file plus the epic's scale/speed gate together, no model call, green-passes/red-escalates — because per-card isolation tests can each pass while story behavior regresses, which is exactly what happened when 203b1's candidate silently broke 203a1's acceptance test. Caught only because `build.py`'s new `finalize_pass` now re-runs every DONE predecessor's acceptance sharing a `snippet_file` before finalizing (Q1, "Done, agora `finalize_pass`, six tests").

Not yet run: a scheduled (vs. incident-triggered) review cadence, a repo-wide duplicate-helper/dead-code scan, or a convention linter beyond `card_lint`'s symbol/stub check.

## 4. An archive of attempts, kept thin

Darwin Gödel Machine (https://arxiv.org/abs/2505.22954) keeps an open-ended **archive of full agent variants** (not just successes) so a later search can branch from an "interestingly new" but not-yet-best ancestor rather than hill-climbing off the current best — this took it from 20.0% to 50.0% on SWE-bench. Dream-RSI (https://arxiv.org/abs/2609.14858) keeps a **discovery tree of past exploration traces** and replays it as a cheap offline simulator to evaluate candidate strategies without new online calls, cutting discovery-agent calls up to 162x (https://venturebeat.com/orchestration/googles-dream-rsi-cuts-discovery-agent-calls-up-to-162x-by-replaying-searches-it-already-ran).

We already keep the raw material: every run directory under `agora/runs/<card>-<timestamp>/` holds `candidates.jsonl` (one line per attempt — model, rung, think mode, passed/failed counts, `failing_ids`, `body_lines`, `diff_sha`, `wall_s`) and `reply-N.md`. For a 30B local model with no training loop, the DGM/Dream-RSI idea shouldn't become "retrain a policy" — it should become an **offline, read-only strategy chooser** `next.py`/escalation consults before a fresh rung: given a card's `snippet_symbol`/algorithm-family tags, look up prior `candidates.jsonl` rows for similar cards and surface which rung/model/think-mode reached DONE last time, plus which `failing_ids` pattern predicted a stall. No vector store or fine-tuning needed — a flat scan by tag, cached, is enough, and it targets the escalation ladder's 2-run/9-run/10-run structure directly by skipping a rung the archive shows is futile for this shape rather than burning it. Keep only `diff_sha` + `failing_ids`, not full reply text, to stay thin.

## 5. Cutting cards along code-ownership seams, and catching a bad cut before queueing

The failure already diagnosed (DECISIONS.md, Third round) is precise: cards were cut by **rule pair** (R-034-05 + R-034-06 style), which is a requirements-document seam, not a code seam, so a card's acceptance test routinely called through a function another card owned. The fix adopted (R1) re-cuts by **file and algorithm family** — one file, one algorithm, matching the sizing contract's own "Algorithm Family Isolation" rule (`docs/northstar/PLAN.md:215`) that the rule-pair cut had been violating in practice even though it satisfied it on paper. The decomposition rule should read: *a card's boundary is the smallest (file, top-level function or function family) pair whose acceptance test's transitive symbol closure stays inside that pair* — not "the smallest set of Given/When/Then rules that fit the line budget." Rule pairs remain the *content* unit (what the card proves) but the *file* is the cut unit.

`card_lint.py` is already most of "detect a bad cut before it's queued": AST-walk the acceptance node ids, resolve every `om_*` symbol via `find_symbol_definitions` against `csrc/*.c`, fail on any symbol whose only definition is a stub outside `allowed_files` (`card_lint.py:305-368`). What it doesn't check, per R4's blind spot, is *functional* completeness of a symbol already inside `allowed_files` — card 207 passed lint while three controls failed because the symbols existed but weren't wired to the needed behavior. Closing that gap needs one more cheap check: does the acceptance closure cover every symbol the *epic's* positive controls for this story require, not just this card's own declared rules.

## Open questions for Westley

- **Q-A3-01 — Architecture-review cadence.** Right now the strong-model review of card cuts is triggered reactively (six lint failures forced the E-05 re-cut). Candidates: (a) leave it reactive — a scheduled review is Claude time we don't have and the lint catches most of it cheaply; (b) one review pass per epic, at Stage 4 exit, before its cards enter `RELEASE_CHAIN`; (c) one review pass every N cards merged (e.g. 20), regardless of epic boundary, to catch drift accumulating within an epic's own card set.
- **Q-A3-02 — Archive retention window.** `runs/` already keeps every attempt indefinitely (visible in the `_archive_202b2_pre_gemini_switch/` and `_archived-*` directories). Candidates: (a) keep forever, it's cheap (jsonl + diffs, no video/logs) and is exactly the DGM/Dream-RSI raw material; (b) prune `reply-N.md` bodies after N days but keep `candidates.jsonl` rows forever, since the memo's answer to Q4 only needs the row, not the prose; (c) prune per-card once its story reaches Built and its gate card is green, on the theory that a Built story's attempt history stops being useful strategy signal.
- **Q-A3-03 — Where the "control-completeness" lint check lives.** Closing card_lint's R4 blind spot (functional completeness against R4 controls, not just symbol existence) could be: (a) an extension to `card_lint.py` itself, keeping one tool; (b) a separate `control_lint.py` run only at story-gate-card authoring time, since it needs the epic's R4 list, not just one card's frontmatter; (c) folded into the `kind: gate` cards' own red-state (a gate card that's red for a "wired but not functional" reason already tells you this, just late — the question is whether catching it before queueing is worth a second script versus catching it at the gate, which we already pay for).
