# A7 — Multiplayer Determinism and QA

## 1. What breaks determinism in practice, and how projects detect it

Lockstep RTS/strategy games (Factorio, Age of Empires, StarCraft) send only the command stream, not state, so every peer must compute byte-identical results from identical inputs. Factorio's own writeups describe the mechanism directly: a CRC of the full game state is computed and compared across all players every tick (configurable interval), and any mismatch is reported as a desync, at which point the desynced peer is auto-reconnected and re-downloads the map state ([Friday Facts #47 — CRC fun](https://www.factorio.com/blog/post/fff-47), [Desynchronization — Factorio Wiki](https://wiki.factorio.com/Desynchronization)). Their replay tooling then re-runs the same input log and CRCs every tick against the original recording; the first tick where the replay's CRC disagrees with the original pins the divergence point, and developers diff human-readable save state at that tick between the two builds. This is exactly the "divergence bisection by tick" pattern this project should adopt: periodic full-state hash plus a replay log that can be re-run and CRC'd tick-by-tick to localize the failing tick before diffing state.

The concrete causes of divergence, per Factorio's history and the classic lockstep literature ([Gaffer On Games, Floating Point Determinism](https://gafferongames.com/post/floating_point_determinism/); [SnapNet, Netcode Architectures Part 1: Lockstep](https://www.snapnet.dev/blog/netcode-architectures-part-1-lockstep/); [Bugnet, How to Debug Desync in Deterministic Lockstep Games](https://bugnet.io/blog/how-to-debug-desync-in-deterministic-lockstep-games)) are: (a) compiler fast-math/reassociation optimizations changing operation order or fusing multiply-add; (b) x87 80-bit extended precision vs. SSE fixed-width precision producing different rounding on the same expression; (c) AMD vs. Intel (and libm vs. libm) disagreeing on the last bit of transcendental functions (sin, cos, pow); (d) hash-map/set iteration order differing between runs or platforms and leaking into simulation order; (e) uninitialized memory read as a "plausible" garbage value that differs by allocator/OS; (f) peer message ordering — applying two peers' commands for the same tick in different order. A single-bit divergence at an early tick compounds into a completely different game state a few thousand ticks later (cited desync rates for shipped lockstep RTS titles run roughly 0.1–1% of matches even with mitigations in place, per the SnapNet piece above). CI practice at studios doing this seriously is a per-commit matrix that plays back a fixed recorded match (or a fuzzed command stream) on each target platform/compiler/arch combination and fails the build on any state-hash mismatch, i.e., exactly the trace-diff idea already named in `docs/northstar/research/c_rewrite.md` under "Determinism proof."

## 2. Gates the factory can run per card, cheaply

The repo already has the two cheapest gates. `tests/csim/test_E02_S020_determinism.py` runs `test_R_020_01_two_runs_same_seed_byte_identical` (repeat-seed, same-process, `memcmp` over trace rows) and `test_R_020_01_same_machine_checksum_repeat`; `tests/csim/test_E02_gate_drift_trajectory.py` additionally asserts the traced run's checksum equals the untraced run's checksum (traced vs. untraced equality, catching a trace hook that perturbs state) and a third independent build's checksum matches (repeat-seed checksum equality at 5,000-tick scale). `test_R_020_02_cross_platform_checksums_match` in the same file is an explicit `pytest.mark.skip`, documented as needing a real multi-OS CI matrix — this is the gate that does not exist yet. Missing entirely: cross-compiler equality (gcc vs. clang, both already candidates since forge has gcc and Phase 2 needs SCons/clang tooling per `docs/northstar/research/c_rewrite.md`), optimization-level equality (`-O0` vs. `-O2`, cheap to add since the Makefile already pins flags per `c_rewrite.md` "Determinism flags"), and 32-bit vs. 64-bit build equality (probably low priority unless a 32-bit target is ever shipped). All four of the missing gates are cheap: same test body as `test_R_020_01_two_runs_same_seed_byte_identical`, just invoked against a second `.so` built with a different toolchain/flag set and loaded via a second `ctypes.CDLL`. A per-card acceptance addition costs one extra Makefile target and one extra fixture parametrization, not new test logic. Cross-OS is the only one that genuinely needs infrastructure (Windows/macOS runners), and should stay a Track R item until CI exists, exactly as `c_rewrite.md`'s R-020-02 skip already states.

## 3. Hazards a weak implementer introduces, and static checks that catch them automatically

The three named hazard classes map to concrete C mistakes: hash/set iteration order (any `qsort` with a comparator that isn't a total order over the sort key, or reliance on pointer-value ordering, or a hand-rolled hash table walked in bucket order); wall-clock/entropy leakage (`time()`, `rand()`, `srand(time(NULL))`, reading `/dev/urandom`, or thread-scheduling-order-dependent code such as unsynchronized OpenMP reductions); uninitialized memory (a `malloc`'d struct field never set before being read into the checksum or the trace row — this is the exact class MSan exists for, since ASan does not catch it: "an uninitialized read stays inside a valid allocation so ASan is silent by construction... MSan tracks the initialization state of every bit of memory" per the sanitizer literature ([Fuzze.rs, Reading UBSan and MSan Reports](https://fuzze.rs/blog/reading-ubsan-and-msan-reports); [Red Hat Developer, Memory error checking in C and C++](https://developers.redhat.com/blog/2021/05/05/memory-error-checking-in-c-and-c-comparing-sanitizers-and-valgrind))). A card's automatic acceptance can bundle, cheaply, per build: `-fsanitize=undefined` (UBSan, catches signed overflow, misaligned loads, and — relevant to the checksum fold in `om_world_checksum` — undefined shift/overflow behavior) and a separate MSan build of the same test suite; a `grep`-based static ban on `rand(`, `srand(`, `time(`, `gettimeofday(`, and any bare `qsort(` whose comparator is not reviewed; and `-Wall -Wextra -Werror` plus `-Wfloat-equal` to flag accidental exact float comparisons. None of these require new test authorship, only wiring into the existing `make` targets `c_rewrite.md` already names (`libouroboros.so` / `libouroboros_dbg.so`), each run against the current `tests/csim/` suite.

## 4. Multiplayer QA as an R4 detector class

The existing R4 catalog (`docs/legacy/research/rts_bug_catalog.md`) already has a T1 desync-adjacent row — row 17, "Pause desync," T1, trace-detected. Desync itself belongs at T1 for the same reason: it is a state-trace fact, not a rendering fact. The detector is exactly what `docs/bible/epics/E-19-multiplayer.md` already specifies under S-139: run two `om_world` instances from the same seed, feed both the same command stream in the same fixed peer order, compare `om_world_checksum` every `om_checksum_cadence()` (10) ticks (R-139-03/04), and report the first differing checkpoint plus, on failure, diff the two `om_trace_row` arrays field-by-field to name the first differing region/field — this needs no rendering and no second Godot process, so it should run as a T1 pytest-via-ctypes test (two `world_factory` instances, one process) rather than spinning up two Godot/Xvfb clients. A positive control is a deliberately corrupted second instance (flip one bit of one region's state, or apply peer commands out of order) that must trip the checksum-divergence detector within 10 ticks per R-139-04. Latency/lag-compensation, join/leave, and replay-determinism are different detector classes that do need the transport and lobby layer (E-19 S-140/S-144, currently gated by open flags Q-140-01/02, Q-144-01/02) and are T2-appropriate once that layer exists — a T2 session there would need two real Godot clients, most cheaply as two headless (or Xvfb, single display, two windows) processes exchanging commands over loopback rather than the real Steam Datagram Relay, since SDR itself is out of scope for QA and only the lockstep contract needs exercising. The game-side hook that layer needs and does not yet have is a way for a driving harness to inject a "peer's command for tick t" without going through the real transport, and a way to force a checksum mismatch (or drop a peer's message) to test R-140-03's stall/drop path — none of this exists yet since S-140 is still an open flag.

## 5. Save/load and replay as QA evidence

A deterministic replay file (seed + full ordered command stream) is the cheapest possible regression test: record once during a real or synthetic session, then "replay forever" by re-running the same seed/commands through any future build and diffing the resulting trace or checksum sequence against the stored one — this is precisely Factorio's own regression practice, replaying old save+input logs through new engine builds and treating any CRC divergence as a regression ([Desynchronization — Factorio Wiki](https://wiki.factorio.com/Desynchronization)). For this project, a factory-found determinism defect should store, per finding: the seed, the exact command stream (or the fixed synthetic setup used by `_build_and_run`/`_build_60_region_world` in `tests/csim/test_E02_S020_determinism.py` and `tests/csim/test_E02_gate_drift_trajectory.py`), the tick number and field name of the first divergence, both `om_trace_row` values at that tick, and the checksum sequence up to and past the divergence point — enough for a human or a future agent to re-run the exact scenario without re-deriving it. Save/load determinism (R4 catalog: "save/load drift," "rewind divergence beyond design") is the same mechanism applied to `save_writer.py`/`save_loader.py`: save mid-run, reload, replay the remaining command tail, and assert the checksum sequence after reload matches the checksum sequence from an unbroken run over the same span.
