# A4 — Game QA as an Agora Plugin

## 1. Oracle taxonomy

Four oracle classes, distinguished by what they compare and when they can fire.

**State oracles** — one debug-port query checked against an expected value right after one action. This is `qa_oracle.evaluate` (`/home/westopoli/Projects/agora/scripts/qa_oracle.py:127-181`): for each present `EXPECT_KEYS` member (`url_path`, `role`, `text_contains`, `status`...) it reads one field and returns `expectation-failed` on the first miss, with `_evaluate_settled` (`specs/cascade-director.md` AC-8, `.../cascade-director.md:70-76`) retrying 3x/0.5s as the only anti-flake mechanism that exists today. Cost: one RPC round-trip (`docs/desktop-qa-protocol.md:25-48`). Flakiness: low once settled; near-certain without it (a point-in-time check racing an animating UI). Prior art: OSWorld's success functions read filesystem/app state directly with no LLM judge in the success path (https://benchmarkingagents.com/osworld/) — the same "read ground truth, compare structurally" shape. Catches: #4 dropped order (ack vs. state), #8 selection miss, #10 control-group loss, #21 layer elevation.

**Invariant/trace detectors (T1)** — a rule over a *window* of ticks, not one point. Ouroboros's own: `simulation/invariants.py` (2682 lines, 78 rule functions — "the ~75 invariants") and the C trace API `om_trace_enable`/`om_trace_read`/`om_world_checksum` (`csrc/ouroboros_sim.h:81-148`), checksummed every 10 ticks (`om_checksum_cadence()`, `:137`). Probe C already proved this class: `detectors/rts.py`, four detectors, five `MOVER_BUG` variants (clean/rubberband/stuck/backwards/dropped), 20/20 pass, fingerprints stable across seeds (`docs/legacy/proving_ground/PC-t1-detectors.md`). Deterministic, cheap, zero flakiness given a fixed seed and command stream — the class the bible's determinism contract exists to make possible. TITAN (arxiv.org/abs/2509.22170) frames this as "an oracle over game state"; GBQA's critic agent (arxiv.org/html/2604.02648) instead matches free-text reports against ground truth, strictly worse when the bug is visible in state. Catches: #1,2,3,5,6,7,10,12,13,17,22, and #21's T1 half.

**Metamorphic relations** — no fixed expected value, a relation between two runs instead. Three shapes: (a) same seed + a harmless action (save/load) should leave the trace unchanged — catalog #18, since "correct" is whatever the pre-save trace already was; (b) two seeds should diverge while a rewind-to-the-same-point should reproduce — catalog #19's two halves; (c) replay determinism itself — same seed, same command stream, byte-identical checksum across OSes — an MR over *machines*, the bible's own determinism contract (`CLAUDE.md` "Determinism is a contract"). Metamorphic-testing surveys (Chen et al., https://dl.acm.org/doi/10.1145/3143561) frame this as solving the oracle problem when no independent expected output exists — our exact situation for "is this stochastic outcome correct." Flakiness: zero if the sim is truly deterministic (a violation *is* the finding); cost is one extra full run per relation, no model calls. Catches: #17 (pause desync, same MR shape as (a)), #18, #19, plus determinism regressions the catalog doesn't itemize.

**Visual oracles (T2)** — a screenshot region plus a yes/no question to a vision judge, used only where the bug is invisible in state. `qa_desktop.py._after_action` already captures one screenshot per action (`:398-403`) but nothing reads them back — vision judgment is explicitly out of scope this wave (`specs/qa-desktop-backend.md:99-102,152-153`). playtest-agent (github.com/kevinnie2003/playtest-agent) pairs generic detectors with an LLM only for triage, not the primary check; VideoGameQA-Bench and GBQA both use a vision judge against a bug description. Flakiness is the highest of the four classes, so it should never solely gate a finding — use it to *propose*, then have a cheaper oracle reproduce; use raw pixel diff (not a vision call) only for golden-screenshot regression, which is deterministic and cheap. Catches: #8/#9 (cross-checked against state — see Q3), #11 camera jitter, #14 projectile miss, #15/#16 HUD desync (visual half), #20 (prefer a perf-log state read over vision), #21's T2 half.

Full catalog mapping: 1 T1, 2 T1, 3 T1, 4 state, 5 T1, 6 T1, 7 T1, 8 state+T2 (cross-check), 9 T2, 10 state, 11 T2, 12 T1, 13 T1, 14 T2, 15 T2 (state if HUD value is queryable), 16 T2 (state if queryable), 17 T1/metamorphic, 18 metamorphic, 19 metamorphic, 20 T2 (prefer perf-log state read over vision), 21 state+T2, 22 T1.

## 2. Actor design for a weak model

Scripted scenarios and personas come first, as playtest-agent found ("personas matter more than cleverness," github.com/kevinnie2003/playtest-agent) and as director mode already implements: DeepSeek writes a mission of concrete `Step`s (`cascade_types.Step:392`), a small local model ("toddler") executes one directive per turn via `ollama_client.chat_json` (`qa_director.py:135-138`), bounded to `ACTION_VERBS` chosen per-step (`allowed_actions`, `qa_session.guard_action`, `cascade_types.py:381`). The parent only escalates at checkpoints (`run_mission`, `qa_director_core.py:137-197`). This shape is right for a 30B local model and should not change.

Current vocabulary: `click, fill, goto, reload, back, submit`. For an RTS this is missing everything a real player does. Minimal addition set: `press` (keybind — half-exists as `DesktopPage.keyboard.press`/`_press_key`, `qa_desktop.py:153-159,394-396`, just not in `ACTION_VERBS`), `drag` (box-select/rally-point — needs a start/end coordinate pair the current `{role,name,value}` schema has no field for), `wait` (tick-stepping, below), `read_state` (an explicit state query as an action, distinct from `evaluate`'s pass/fail use), `screenshot` (explicit capture beyond the automatic per-action one). RTS-specific: `box_select` (drag+release triggering selection, not movement), `hotkey` (control groups, `ctrl+1..9` — `xdotool key --window <wid> ctrl+1` already supports this with no protocol change), `camera_pan` (camera state isn't sim state; catalog #11, #14 are camera-relative).

Pause-while-thinking is VideoGameBench's answer to slow inference in a real-time game: the emulator only advances when the model acts; even top frontier models clear only 0.48%/1.6% of the full/Lite variants (arxiv.org/html/2505.18134v3, vgbench.com). Ouroboros should adopt "Lite" directly: extend the debug port with a `pause`/`step <n>` pair so `wait` means "advance N ticks deterministically," not "sleep wall-clock time" — strictly better than VideoGameBench's own setting because `om_trace_read`'s tick-level determinism lets a session step exactly as many ticks as needed with zero timing flakiness. Step budgets and loop detection: cap actions at `profile.director["max_steps"]`/`checkpoint_every` (already exist), and add a state-hash loop detector — hash the `tree`/`state` reply after each action; N consecutive identical hashes despite distinct directives flags a stuck actor, the same shape as catalog #2 (stuck unit) applied to the actor instead of a unit.

Protocol extension of `docs/desktop-qa-protocol.md`: add `pause`, `step <n>`, `drag <x1> <y1> <x2> <y2>`, `hotkey <combo>` alongside `state`/`tree`/`nav`/`seed`/`screenshot`/`quit` (`:23-79`), same newline-JSON shape, "app answers what it can" — an app with no camera has no `camera_pan` handler, treated as a no-op the way `nav` on a single-route toy scene already acks unconditionally (`:55-58`). This stays product-agnostic: a web app or CLI profile never lists `hotkey`/`camera_pan` in `allowed_actions`, the same gate `_sanitize_steps` already applies to today's six verbs (`qa_director_core.py:56-68`).

## 3. Verifier separate from actor

GBQA (arxiv.org/html/2604.02648) is the cleanest published version of this split: a QA agent (actor) runs a ReAct loop and files bug reports; a separate critic agent (verifier) matches reports against human-annotated ground truth — even Claude-4.6-Opus-thinking as actor clears only 48.39% of GBQA's planted bugs, arguing against ever trusting an actor's own claim. Agora already has this split in miniature: the toddler never judges; only DeepSeek's `judge` phase does (`qa_director_core.judge`, `:202-222`), and its verdict is intersected against fingerprints the session actually *observed* — a `finding` whose cluster doesn't survive that intersection is downgraded to `held` (`:213-218`). That intersection is effectively "require replay-to-reproduce before filing."

The harness-caused-false-positive class must be first-class, not folded into "held." The proving-ground scorecard is the cautionary tale: probes D and G were both marked pass, then retracted, because clicks recorded outcome `"ok"` and produced real screenshots while never reaching the app (`docs/northstar/proving_ground/SCORECARD.md`, D's "Second correction" and G's 2026-09-12 row — a shared-Wayland-seat focus bug, fixed by defaulting to a private Xvfb plus "an input-liveness pre-check that fails the run if a click never mutates the page"). That pre-check is the template: confirm actions landed (state hash changed after a known-mutating action) before trusting any finding, and tag a failing session `harness-error`, never `inconclusive`/`held` — those get re-triaged by DeepSeek and can accumulate as false "the app never changes" findings, which happened twice here. A dedicated status also stops `termination_ready` (`qa_oracle.py:264-284`, gates on `qualifying` sessions with `new_fingerprints == 0`) from counting a dead-input session as clean.

Local qwen2.5-vl 7B alongside qwen3-coder on one RTX 3060 (12GB): feasible only quantized. FP16 Qwen2.5-VL-7B wants ~17GB; 4-bit quantization brings a same-size text model to ~4.7GB (modelfit.io/gpu/rtx-3060), and the VL variant needs extra margin for its vision encoder (even the 3B variant strained an 8GB card unquantized, per huggingface.co/Qwen/Qwen2.5-VL-3B-Instruct/discussions/20). Running both quantized 7B-class models concurrently on 12GB is tight, not comfortable — worth a real measurement before committing. Gemini via CLI avoids the VRAM contention but adds a paid-API hop; acceptable per D16 (no *Claude* in unattended paths) as long as it stays capped like the existing DeepSeek budget gate (`specs/cascade-director.md` AC-15). A judge is needed at all only for the visual-oracle class — never for state/trace oracles (exact comparisons) or metamorphic relations (exact by construction).

## 4. Per-project profile shape

A second project supplies the same six things `projects/ouroboros/qa.toml` and `projects/proving-ground/qa.toml` already supply for this one, generalized:

- **`[target]`** — path, interpreter, one-line description, `entry_paths` (route or scene list). Unchanged from today (`cascade_types.QaProfile`).
- **`[backend]`/`[desktop]` or browser** — `kind = "browser"|"desktop"`, and for desktop: `launch_argv`, `window_title`, `debug_port`, `display`, `screenshot_every_action`, `log_error_patterns` (`specs/qa-desktop-backend.md` AC-2). A non-game "desktop" CLI tool profile would set `launch_argv` to the binary and `window_title`/`debug_port` to whatever thin debug-port shim it wraps its own state in — the seam doesn't care what's on the other end.
- **`[[scenario]]` rows** — `id, goal, expect, start, max_actions, allowed_actions` (`Scenario`, `cascade_types.py:384-393`) for coverage-mode QA; unchanged.
- **`[director]`** — `rules_dir`, `invariants`, `max_steps`, `checkpoint_every`, `max_calls_per_session`, `sessions_per_day`, `interval_min`, `max_rules_chars`, and one or more `[[director.feature]]` (`id`, `rules`, `entry`) for mission-mode QA (`specs/cascade-director.md` AC-18-19). Rules files are project-authored markdown, capped and distilled — never the full bible.
- **Detectors** — the five generic ones (`DETECTORS`, `cascade_types.py:732-733`) apply to any project unmodified (console/pageerror/http-5xx/json-not-page/expectation-failed); a game additionally needs its trace-window detectors (Ouroboros: `simulation/invariants.py` equivalent, or the C `om_trace_*` API for a from-scratch project) declared as an out-of-band pytest/ctypes suite, not inside `qa.toml` — T1 never goes through the browser/desktop seam at all.
- **Planted bugs** — a project-side build flag analogous to `MOVER_BUG 0-4` (Probe C) or `TOY_FAULT` (`qa_control.py`'s desktop daily control, AC-12, `specs/qa-desktop-backend.md:117-127`): one clean build, N faulty builds, one env var to pick. This is not optional — see Q5.
- **Personas** — a project-side prompt fragment (playtest-agent's finding) layered onto `prompts/qa-explorer.md`/`director-plan.md`, e.g. "reckless: never retreats, always attacks the nearest target" for an RTS, versus "cautious: never submits a form without re-reading every field" for a form-heavy app. These belong in the profile (`projects/<slug>/personas/*.md`), not in Agora's shared prompts, the same separation `rules_dir` already establishes for feature rules.

## 5. Harness positive controls at the QA level

Ouroboros's own `MOVER_BUG`/`OM_BUG_*` pattern (Probe C) is the template, already proven end to end: a build flag flips in exactly one known way, the detector suite must fire on the matching variant and stay silent on every other, and fingerprints must be stable across seeds (`docs/legacy/proving_ground/PC-t1-detectors.md`). The QA-level equivalent already exists for both backends: `qa_control.py`'s daily control, `FaultServer` (browser) or `TOY_FAULT=script-error|crash|stale` (desktop, AC-12), must make every `DETECTORS` member fire or exit non-zero (`specs/qa-desktop-backend.md:117-127`). Mutation testing is the general prior art — "testing the tests" by planting faults the suite must kill (dl.acm.org survey); TITAN and GBQA both validate against a fixed set of planted/injected bugs with human-verified ground truth (GBQA: 124 implants across 30 games, three tiers).

Three checks compose the QA-level control: (1) **input-liveness precheck** — a known-mutating action must change queryable state before any real mission runs; exists for the desktop backend post-D/G-retraction and should be a hard precondition on every session; (2) **scenarios that must be able to fail** — every `[[scenario]]`/`[[director.feature]]` needs a planted-bug variant where its `expect` is known to fail, else the scenario is vacuous (CLAUDE.md: "a test that cannot fail is a defect"); (3) **zero findings on a planted build is a harness failure, not a clean pass** — extend `is_qualifying`'s "every `DETECTORS` member fired that day" rule (`qa_oracle.py:244-261`) to scheduled planted-build runs, and block convergence outright on a miss, not just delay it.
