# A6 — Content at Scale: Era Packs, Landscape Packs, and a Factory That Verifies Them

## 1. How data-driven games ship dozens of packs on one engine

Paradox's Clausewitz games are the closest precedent to "engine speaks abstractly, content is data": Stellaris/EU4 script and events are plain-text def files, and the community tool CWTools (github.com/cwtools/cwtools) provides `.cwt` rule files that give live validation — syntax errors, missing keys, and "does this scope even exist" checks — before the game ever loads the mod (github.com/cwtools/cwtools/wiki/.cwt-config-file-guidance). RimWorld does the equivalent in XML: every `Def` subclass can override `ConfigErrors()`, and because it is checked at startup via `[DefOf]` binding, a bad def surfaces once, at load, with the def named, rather than as a runtime crash mid-game (rimworldwiki.com/wiki/Modding_Tutorials/ConfigErrors; rimworldwiki.com/wiki/Modding_Tutorials/Linking_XML_and_C). Fortnite's UEFN pipeline validates Verse code against the engine's real API through deterministic checks before "cooking," and Epic runs each cook in an isolated container specifically because it is processing untrusted third-party content (hashicorp.com/resources/cooking-with-nomad-powering-the-fortnite-creator-ecosystem). Godot's own answer is PCK files loaded at runtime, with community mod-loaders doing resource overrides rather than engine forks (docs.godotengine.org/en/stable/tutorials/export/exporting_pcks.html).

The common shape: (1) a schema or def format the content author writes directly, (2) a fast, deterministic validator that runs before the content is trusted, separate from any "does it play well" pass, (3) the engine never special-cases a mod by name. Ouroboros already states this exact contract: `docs/bible/epics/E-20-multi-era-and-monetization.md` R-145-01/R-145-02 forbid any `if era ==` branch and require per-era variation to be config the engine reads uniformly, and R-145-04 requires "a contract test loads every shipped pack against the same engine build" — that is CWTools' and RimWorld's load-time validation, already specified, just not yet built as a factory step.

What breaks at scale in every one of these systems is not the schema, it's the things schema can't see: cross-mod interaction (Paradox mods conflict on load order and patch targets, hence the whole `PatchOperations` sublanguage — rimworldwiki.com/wiki/Modding_Tutorials/PatchOperations), save compatibility (a def added or removed after a save exists), and performance (validating hundreds of mods at boot has to stay cheap or it kills iteration speed). Ouroboros's structure limits two of these by design: R-150-01/R-150-02 (`E-20-multi-era-and-monetization.md:97-99`) require layouts and civilizations to be valid in *every* era with no era tag, so there is no cross-pack dependency graph to break — packs are parallel, not layered. Save compatibility is the one still open: E-20 lists "Era transition resets the ledger or the world" as a named way-it-could-be-wrong (`E-20-multi-era-and-monetization.md:150`), and a growing pack count is exactly what stresses this.

## 2. Procedural generation QA: solvability isn't enough, and E-17 half-has the tooling already

The PCG literature's dominant method past "does the level solve" is agent-based or graph-based playthrough validation: Spelunky's academic reconstructions use a graph representation of rooms plus an agent that walks the generated level to prove reachability, and record completion time, backtracking, and failure rate as level-quality signals, not just a pass/fail (researchgate.net/publication/301986769; arxiv.org/pdf/2409.06349 does the same for match-3, driving thousands of generated boards through an automated solver before any human sees them). The recurring practice across studios is: sweep thousands of seeds headlessly against hard invariants (reachability, no soft-lock), keep a small set of golden seeds whose exact output is checked byte-for-byte on every change (a determinism regression test), and sample a handful of seeds for human visual review because no automated metric catches "this reads as generic."

E-17 already has the hard-invariant half built: `simulation/fairness_evaluator.py` computes four ratio metrics (path balance, travel time, vantage balance, hazard balance) each checked against an archetype's tolerance band, with an explicit skip rule for metrics that are undefined when a node type is absent (`simulation/fairness_evaluator.py:24-99`, the "D1 zero-count scope narrowing" comment at line 25). `E-17-map-generation.md` R-117-01/R-117-02 spec exactly the sweep-and-log pattern, but Q-113-01 is still open on what happens when a map fails: regenerate up to 5 times (the bible's stated behavior) or accept-and-log (what the code, A-393, currently does) — `E-17-map-generation.md:151-153`. This is the one flag a factory gate for new content cannot work around: a "gate" is either a hard reject or a soft log, and right now it is genuinely undefined which.

The recommended factory gate for a new biome or layout entry, buildable today against existing code: run `evaluate_fairness` over a fixed set of N seeds (e.g. 500) with the new layout forced into the candidate pool, require a pass rate above a threshold (not 100 percent — R-117-03's hard constraints, `E-17-map-generation.md:145`, are the true floor; the ratio metrics are soft), keep 3-5 of those seeds as golden fixtures asserting byte-identical map-seed output per the determinism contract in `CLAUDE.md`, and route a fixed handful of seeds to a T2 screenshot pass against `E-17`'s still-missing reference notes (`E-17-map-generation.md:171`, "Reference required... missing"). That reference gap blocks the visual half of this gate today.

## 3. Era pack and landscape pack as buildable artifacts

**Era pack**, schema per `E-20-multi-era-and-monetization.md` R-146-01 (`E-20-multi-era-and-monetization.md:45`): identity (name, spatial scale, tone), three tier definitions, 18 unit models with per-type silhouette conformance, 3-6 tiered structures, 5-10 environment objects, six ability visual mappings, attack visual categories per type, naming pools, chronicle/briefing fragments, a strategic view definition, and per-era config values (stat profile per tier, restriction mask, elevation flag, reinforcement and fog constants). R-146-02 requires those config values identical across the three launch eras except art/names/prose — this is the load-bearing rule for a "mechanics unchanged" test, but Q-146-01 leaves open whether "identical" means byte-identical or only tempo-identical.

**Landscape pack**: one or more `layout_library/*.json` entries (`simulation/layout_library.py:7`), each restricted by R-112-06 to zone positions, connectivity, and chokepoint specs only — explicitly never gradient values, era visuals, absolute coordinates, or difficulty (`E-17-map-generation.md:41`). A landscape pack is therefore purely spatial topology; the era kit (S-119's still-open procedural architecture ambition, `E-17-map-generation.md:73-75`) supplies the skin.

**Tests that prove one**: the R-145-04 contract test (load against the current engine build, zero code changes) run per pack; a config diff against the invariant in R-146-02/E-20's Invariants section ("The three launch eras share identical mechanical config," `E-20-multi-era-and-monetization.md:139`); the balance harness (`E-21-offline-ai-pipeline.md` S-156, R-156-01/03) re-run per pack and diffed against the baseline win-rate matrix so a pack that changes outcomes despite passing the config diff is caught.

**QA missions that prove it plays**: a full chapter loop (mission, outcome resolver, time jump, chronicle) run headless with the pack loaded, per the Round 1 build order already defined in `docs/legacy/mvp/feature_mvps.md`; the chronicle output run through the same validator S-153 defines (schema, word limits, banned language, `E-21-offline-ai-pipeline.md:46`); a T2 pass against the era's reference set per `E-18-visual-style-and-combat-visuals.md` R-138-02 — currently a manual-only check, since R-132-02 states no automated silhouette classifier exists at launch.

**Content card vs code card**: `E-21-offline-ai-pipeline.md`'s gate note is explicit that this epic is "Claude-side and Westley-side tooling, not Agora build work, except the loaders and validators the game needs" (`E-21-offline-ai-pipeline.md:14`). So prose, names, and asset direction are authored by the library builder pipeline (S-153, S-155) under Claude/Westley, never by Agora — the same fencing principle that keeps Agora off `docs/bible/**` (per `CLAUDE.md`'s "Sub-agents implement, never design") extends naturally to "Agora verifies content, never authors it." A content card's acceptance commands are validator and diff-tool invocations; a code card's acceptance commands are the fenced tests Agora cannot edit (`docs/northstar/PLAN.md:63`).

## 4. What scales linearly, what must stay constant, and what generic Agora needs

Linear with pack count: manifest files, per-pack validation reports, per-pack contract-test runs (same test, parameterized), win-rate matrix rows, naming pools. Constant regardless of pack count: the C sim engine, the fairness evaluator, the contract test definition itself, the T1 trace format, and the validator code — these are exactly the pieces R-145-01 through R-145-04 already forbid from branching on era.

For a content card to not be a special case inside Agora's existing model (`docs/northstar/PLAN.md:48`, task = acceptance commands as ground truth), it needs three things that don't exist yet: (a) **data validators as acceptance commands** — a script like `scripts/validate_era_pack.py <manifest>` returning nonzero on failure, so a content card's `acceptance:` list looks exactly like a code card's, just calling validators instead of pytest; (b) **a content diff fence** — a script, itself fenced (Agora cannot edit it, same as the test fence), that diffs a new pack's mechanical config values against the R-146-02 invariant and fails the card if a value differs; this is the content equivalent of "tests Agora cannot edit" and is what actually enforces A-321's no-mechanical-differentiation rule at build time rather than by manual review; (c) **a content-only positive control** — per `docs/northstar/PLAN.md:63`'s rule that every detector needs a positive control, one deliberately-broken pack fixture (a stat one tier off, a banned word, a name within 3 edits of an existing one) that the validator must catch before it is trusted on real packs.

Agora's existing card-sizing rule (3-5 public symbols, one algorithm family, `docs/northstar/PLAN.md:214-217`) doesn't map onto content, which has no algorithm to isolate. The factory needs a parallel sizing rule — one pack, or one library category, per card, bounded by the entry-count checklist R-146-01 already specifies rather than by line count.

## 5. Pitfalls and how others catch them

**Passes schema, plays badly.** Schema and referential-integrity checks (RimWorld's `ConfigErrors`, CWTools' rule files) catch malformed content, not boring content. The PCG literature's answer is playthrough metadata beyond solvability — completion time, backtracking, failure rate (arxiv.org/pdf/2409.06349) — and this project already half-has the equivalent: log outcome *diversity* from the balance harness's bot matches (S-156), not just the win-rate matrix, as a boredom proxy for a new layout or unit skin.

**Prose leaks IP.** `CLAUDE.md`'s "No IP exposure" rule is enforced today only by S-153's banned-language pass (`E-21-offline-ai-pipeline.md:46`) and the edit-distance dedup already required for names (R-154-06, R-153-03). Full trademark-style similarity search (corsearch.com/trademark-solutions/trademark-screening) is heavier tooling than this project needs; the cheaper, already-spec'd move is to extend the existing edit-distance check from "no two names within 3 edits of each other" to "no generated name or phrase within N edits of a fixed denylist of known IP terms" — same technique, new comparison set.

**Balance regressions across packs.** Because R-146-02 requires identical mechanical config across launch eras, a real regression can only come from a pack-loading bug, not intentional tuning — which is exactly what the content diff fence in section 4 is for: it should catch this before the balance harness (S-156) even runs a single match. When S-151 (later: eras that feel different) eventually reopens, the fence needs to become "within band" rather than "identical," so it should be written swappable now rather than deleted later.

## Open questions for Westley

- Q-113-01 decides whether a new layout/biome's fairness gate is a hard reject or a soft log — the factory's pass/fail behavior for section 2's gate depends on it.
- R-132-02 states no automated silhouette classifier exists at launch, and R-138-02's visual-style check is manual review only. Is manual T2 review still acceptable once the factory is producing dozens of eras, or does content-at-scale need to pull visual-QA automation earlier than currently planned?
