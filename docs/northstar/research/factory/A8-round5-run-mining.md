## Root-cause classification

**(1) Harness defect — 1 incident, ~13 candidates, ~17.5 minutes.** R7a: `csrc/resolve.c` used `fmin` with no `math.h` include; function-level splice can't add header lines, so no candidate body could ever compile. Directly verified in `_archived-prefix-204a3-e05-core-attack-20260918-1301` and `-1309`: 6 and 7 candidates respectively, every single one 0 passed / 10 failed, identical, matching R7a's "14 candidates... 0/10 identically" almost exactly. Caught by a human watching a live `agy` intervene call mid-flight, not by the harness itself. **Would-have-caught mechanism: "skeletons carry standard includes" (`math.h`, `stdlib.h`, `string.h`) — yes, fires cleanly, this is the cheapest fix in the whole audit.**

**(2) Card cut / ordering defect — 3 confirmed circular/mis-ordered cuts, plus 8 stale-card SPEC-INVALID hits.** R7b/R7c: 204a1 and 204a3 each needed the other's function to pass their own acceptance test — true circularity, not a coding failure, confirmed by reading both cards' tests against the actual split. Cost: two full UNSATISFIABLE cycles (`_archived-superseded-204a1-*-1058`, `-1333`, 4 candidates each) before the recut, plus a stale terminal marker (R7g) that stalled the dispatcher on `driver: idle` for four cycles until archived by hand. Separately, 8 SPEC-INVALID markers in the window (200-e02, 202a1, 203b2 x2, 203d, plus 202z1's first attempt) are all the cheap flavor of this defect: `fail-first gate: ... passed pre-change` — the card's own acceptance was already green before any candidate touched it, meaning it was queued after something else had already satisfied it. These cost 0 wall-minutes each; the fail-first gate already catches them for free. **Would-have-caught: tick-stage closure lint — yes for the circular pair (that's its whole design point, R7b/R7c are its citation); the fail-first gate already catches the stale-card flavor today, no new mechanism needed there.**

**(3) Test/fixture defect (unsatisfiable, vacuous, confounded) — the largest class by both incident count and burned attempts.** Six distinct fixture defects found by hand in R7e, R7h, R7i, R7k, R7l, plus a seventh (204b3, below) found live during this mining pass:
- R7e: `test_R_036_05` Case 2 confounded — the "defender" had enough budget to legitimately counter-attack under the bible's own no-scripted-villain rule (S-032). Fixed by narrowing the assertion to the region under test (R7f), not by changing behavior.
- R7h: `test_control_e05_agent_reads_live` unsatisfiable by construction — the whole 3d decision loop finishes for every faction before 3f resolves anything, so no candidate could ever see same-tick mutation. Removed from acceptance.
- R7i / R7k: same-target re-declaration — a target crushed mid-tick gets re-evaluated and re-attacked by `om_step_decisions` before the test can read back a single attack. R7i fixed once by moving a fixture line; R7k hit the same pattern where no fixture reordering was possible (`R_038_01`), and remains an open bible gap (does the sim need a "don't re-target what you just resolved this tick" rule?).
- R7l: `test_control_e05_garrison_before_damage` vacuous — reused numbers from `R_038_01` where `military + damage` never goes negative, so the `fmax(0.0, ...)` clamp this control exists to test never engages under either the correct or the buggy order. 14 attempts across two runs could not have tripped it; the fixture, not any candidate, was missing the distinguishing case. The corrected numbers were worked out by hand and left for whoever redesigns the fixture.
- **204b3 (new, found live during this mining pass, timestamped 2026-09-19 08:14, archived to `_archived-superseded-204b3-e05-damage-history-20260919-0814` mid-mining):** the exact R7i/R7k pattern recurring a third time, now on a different card (`S-034`, candidate scoring) — a forced 0.5 draw triggers an opportunist surprise attack that mutates region 1 mid-tick, contradicting the test's assumption that candidate attractiveness reads unmutated baseline stats. The advisor's own abort message named this precisely (region-mutation-before-read), unprompted, on the first cycle — confirming R7i's prediction word for word ("worth a deliberate answer eventually rather than continuing to route around it fixture by fixture... not blocking anything today").

Burned attempts: R7e (3 INCOMPLETE cycles, ~28 minutes), R7h (found inline mid-cycle, no extra burn), R7i (1 UNSATISFIABLE cycle), R7k+R7l (204b1's second and third releases, 3+10 attempts, ~2 hours), 204b3 (4 candidates, ~1.7 minutes, caught same-cycle). Human hours: R7e/R7f was a multi-hour hand-diagnosis pass (patched reference logic into `resolve.c`, instrumented, computed exact numbers); R7l's fixture rework is still undone. **Would-have-caught: fixture-defect detectors — tick-order reachability catches R7h and 204b3 before any model call, branch-coverage-against-a-reference-stub catches R7l, a two-agent fixture warning catches R7e. Yes for all four, and this is the evidence the plan cites them against.**

**(4) Already-merged code violating a documented contract — 2 incidents, both severe, both from the same human hand-patch chain.** R7g: 204a1's merged `om_step_telegraphs` compiled, lint-passed, and passed its own acceptance test, but silently violated ALG-20/21/22 six different ways (stochastic never multiplied into net, wrong thresholds, wrong damage formula, wrong entrenchment check, conquest-on-band instead of the real gate, no delta write-back at all) — none of which its own single-field acceptance test could see. This is the plan's diff-scoped mutation gate citation. R7j: the fix for R7g, from the same hand, accidentally added conquest/garrison/ownership-transfer into 204a1's function — 204b1's exclusive scope — making every one of 204b1's first 10 attempts structurally unsatisfiable, since the region was already mutated before 204b1's own pass ran. This is the plan's parent-patch fence citation (commit `c3aa447`). Cost: R7g's bug survived 204a1's own DONE and stalled 204a3 at a 4/11 ceiling for three full cycles (20+ candidates) before being found; R7j cost 204b1 its entire first 10-attempt budget (`_archived-prefix-204b1-*-1945` through `-0143`, 18 dirs, ~120 minutes). **Would-have-caught: diff-scoped mutation gate for R7g (a mutant flipping any of the six wrong constants still passes 204a1's own test — textbook under-testing); parent-patch fence for R7j (rejects a hand patch touching another card's named scope, exactly the edit that caused it).**

**(5) Brief error — 0 confirmed incidents in this window** beyond what's already folded into class 3/4 (the briefs mirror the buggy reference math, but the bug was in already-merged code the brief correctly assumed, not in the brief's own text).

**(6) Worker (model) inability — 0 confirmed incidents.** Every terminal non-DONE outcome in the window traces to a harness, cut, fixture, or upstream-code cause, never to "the model tried and simply couldn't write correct code" once the actual target was satisfiable. The one `regression`-reason candidate (`204b1-0257`, candidate 1, 5/0 own tests) is worth noting as the inverse case: a candidate that looked complete and got correctly rejected by the whole-suite regression gate — the gate is doing its job, this is not a failure mode.

**(7) Bible/rule gap — 1 open, now three-times-confirmed.** Whether the sim should skip re-evaluating a target it already resolved an attack against in the same tick (R7i, R7k, 204b3). ALG-14/15 say nothing about it. Flagged, not guessed, each time; still open. No mechanism in the current B.7 draft "catches" a bible gap before a human decides it — the fixture-defect detector can flag the *symptom* (a confounded/unsatisfiable test) but the actual rule question still needs Westley or a design-lane pass.

## Five things the data says that the plan does not yet account for

1. **The advisor's own abort text is already a near-perfect root-cause diagnosis tool when it fires** — the UNSATISFIABLE.md abort messages for R7h, R7i, and the newly-found 204b3 read almost word-for-word like the DECISIONS.md rows a human later wrote, down to line numbers and exact contradiction. The plan treats fixture-defect detection as new tooling to build; a cheaper first step is auditing why the advisor sometimes aborts correctly (R7h, R7i, 204b3) and sometimes exhausts all resets without concluding impossibility instead (R7l) — that's a prompt/threshold gap in an existing mechanism, not an absent one.
2. **Advisor hints can name the real cause and still make things worse.** The `advisor_hint.md` files for `204b1-*-2107` and `-2116` (both mid-plateau, before R7j's fix) explicitly describe "om_step_telegraphs already applied damage and garrison" — the exact R7j finding — five-plus hours before the human diagnosed it, but the hint's instruction was "route around it" (read `r->conquest` instead of recomputing), not "this needs an upstream fix." A hint that correctly identifies a structural confound but recommends coping with it, instead of escalating it, spends cycles the plateau early-stop is meant to save.
3. **The regression gate fired exactly once in the entire window and it was correct** — `204b1-0257` candidate 1 passed 5/0 on its own tests and was rejected for regressing something else. This is good news for A2's fence design but means the window has only n=1 to validate the regression tier against; PF-7 (replay the 203b1 regression) is the only real evidence base until more data accumulates.
4. **The cheapest defect class (stale-card SPEC-INVALID, 8 of 77 dirs, $0 and 0 minutes each) is already fully handled by an existing mechanism** (the fail-first gate) and needs no new B.7 machinery — worth stating explicitly so the failure-mode table doesn't imply every row needs a new detector.
5. **A structural confound can recur across unrelated cards** (R7i on 204a3, R7k on 204b1, now 204b3 on an S-034 card) faster than the human decision about it lands — the bible/rule gap (same-tick re-targeting) is still open as of this memo and just cost a fourth-ish incident. The plan has no mechanism class for "the same open Q- flag will keep taxing new cards until it's answered"; today the only defense is that the advisor keeps re-discovering and re-flagging it, which works but is not free.
