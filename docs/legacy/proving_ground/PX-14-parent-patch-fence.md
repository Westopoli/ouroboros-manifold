# PX-14 — Parent-patch fence (proving the factory)

Run 2026-09-21 (ouroboros commit at run time: `main` after PX-19/PX-7; `scripts/specfactory/parent_patch_fence.py`, `tests/specfactory/test_parent_patch_fence.py`, 9 synthetic tests, whole `tests/specfactory/` suite 172 tests green). Claim (Factory, "Gates"): parent patches obey the same ownership check as cards; a patch may touch only the function its diagnosis names and never another card's scope.

Result: **partial pass** — the fence built correctly rejects the real violation and accepts the two real clean patches, but with real caveats worth carrying into the design lane, not papered over.

## The incident, corrected

R7j (`docs/northstar/research/harness_defects_2026-09-17/DECISIONS.md:84`): `a493cfd` ("fix(csrc): om_step_telegraphs implemented the wrong damage formula", card `204a1-e05-telegraph-maturation`'s own hand patch) genuinely fixed 204a1's formula, but also added conquest detection, garrison, and ownership transfer inside `om_step_telegraphs` — entirely `204b1-e05-conquest-garrison`'s job (`om_step_resolve`), per its own card title and acceptance list. `c7f4a5d` ("remove conquest/garrison from om_step_telegraphs, it's 204b1's job") is the repair. `c3aa447` ("implement 204b1's conquest and garrison logic by hand") is a later, separate, sign-off escalation — not a fence violation, and out of scope for this replay.

**The subtlety that makes this hard to catch mechanically:** `a493cfd`'s diff touches only `om_step_telegraphs`, which genuinely is 204a1's own `snippet_symbol`. A function-ownership check alone accepts it. What makes it a violation is invisible to a line-range-to-function-name check: the patch did another card's job *inside* the function it legitimately owns.

## Two checks, as specified

1. **Function ownership** (`check_function_ownership`): every function a diff's hunks overlap — by post-patch line range, mapped through `card_lint.py`'s own brace matcher (`find_function_span`/`all_defined_symbols`), not git's funcname-heuristic hunk headers (confirmed the two agree on all three real replay diffs during development, but the brace matcher is the one actually used, since it doesn't depend on git's C-language heuristic being enabled) — must be in the named card's own `snippet_symbol`, or unclaimed by any card. A function another card's `snippet_symbol` lists is a violation.
2. **Scope capture** (`check_scope_capture`): every OTHER project-scoped queued-or-parked card's acceptance node ids are run once before the patch and once after, as a single combined `pytest` invocation each side (not one subprocess per card —197 covering cards on the real replay). Any test that goes red-before/green-after is attributed to whichever card's acceptance list names it.

Fence accepts iff both checks pass.

## Limitations found, stated plainly

1. **The queue is shared across five unrelated projects** (`agora`, `agora-proving-ground`, `ouroboros-manifold`, `switchboard`, `the-best-salesmen` — confirmed via `grep -h "^project:" ~/Projects/agora/queue/*.md ~/Projects/agora/queue/parked/*`). An unfiltered scope-capture run picked up a `the-best-salesmen` card (`queue/parked/006-best-salesmen-test-skip.md`) whose acceptance command named `tests/test_app.py`, a file that does not exist in this repo. `pytest` given an uncollectable node id aborts the *whole* combined invocation (returncode 4, "file or directory not found") and prints no per-test FAILED/ERROR lines — `suite_regression.py`'s `parse_pytest` (built by PX-7, reused here) then silently reports 0 passed/0 failed, indistinguishable from a genuinely clean run. First run of case (a) reported a false ACCEPT this way. Fixed two ways: `load_cards()` now filters to `project: /home/westopoli/Projects/ouroboros-manifold` by default (`--project` to override), and `run_fence()` now refuses to trust any scope-capture run whose returncode isn't 0 or 1 (`_require_clean_pytest_run`, raises loudly instead of reporting false green). Not a fix to `suite_regression.py` itself — that stays PX-7's file, unmodified; the guard lives entirely in this probe's own module.
2. **The queue also carries stale card revisions under the same story.** `204a3-e05-battle-damage-bands.md.superseded` sits in `queue/parked/` alongside its replacement `204a3-e05-core-attack.md`; both claim overlapping `snippet_symbol`s, which is why the case (a) capture list double-attributes two of the seven tests to both card ids. "Every queued or parked card" taken literally (as the brief specifies) includes every historical revision a card ever had, not just the live one. A production version of this fence would need a "latest revision only" filter analogous to the project filter above; this probe reports the raw double-attribution rather than silently resolving it, since deciding which revision is authoritative is a queue-semantics question, not a mechanical one.
3. **Check 2 cannot distinguish "stole another card's scope" from "legitimately unblocked a downstream dependent card's test by fixing a shared upstream bug."** `204a3-e05-core-attack` and `204a3-e05-battle-damage-bands` both depend on `om_step_telegraphs`'s output (`effective_attack`/`effective_defense`), so fixing 204a1's own formula bug correctly unblocks their tests too — that is not scope capture, it is normal dependency unblocking, and `a493cfd`'s own commit message says as much. The mechanical red-before/green-after signal cannot tell these two cases apart; only `204b1-e05-conquest-garrison`'s capture (garrison/conquest/ownership-transfer logic, wholly outside `om_step_telegraphs`'s documented job) is the real violation. This probe reports both, correctly attributed by test id, and leaves the true-violation-vs-legitimate-unblock judgment to whoever reads the fence's output — automating that judgment (e.g., only counting a capture against a card whose own `snippet_file` differs from the patch's, or whose dependency chain doesn't include the patched function) is a design decision for the design lane, not something to build unasked here.
4. **`test_R_038_03_no_conquest_ever_happens`'s capture may be weaker evidence than the other six.** Per R7k (`DECISIONS.md:85`), 204b1's conquest logic only ever reached a 4/7 ceiling even after R7j's fix landed; a "no conquest happens" negative-shaped test going green could reflect any working combat-resolution code existing at all, not specifically the stolen garrison logic. Flagged, not resolved — consistent with the brief's own hedge about R7k's messiness.

## Design consequences

Filled by the design lane, 2026-09-21.

1. The parent-patch fence is both checks: function ownership, then scope capture over every other card's acceptance.
2. A capture is classified mechanically: if the captured test's owning symbol still carries a STUB marker at the time of the patch, the patch did that card's job (violation, as 204b1 in `a493cfd`); if the owning symbol is implemented, the patch unblocked a downstream card (allowed, as 204a3 here). The two captures the probe could not separate split cleanly under this rule; it is written into the fence, with the a493cfd replay as its positive control and the 204a3 captures as its negative.
3. Include-only diffs have no owner and are allowed only for standard headers; a `"..."` include is rejected (audit item 5).
4. Check 2 runs in the CPU slot (67 s here); the acceptance runner must filter cards by project and treat a pytest abort as an error, never as 0 failed (the false 0/0 the probe found is the same class as PX-03's dead-input sessions).
