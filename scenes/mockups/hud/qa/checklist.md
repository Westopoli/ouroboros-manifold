# HUD mockup QA checklist

Real measured numbers from `scripts/mockup_qa.sh` and `scripts/mockup_verify.sh` runs on 2026-09-22, Godot 4.6.3, llvmpipe, 1280x720 unless noted. This is the fresh-eyes fix pass: camera clamp now bounds the visible ground extent (not the camera centre), `qa/box.json` reconciled with the committed screenshot, Q3 promoted, an `after_tab` shot added, and the layer-2 accent moved off the enemy's red. A third real bug was found and fixed in this pass (beyond the two below): `qa_camera()` called `centre_on()` before `set_height()`, so once the clamp became height-dependent, a height change could get silently swallowed by a stale clamp from the previous height — see the BOUND-8 note below. Two harness defects were found and fixed on `main` before this branch started (not by this brief's implementor): an Xvfb screensaver blanking after 600s (`a98c47f`), and `qa_boot.gd` leaving autoloads running so `SimBridge`'s dead child sim froze the driver (`b65afa8`). Two real bugs were found and fixed *in this mockup* in the original pass (DRAG-X below, and a `%`-format crash in `verify.gd` that could mask a failure — both documented under their oracle).

`scripts/mockup_verify.sh hud` → `VERIFY OK`, exit 0. `scripts/mockup_verify.sh hud --plant <id>` → `PLANT <id> LIVE` for all 6 ids, confirmed individually (each plant run shows exactly its own named check FAIL and nothing else — see full plant sweep below).

**The BOUND-8/qa_camera bug, found by this check.** Once the clamp became height-dependent (this pass's fix), `qa_camera(height, x, z)` called `_camera_rig.centre_on(x,z)` (clamps against whatever height was still current) *then* `_camera_rig.set_height(height)` (re-clamps the already-clamped position against the new height). Going from a wide clamp range to a narrower one this still works; going the other way, the stale value from the old, tighter clamp already sits inside the new, looser range, so the second clamp is a no-op and the camera silently stays at the wrong spot. Caught by temporarily making `_assert` print every message (not `FAIL`-gated) via a one-line local edit, running `mockup_verify.sh hud`, and hand-checking the h=150 result against the clamp math by hand — it printed `cam=(3223.6,1561.7)`, the h=3000 answer, not h=150's `(5861.2,78.1)`. Reverted the debug print before committing; fixed `qa_camera()` to set height before centring.

**Why TAB-X and EDGE-X were revised, with the evidence.**

**TAB-X.** The brief's own smoke script (which I transcribed verbatim into `qa/smoke.json`) calls `qa_bind(2)` exactly once, on a selection that was never in any other group. `group-shared`'s fault ("skips removal from other groups on bind") has nothing to skip in that situation — clean and planted produce byte-identical `groups` dictionaries at `recall_2`/`state recall_2` (re-verified this pass: both `{'2': [1, 2, 3]}`). The pixel-diff oracle as specified therefore cannot discriminate this fault with this script; I did not invent a second bind call to force it to discriminate, since the brief's own template is the fixed script. GROUP-4's headless check (which does bind into group 1, then group 2, and checks group 1) is the real, already-live oracle for this fault — see the plant sweep table above.

**EDGE-X.** The brief's candidate reads "two screenshots after `key_down D` for 60 frames at the east bound are identical, `diff` < 0.001 excluding the clock crop; under `camera-unbounded` they differ." Measured this pass (post camera-clamp fix): clean `east_a` vs `east_b` (within one run) is 0.003181, not under 0.001 — because units keep wandering during the 60+60 held frames and the clock keeps ticking, and the diff tool has no crop option to exclude either. This is real simulation motion, not camera drift (`camera.x` reads exactly 3223.64 — the new ground-extent clamp at height 3000, not the old centre clamp's 6000 — in both frames' `state` dumps). The dimension that discriminates the fault is not east_a-vs-east_b within a run; it's the same checkpoint across runs: clean `east_a` vs planted `east_a` differs by **0.999390** (nearly the whole frame) — clean shows the full ground plane with a clean static stop at the clamped edge (no void at all, see Q5), planted is solid void, camera having flown to x=12150, far past the canvas. Recommend the oracle compare `east_a(clean)` to `east_a(plant)` directly rather than `east_a` to `east_b` within a run.

**Why BOX-X's clean count changed (6 → 5) and the screenshot now agrees with the table.** The original `qa/box.json` had no `wait_frames` between the `drag` verb and `state`/`screenshot`: `_finish_box()` updates `_selection.selected` and the 3D selection rings synchronously (same input-handling call), but `hud.gd`'s 2D selection panel only rebuilds on the next `_process()`, and the screenshot was grabbed before that frame ran — so the *panel text and count* in the committed `boxed.png` lagged one frame behind the true state (rings were already correct; the panel undercounted by one). This was not units wandering off a stale rectangle — world positions are fully deterministic for a given seed and frame-accurate script, and the same tick is reached every run — it was a missing frame between the selection changing and the pixels being grabbed. Added `["wait_frames", 2]` after the drag. Separately, the fixed pixel rectangle (`x:[280,1020] y:[-20,620]`) covers a different fraction of world space at different resolutions (same NDC box, more pixels per world unit at higher resolution): at 1280x720 it catches 6 uids, at 1920x1080 (the resolution the `pass1/` review batch and the committed `boxed.png` use) it catches 5. Both numbers were internally correct for their own resolution; the checklist previously mixed a 1280x720 number with a 1920x1080 screenshot. The table above is now measured at 1920x1080 to match the committed image, and the panel/state agree: `SELECTION (5)`, uids `[1,2,4,6,8]` (1 layer-1 + 4 layer-2).

## Colour fix

Layer 2's accent was orange (`Color(1.0, 0.55, 0.0)`), close enough in hue to the enemy faction's warm red (`#FF4738`) to read ambiguously in the small selection-panel dots and the layer strip. Moved to purple (`Color(0.72, 0.35, 0.95)`, `hud.gd`'s `LAYER_COLORS[2]`), well separated in hue from the enemy's red, the player's blue (`#4099FF`), and layer 1's cyan. Checked for other layer-2-colour literals: `hud_mockup.gd`'s selection `Ring` (`Color(0.3, 0.8, 1.0)`) is the generic selected-unit highlight, the same cyan as layer 1/`ACTIVE_COLOR`, shared by every selected unit regardless of layer — not a per-layer indicator, left unchanged.
